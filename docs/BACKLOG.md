## Очередь

В очереди остался только T-17, заблокированный до первого реального деплоя —
стенд мёртв, торопиться некуда. Дальнейшие шаги — в разделе «Что дальше».

### T-17 Прод-контур (заблокирован до первого реального деплоя)

Сюда же входит отложенная прод-часть T-09: отдельные прод-секреты в GitHub Actions
Secrets и запись `.env` на сервере из `deploy.yml`.

**Зачем** — стенд мёртв, но нынешние прод-конфиги при первом же деплое дадут неработающий
или дырявый стенд:

* `docker-compose.prod.yml` не передаёт `CORS_ALLOWED_ORIGINS` — прод-фронт упрётся
  в дефолт `localhost:5173`; `POSTGRES_USER` по умолчанию — суперпользователь `postgres`;
  пустые секреты не валят запуск (нет guard'ов `:?`); у postgres нет healthcheck,
  `depends_on` без `condition`;
* Dockerfile: рантайм-контейнер работает под root; `|| true` на прогреве зависимостей
  маскирует ошибки; атрибут `version:` в compose устарел;
* `show-sql: true` и открытый Swagger действуют во всех профилях, включая прод;
  actuator health отсутствует — деплою нечем проверить, что приложение живо;
* `deploy.yml`: не проверяет, что приложение поднялось; `docker compose down` роняет
  весь стек вместе с базой; триггерится на любой push в `main`, включая docs-only;
  собирает образ на VPS — прямое нарушение ARCHITECTURE §8 «не собирать на проде»;
* compose использует `postgres:15-alpine`, а решением ARCHITECTURE §2 зафиксирован 17 —
  пока база пустая, переход бесплатен.

**Готово когда** — прод-секреты в GitHub Actions Secrets; в `docker-compose.prod.yml`
guard'ы `:?`, без дефолтного `postgres`, healthcheck + `condition: service_healthy`,
CORS-переменная прокинута; Dockerfile под непривилегированным пользователем;
`show-sql` и Swagger — только в dev-профиле; подключён actuator health;
`deploy.yml` собирает образ в CI и публикует в registry (GHCR), на сервере — только
pull и перезапуск контейнера приложения без остановки базы, после подъёма —
smoke-проверка `/actuator/health`, paths-фильтр на `backend/**`; `postgres:17`.
**Изучить** — GitHub Actions Secrets и environments; healthcheck в Docker и
`depends_on.condition`; публикация образа в GHCR из CI; liveness/readiness в actuator.
**Грабли** — переезд 15 → 17 бесплатен только пока в базе нет данных — сделать
до появления реальных; образ из registry тянуть по тегу версии/digest, `latest` —
ловушка кэша.
**Опционально, перед публичным запуском** — rate limit на `/login`
(bucket4j или `limit_req` в nginx).
**Оценка** — выходные, вместе с самим деплоем.

## Что дальше, после очереди

**Шаг 2 — вертикальный срез.** Самый важный непроверенный риск проекта: фронт и бэк
ни разу не разговаривали друг с другом по-настоящему. Рубеж — «зашёл на сайт, залогинился,
увидел свой профиль и список новостей». Бэкенд для этого готов; всё упирается в реанимацию
фронта. Зона напарника, но это **критический путь** — пока его нет, каждый новый модуль
бэкенда пишется вслепую.

**Шаг 3 — новости до полного паритета.** Первый настоящий модуль: rich-text + санитайзер,
загрузка картинок через `FileStorage`, CRUD под ролями + админ-экран на фронте.
Заодно закрываются известные ограничения контракта: `POST /api/news` начнёт возвращать
201 с `id`, `previewImageDescription` появится в ответе. Модуль маленький, но проходит
насквозь через все слои — файлы, безопасность контента, роли, админка. После него
остальные 20 модулей идут по готовому шаблону.

**Шаг 4+** — по фазам MIGRATION.md. Самое сложное и рискованное (расписание
с PDF-парсером, Telegram-бот) намеренно едет позже. Refresh-токены и отзыв access-токенов
(D-03, ARCHITECTURE §4.5) — обязательная часть подготовки к первому публичному запуску.
