слой данных (T-16), долг по тестам (T-18), архитектурные тесты (T-13).

### T-15 Валидация входных данных и `?sort=`

**Зачем** — на входе API дыры, часть отвечает 500 на мусор:

* `LoginRequest` без аннотаций и без `@Valid` — любое тело уезжает в `AuthenticationManager`;
* минимальная длина нового пароля — 6, слабее валидаторов старого Django-портала (8);
* `postType` — свободная строка: контракт обещает `news`/`announcements`, но принимается всё;
* `display` — примитив `boolean`: JSON без этого поля молча создаёт скрытую новость;
* `previewImage`/`previewImageDescription` без `@Size` — переполнение колонки станет 500 из БД;
* `?sort=несуществующее_поле` на публичных списках → `PropertyReferenceException` → 500
  (в API.md это помечено «известным ограничением» — пора снять).

**Готово когда** — невалидное тело логина → 400 со словарём `errors`; минимум пароля — 8,
зафиксировано в API.md; `postType` вне словаря → 400; тело без `display` → 400
(`Boolean` + `@NotNull`); строки длиннее колонок → 400 до БД; `?sort=abc` → 400
с `ProblemDetail`; из API.md убрано «известное ограничение» про sort. Тест на каждый кейс.
**Файлы** — `AuthController.LoginRequest`, `ChangePasswordRequest`, `NewsRequestDto`,
`GlobalExceptionHandler` (+`PropertyReferenceException`), `docs/API.md`.
**Изучить** — Bean Validation на компонентах record; enum в DTO против `@Pattern` —
как выглядит тело ошибки в каждом варианте; откуда берётся `PropertyReferenceException`.
**Грабли** — невалидное значение enum в JSON даёт `HttpMessageNotReadableException`
с дефолтным телом — если выбран enum, оформить и его; `Boolean` вместо `boolean`
затронет builder и тесты; минимум длины проверяется на новом пароле, не на старом.
**Оценка** — вечер-два.

### T-16 Слой данных: N+1 на новостях, OSIV, detached-сущность

**Зачем** — страница новостей выполняет 1 + N запросов: `author` у `NewsPost` — LAZY,
а маппер собирает `authorName`, поэтому на 20 новостей уходит 21 SELECT.
`spring.jpa.open-in-view` по умолчанию `true` — держит соединение БД на всё время
HTTP-запроса и маскирует такие ошибки. `changePassword` сохраняет detached-сущность,
пришедшую из секьюрити-контекста, вместо перечитывания по id в транзакции.
На FK `news_post.author_id` нет индекса (PostgreSQL не индексирует FK сам).

**Готово когда** — выдача `/api/public/news` — ровно два SQL (данные + count),
проверено по `show-sql`; `open-in-view: false` и приложение с тестами зелёные;
`changePassword` перечитывает пользователя из репозитория; changeset 006 с индексом
по `author_id`.
**Файлы** — `NewsRepository` (`@EntityGraph` на `findAllByDisplayTrue`), `application.yaml`,
`UserService`, новый changeset.
**Изучить** — как `@EntityGraph` превращается в LEFT JOIN FETCH; предупреждение
`HHH000104`: почему пагинация с to-one графом безопасна, а с коллекцией уходит в память;
что такое OSIV и почему его дефолт считают ошибкой дизайна; managed vs detached
и что на самом деле делает `save()` у Spring Data.
**Грабли** — после `open-in-view: false` могут вылезти `LazyInitializationException` там,
где сущность утекала за границу транзакции — это полезные падения, чинить выборкой,
а не возвратом OSIV; рабочий пример `@EntityGraph` уже есть в `TeacherRepository`.
**Оценка** — вечер.

### T-18 Тесты: дыры покрытия и слабые ассерты

**Зачем** — смена пароля не покрыта вовсе (ни happy-path, ни «неверный старый» → 400);
`POST /api/news` не проверяется на модератора, анонима (401) и валидацию тела;
пагинация и сортировка публичных списков не ассертятся, хотя это контракт фронта;
часть тестов проверяет только статус-код без тела `ProblemDetail`;
в `UserIntegrationTest` пароль в setUp сохраняется в обход `PasswordEncoder`.

**Готово когда** — перечисленные сценарии покрыты; ассерты на ошибки проверяют статус
и тело (`status`/`detail`/`errors`); формат `PageResponseDto`
(`content`/`page`/`size`/`totalElements`/`totalPages`) зафиксирован тестом;
`ci.yml` сохраняет отчёты тестов артефактом при падении сборки.
**Файлы** — пять интеграционных тестов, `.github/workflows/ci.yml`.
**Изучить** — `jsonPath`-ассерты в MockMvc; `actions/upload-artifact` с `if: failure()`.
**Грабли** — тесты сценариев T-14/T-15 пишутся в их тикетах, здесь — только дыры
существующего поведения, не дублировать.
**Оценка** — выходные.

### T-13 ArchUnit (опционально, но сильно)

**Зачем** — раскладка по папкам соблюдение слоёв не гарантирует: ничто не мешает
контроллеру дёрнуть репозиторий напрямую. ArchUnit превращает договорённость
в падающий тест.
**Готово когда** — тесты проверяют: контроллер не зависит от репозитория; сущности
не покидают свой модуль; модули не лезут во внутренности друг друга; DTO не используются
в репозиториях.
**Оценка** — выходные. Для резюме читается лучше, чем любая раскладка папок.

### T-17 Прод-контур (заблокирован до первого реального деплоя)

Сюда же входит отложенная прод-часть T-09: отдельные прод-секреты в GitHub Actions
Secrets и запись `.env` на сервере из `deploy.yml`.

**Зачем** — стенд мёртв, но нынешние прод-конфиги при первом же деплое дадут неработающий
или дырявый стенд:

* `docker-compose.prod.yml` не передаёт `CORS_ALLOWED_ORIGINS` — прод-фронт упрётся
  в дефолт `localhost:5173`; `POSTGRES_USER` по умолчанию — суперпользователь `postgres`;
  пустые секреты не валят запуск (нет guard'ов `:?`); у postgres нет healthcheck,
  `depends_on` без `condition`;
* Dockerfile: рантайм-контейнер работает под root; `|| true` на прогреве зависимостей
  маскирует ошибки; атрибут `version:` в compose устарел;
* `show-sql: true` и открытый Swagger действуют во всех профилях, включая прод;
  actuator health отсутствует — деплою нечем проверить, что приложение живо;
* `deploy.yml`: не проверяет, что приложение поднялось; `docker compose down` роняет
  весь стек вместе с базой; триггерится на любой push в `main`, включая docs-only;
  собирает образ на VPS — прямое нарушение ARCHITECTURE §8 «не собирать на проде»;
* compose использует `postgres:15-alpine`, а решением ARCHITECTURE §2 зафиксирован 17 —
  пока база пустая, переход бесплатен.

**Готово когда** — прод-секреты в GitHub Actions Secrets; в `docker-compose.prod.yml`
guard'ы `:?`, без дефолтного `postgres`, healthcheck + `condition: service_healthy`,
CORS-переменная прокинута; Dockerfile под непривилегированным пользователем;
`show-sql` и Swagger — только в dev-профиле; подключён actuator health;
`deploy.yml` собирает образ в CI и публикует в registry (GHCR), на сервере — только
pull и перезапуск контейнера приложения без остановки базы, после подъёма —
smoke-проверка `/actuator/health`, paths-фильтр на `backend/**`; `postgres:17`.
**Изучить** — GitHub Actions Secrets и environments; healthcheck в Docker и
`depends_on.condition`; публикация образа в GHCR из CI; liveness/readiness в actuator.
**Грабли** — переезд 15 → 17 бесплатен только пока в базе нет данных — сделать
до появления реальных; образ из registry тянуть по тегу версии/digest, `latest` —
ловушка кэша.
**Опционально, перед публичным запуском** — rate limit на `/login`
(bucket4j или `limit_req` в nginx).
**Оценка** — выходные, вместе с самим деплоем.

## Что дальше, после очереди

**Шаг 2 — вертикальный срез.** Самый важный непроверенный риск проекта: фронт и бэк
ни разу не разговаривали друг с другом по-настоящему. Рубеж — «зашёл на сайт, залогинился,
увидел свой профиль и список новостей». Бэкенд для этого готов; всё упирается в реанимацию
фронта. Зона напарника, но это **критический путь** — пока его нет, каждый новый модуль
бэкенда пишется вслепую.

**Шаг 3 — новости до полного паритета.** Первый настоящий модуль: rich-text + санитайзер,
загрузка картинок через `FileStorage`, CRUD под ролями + админ-экран на фронте.
Заодно закрываются известные ограничения контракта: `POST /api/news` начнёт возвращать
201 с `id`, `previewImageDescription` появится в ответе. Модуль маленький, но проходит
насквозь через все слои — файлы, безопасность контента, роли, админка. После него
остальные 20 модулей идут по готовому шаблону.

**Шаг 4+** — по фазам MIGRATION.md. Самое сложное и рискованное (расписание
с PDF-парсером, Telegram-бот) намеренно едет позже. Refresh-токены и отзыв access-токенов
(D-03, ARCHITECTURE §4.5) — обязательная часть подготовки к первому публичному запуску.
