**✅ Использовать**
- **Модульный монолит** на backend: пакет на домен (`auth`, `user`, `staff`, `news`, `schedule`, `events`, `telegram`, `publications`, `pages`, `grades`). Внутри — `controller → service → repository`, DTO + MapStruct.

- ⛔ Не коммитить секреты (сейчас в репозитории лежит `backend/.env` — убрать и ротировать).

## 1. Telegram-бот

**Что реализовать**
- Привязка аккаунта: пользователь берёт `telegram_code` из личного кабинета → пишет боту `/register <код>` → создаётся связь `TelegramUser (chat_id ↔ user)`.
- Команды: `/start` (приветствие), `/register <код>`, `/cancel` (отписка от уведомлений).
- Исходящие уведомления: напоминания о событиях календаря + «ручное» уведомление по кнопке.
- Webhook-эндпоинт `POST /api/telegram/webhook`, защищённый секрет-токеном.
- Разовая установка webhook (`setWebhook` с `url` + `secret_token`) — админ-действие или шаг деплоя.

**✅ Использовать**
- **Режим webhook** (Telegram сам шлёт апдейты на наш HTTPS через nginx → backend). Проверять заголовок `X-Telegram-Bot-Api-Secret-Token`.
- **Вариант A (рекомендуется, «по феншую»):** тонкий клиент на `RestClient`/`WebClient` к `https://api.telegram.org/bot<token>/...` (`sendMessage`, `setWebhook`) + свой контроллер, парсящий `Update` в DTO. Минимум зависимостей, полный контроль.
- ~~**Вариант B:** библиотека `org.telegram:telegrambots-spring-boot-starter`~~ — **отклонён**: принят вариант A (решение зафиксировано в [ARCHITECTURE.md](ARCHITECTURE.md) §4.3; для трёх команд фреймворк не нужен).
- Отправку выносить в **`@Async`** с ограниченным пулом; учитывать лимиты Telegram (~30 сообщений/сек глобально, ~1/сек на чат).
- `telegram_code` генерировать **один раз** (при создании пользователя); перегенерация — только явным действием.
- `chat_id` и `user_id` хранить как **`BIGINT` / `long`**.

**⛔ Не использовать / не делать**
- ⛔ **Не long polling** в проде — конфликтует с webhook, держит вечный поток, хуже для веб-приложения.
- ⛔ Не `pyTelegramBotAPI`/telebot — это Python; бот живёт в Spring-backend, а не в микросервисе. Микросервис — только парсинг.
- ⚠️ ⛔ Не перегенерировать `telegram_code` в `save()` при каждом сохранении (в оригинале `users/models.py` так — код протухает сразу после копирования).
- ⚠️ ⛔ Не хранить `chat_id`/`user_id` в 32-битном `Integer` (в оригинале `IntegerField`) — Telegram-ID уже превышают 2³¹, будет переполнение.
- ⚠️ ⛔ Не создавать «сырой» `new Thread()` на каждое сообщение (в оригинале `tg_bot/utils.py`) — управляемый executor.
- ⛔ Не делать тяжёлую работу в потоке webhook — быстро отдать `200 OK`, обработку в async. Хендлер должен быть идемпотентным (Telegram повторяет доставку).
- ⛔ Не логировать/не хранить токен бота; только из переменных окружения.

## 2. Парсинг расписания — микросервис `schedule-service`

**Что реализовать**
- Отдельный сервис на **Python + FastAPI**. Эндпоинты (сделано в T-39/T-40, контракт — `schedule-service/README.md`):
  - `POST /parse` (multipart `file=<pdf>`) → `200 {lessons: [...]}` — плоский список занятий с `week_day` и `class_time`, а не вложенное дерево дней: разбор всё равно раскладывается по строкам таблиц `ScheduleLesson`/`ScheduleLessonDate`, и дерево пришлось бы разбирать обратно. Ошибки — единым телом `{error, detail}`: `400` (нет поля `file`), `413` (больше 5 МБ), `422` (незнакомый формат), `500` (без подробностей наружу).
  - `GET /health`.
- Backend при импорте расписания преподавателя принимает PDF от админа → **проксирует** в `schedule-service` → получает JSON → сам сохраняет `Schedule / ScheduleLesson / ScheduleLessonDate`.

**✅ Использовать**
- `pdfplumber` (переиспользуем рабочий парсер из `department/employee/schedule/parse_schedule.py` + `pydantic_models.py`).
- `pydantic` для схем запроса/ответа, `python-multipart` для загрузки файла.
- Обходить **все страницы** PDF и объединять таблицы.
- Возвращать **структурированную ошибку** (422) на неизвестный формат — не 500.
- Юнит-тесты с реальным PDF-фикстуром СТАНКИНа.
- Сервис **stateless**, доступен только по внутренней docker-сети.

**⛔ Не использовать / не делать**
- ⛔ **Не парсить PDF в Java** (PDFBox/tabula-java) — рабочий парсер написан на Python и завязан на формат; порт = повтор багов и лишние недели.
- ⛔ Не давать микросервису доступ к БД — он «чистая функция» (PDF → JSON). Персистентность — задача backend.
- ⛔ Не публиковать сервис наружу — только backend его вызывает.
- ⚠️ ⛔ Не оставлять чтение только последней страницы (в оригинале цикл `for page in pdf.pages: table = page.extract_table()` затирает всё, кроме последней).
- ⛔ Не доверять результату вслепую — валидировать против целевой схемы (формат СТАНКИНа с «перевёрнутым» текстом дня `[::-1]` и датами в скобках `[..]` хрупкий).
- 🔭 На будущее (не обязательно сейчас): предусмотреть **резервный структурированный импорт** (Excel-шаблон/форма) — PDF-формат нестабилен между семестрами.

## 3. Напоминания и планировщик (замена Celery/Redis)

**Что реализовать**
- Периодические задачи daily/weekly/monthly: выбрать события с `next_notification_at <= now`, отправить назначенным пользователям в Telegram, пересчитать следующую дату.
- Ручное уведомление по событию (кнопка в ЛК).

**✅ Использовать**
- Встроенный **`@Scheduled`** (`@EnableScheduling`) с cron-выражениями — для простого случая.
- ~~**Quartz** с JDBC job-store~~ — **не берём** (ARCHITECTURE.md §4.2/§8): состояние напоминаний уже в БД (`next_notification_at`), `@Scheduled` его просто сканирует — персистентность есть без Quartz.
- `next_notification_at` — обычный timestamp; считать от времени старта события и частоты. Флаг «отправлено» для идемпотентности.

**⛔ Не использовать / не делать**
- ⛔ **Не Celery + Redis** — это Python-стек и избыточно; вся суть замены в том, чтобы убрать 2 компонента.
- ⚠️ ⛔ Не вешать `auto_now` (или его аналог) на поле планирования (в оригинале `UserEvent.next_notification_at = auto_now=True` затирает плановую дату на «сейчас» при каждом save — планировщик ломается).
- ⚠️ ⛔ Не считать «месяц = 28 дней» фиксированными секундами — использовать нормальную работу с датами (`ChronoUnit`/cron).
- ⛔ Не рассылать синхронно в потоке планировщика при росте объёма — offload в async-пул.

## 4. Брокеры и очереди

**Прямой ответ: не нужны на текущем масштабе.**

**⛔ Не использовать сейчас**
- ⛔ RabbitMQ / Kafka / Redis-как-брокер / Celery — избыточно для десятков уведомлений и низкой нагрузки.

**✅ Когда вернуться к вопросу**

## 5. Научные публикации / Google Scholar (SerpApi)

**Что реализовать**
- Поиск публикаций по имени преподавателя через SerpApi (`engine=google_scholar`), пагинация по `serpapi_pagination.next`.
- CRUD публикаций и тегов, ручное добавление, фильтры (автор/тег/год/источник).

**✅ Использовать**
- `RestClient`/`WebClient` к SerpApi; **URL-энкодить** параметр `q`; API-ключ из конфигурации.
- Кэшировать результаты (в БД или Redis-кэш) — экономия лимита **100 запросов/мес** на бесплатном тарифе.
- Файлы публикаций (PDF) — в **файловое хранилище**, в БД только ссылка.
- Маппинг ответа в DTO.

**⛔ Не использовать / не делать**
- ⚠️ ⛔ Не собирать URL конкатенацией с неэкранированным вводом (в оригинале `q={name}` без encode — ломается на пробелах, риск инъекции query-параметров).
- ⚠️ ⛔ Не хранить PDF как **base64 в `TEXT`-поле** (в оригинале `ScientificPublication.file` — раздувание БД, медленно).
- ⛔ Не дёргать SerpApi на каждый заход на страницу — кэш; тариф платный/лимитированный.
- ⛔ Не отдавать API-ключ на фронтенд.

## 6. Файлы и медиа (замена django-imagekit)

**Что реализовать**
- Загрузка аватаров, превью новостей/достижений/конференций, PDF публикаций/расписаний экзаменов; ресайз изображений.

**✅ Использовать**

- ⛔ Не доверять имени файла от клиента — санитизировать, генерировать ключ.
- ⛔ Не отдавать пользовательские файлы без лимитов размера/типа.

## 8. Аутентификация и безопасность

**✅ Использовать**
- JWT (уже есть). Рассмотреть **access + refresh** токены. BCrypt (уже).
- Роли через Spring Security authorities + `@PreAuthorize` на всех непубличных эндпоинтах.
- CORS — **только известные домены** фронтенда.
- Секреты — переменные окружения; `.env` в `.gitignore`.

**⛔ Не использовать / не делать**
- ⚠️ ⛔ Не коммитить `.env`/секреты (проверено 2026-07-27: в git-истории их нет, значения в рабочей копии ротированы; прод-значения — только в GitHub Actions Secrets).
- ⚠️ ⛔ Не оставлять `CORS allow all origins` / `*` в проде (сейчас так в `SecurityConfig`).
- ⛔ Не отдавать stacktrace/Swagger/actuator наружу в проде без ограничений.
- ⛔ Не переносить token-auth (`dj-rest-auth`) — JWT уже правильнее.

## 9. Frontend и админ-панель

**Что реализовать**
- Публичная зона (все разделы) + **админ-панель** (CRUD всех сущностей — заменяет Django Admin, которого «из коробки» больше нет).

**✅ Использовать**

## 11. Конвенции данных

**✅ Использовать**
- Идентификаторы — `BIGINT`/`Long`; временные метки — `timestamptz` (`OffsetDateTime`).
- Имена таблиц сохранять как в Django (`users_user`, `news_post`, `employee_teacher`, …) — упростит перенос данных.
- Enum'ы (звания/степени преподавателя, тип поста, частота уведомлений, статус события) — как строковые enum в БД + Java `enum`.
- Отчество (`patronymic`) — обязательно есть в модели (в новом репо сейчас потеряно, а для ФИО на русском критично).

**⛔ Не использовать / не делать**
- ⛔ Не использовать 32-битные `Integer` для внешних ID (Telegram и т.п.).
- ⛔ Не хранить перечисления «магическими» строками в разных регистрах (в оригинале `post_type` то `NEWS`, то `news`).
