# Деплой

Порядок выкатки на боевой стенд и того, что нужно сделать до неё. Код деплоя закрыт
(T-17c, T-84, T-85), незакрытым остаётся всё, что требует живого сервера, — T-17d.

> Стенд на VPS мёртв с 2026-07-21, реальных пользователей нет. `deploy.yml` целиком
> не выполнялся ни разу: каждый его шаг проверен локально по отдельности, но в бою
> workflow сработает впервые. Ошибки в нём всплывут на первой же выкатке.

---

## 1. Что мешает выкатке прямо сейчас

Три вещи, каждая из которых делает поднятый стенд бесполезным. Решать их нужно
**до** деплоя, а не после.

### 1.1 В прод-базе не будет ни одного пользователя

Единственный сид учётных записей — `DevDataSeeder`, и он помечен `@Profile("dev")`.
Миграции Liquibase вставляют только редактируемые страницы (`008-seed-editable-pages`).
После первого деплоя портал поднимется, но войти в него будет некому: ни администратора,
ни модератора. Варианты — в T-87.

### 1.2 Без TLS не работает вход

`REFRESH_COOKIE_SECURE` по умолчанию `true`, то есть refresh-токен уезжает в cookie
с флагом `Secure`. По HTTP браузер такую cookie не сохранит: access живёт 15 минут,
обновить его будет нечем, и пользователя выбросит. TLS — не завершающий штрих,
а условие работоспособности.

Временно снизить `REFRESH_COOKIE_SECURE` до `false` допустимо только на проверочной
выкатке без реальных людей: refresh-токен пойдёт по открытому каналу.

### 1.3 Скрипты бэкапа на сервер не попадают

`deploy.yml` копирует только `docker-compose.prod.yml`. `backend/ops/backup.sh`
и `restore-check.sh` придётся класть на сервер вручную.

## 2. Подготовка сервера — один раз

1. VPS: Ubuntu 24.04, минимум 2 vCPU / 4 ГБ / 40 ГБ. Ориентир по памяти — лимиты
   в `docker-compose.prod.yml`: backend 1536 МБ, postgres 512 МБ, schedule-service 512 МБ,
   nginx 128 МБ, плюс сама система.
2. Отдельный пользователь для деплоя, вход по ssh-ключу. В `sshd_config` отключить
   парольную аутентификацию и вход под root.
3. Файрвол: 22, 80, 443. Порт 8080 наружу не открывать — приложение доступно
   только через nginx, и это не случайность (см. §4.2).
4. Docker Engine и compose plugin.
5. `mkdir -p /opt/uits/backend`, владелец — пользователь деплоя. Именно этот путь
   ждёт `deploy.yml`.
6. Домен: A-запись на адрес сервера.
7. **Проверить `docker pull ghcr.io/...` с самого сервера.** Docker Hub ограничивает
   загрузку с российских адресов, и с GHCR стоит убедиться заранее (ARCHITECTURE §7.2,
   пункт 5). Если образ не тянется — деплой не поедет вовсе, и узнать об этом
   лучше до выкатки.

## 3. Секреты

Заводятся в environment `production`, а не в секретах репозитория: секрет репозитория
читает любой job любого workflow на любой ветке (T-43).

| Секрет | Чем заполняется |
|---|---|
| `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_PORT` | доступ к серверу |
| `POSTGRES_DB`, `POSTGRES_USER` | имя базы и учётка приложения, не суперпользователь кластера |
| `POSTGRES_PASSWORD` | `openssl rand -base64 32` |
| `JWT_SECRET_KEY` | `openssl rand -base64 32` |
| `CORS_ALLOWED_ORIGINS` | `https://<домен>`, со схемой и без слеша на конце |
| `SERPER_API_KEY` | ключ Serper; без него поиск публикаций отвечает 503, остальной портал работает |

Генерация через `openssl rand -base64 32` выбрана не только за стойкость: алфавит
base64 не содержит одинарной кавычки, а она уронит шаг записи `.env`. Так задумано —
значение с кавычкой иначе молча превратилось бы в пустую строку (§4.1).

---

## 4. Как устроен деплой

Запускается автоматически на push в `main` с изменениями в `backend/**`,
`frontend/**` или `.github/workflows/**`. Ручного шага нет: релиз — это merge PR
из `dev` в `main`.

Порядок работы `deploy.yml`:

1. Вызов `ci.yml` — тесты бэкенда и микросервиса, публикация трёх образов в GHCR
   тегом `github.sha`.
2. Вызов `frontend.yml` — линт, тесты и сборка фронтенда. Без этого шага на `main`
   фронтовые проверки не запускались бы вовсе.
3. Копирование `docker-compose.prod.yml` в `/opt/uits/`.
4. Запись `.env` на сервер из секретов.
5. `docker login` → `pull` всех образов → `docker logout` → `up -d --wait`.

### 4.1 Почему значения `.env` пишутся в кавычках

Содержимое `.env` docker compose интерполирует. Пароль вида `p$ss…`, записанный
без кавычек, превращается в `p…`: подстрока `$ss` читается как пустая переменная.
Решётка после пробела обрезает хвост значения как комментарий. Оба случая тихие —
приложение просто получает не тот пароль. Кавычки снимают их, а секрет
с одинарной кавычкой внутри валит шаг явной ошибкой.

Проверять такое через `docker compose config` бесполезно: он показывает `$` удвоенным
и выглядит сломанным там, где всё правильно. Достоверный способ — запустить контейнер
и сравнить байты.

### 4.2 Почему деплой ждёт готовности, а не запуска

`docker compose up -d` сообщает, что контейнер запущен, а не что приложение готово.
Деплой с таким шагом считался бы успешным и тогда, когда бэкенд падает на миграциях.
Поэтому у бэкенда есть healthcheck по `/actuator/health/readiness`, а запуск идёт
через `up -d --wait`: шаг держится до зелёных проб всех сервисов и отдаёт ненулевой
код, если не дождался. При падении печатаются `ps` и последние 200 строк логов.

## 5. Проверка после выкатки

`/actuator` наружу намеренно не проксируется, поэтому состояние смотрится по ssh:

```
ssh <user>@<host> 'cd /opt/uits/backend && docker compose -f docker-compose.prod.yml ps'
```

Все четыре сервиса должны быть `healthy`. Дальше — открыть домен в браузере
и проверить вход: именно он ломается первым, если TLS ещё нет (§1.2).

---

## 6. Откат

Версия на стенде задаётся строкой `IMAGE_TAG` в `/opt/uits/backend/.env`,
и откат не требует прогона workflow:

```
ssh <user>@<host>
cd /opt/uits/backend
sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG='<предыдущий sha>'/" .env
docker compose -f docker-compose.prod.yml up -d
```

Кавычки вокруг значения обязательны по той же причине, что и при записи `.env`
из workflow (§4.1).

Теги образов — sha коммитов, а не `latest`: подвижная метка позволила бы `docker pull`
отдать закэшированный старый слой, и расхождение было бы видно только по поведению
приложения.

## 7. Сразу после первого успешного деплоя

1. Скопировать `backend/ops/backup.sh` и `restore-check.sh` на сервер.
2. Поставить ночной бэкап в cron:

   ```
   15 3 * * * cd /opt/uits/backend && BACKUP_ROOT=/var/backups/uits ops/backup.sh >> /var/log/uits-backup.log 2>&1
   ```

3. Настроить увоз копий за пределы машины. Бэкап на том же диске, что и база,
   спасает от ошибки оператора, но не от потери сервера, — и это названо самым
   большим инфраструктурным риском проекта (ARCHITECTURE §7.4).
4. Проверить восстановление: `restore-check.sh` разворачивает бэкап в одноразовые
   тома и контейнер, рабочих данных не касаясь. Бэкап, который ни разу
   не восстанавливали, бэкапом не является.
