## 1. Чего деплой не делает сам

Три вещи, которые не приезжают вместе с выкаткой, а без них поднятый стенд бесполезен.
На стенде первая сделана вручную, вторая закрыта в T-94, третья выполнена по §7. На новом
сервере все три нужны заново и **до** первого входа пользователей, а не после.

### 1.1 В прод-базе не будет ни одного пользователя

Единственный сид учётных записей — `DevDataSeeder`, и он помечен `@Profile("dev")`.
Миграции Liquibase вставляют только редактируемые страницы (`008-seed-editable-pages`).
После первого деплоя портал поднимется, но войти в него будет некому: ни администратора,
ни модератора. Варианты — в T-87. На стенде администратор заведён способом ниже 2026-10-16.

Способ для стенда, без правок кода и без пароля в git. В ssh-сессии на сервере, из `/opt/uits/backend`:

```
set -a; . ./.env; set +a
read -rs -p "Пароль админа: " PW; echo
HASH=$(printf '%s\n' "$PW" | docker run -i --rm httpd:2.4-alpine htpasswd -niBC 10 x | cut -d: -f2)
unset PW
docker compose -f docker-compose.prod.yml exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -v h="$HASH" <<'SQL'
INSERT INTO users_user (username, password, email, is_superuser, is_staff, is_moderator, is_active, date_joined)
VALUES ('admin', :'h', 'admin@example.com', true, true, true, true, now());
SQL
unset HASH
```

Роль администратора даёт `is_superuser`. Пароль сразу сменить штатной ручкой
`POST /api/users/change-password`: смена закрывает все сессии, после неё нужен новый вход.

### 1.2 Без TLS не работает вход

`REFRESH_COOKIE_SECURE` по умолчанию `true`, то есть refresh-токен уезжает в cookie
с флагом `Secure`. По HTTP браузер такую cookie не сохранит: access живёт 15 минут,
обновить его будет нечем, и пользователя выбросит. TLS — не завершающий штрих,
а условие работоспособности.

Сертификат выпускается по §8; при работающем TLS `REFRESH_COOKIE_SECURE` остаётся `true`.
На стенде TLS работает с 2026-10-16 (T-94), вход проверен на боевом сертификате.

Временно снизить `REFRESH_COOKIE_SECURE` до `false` допустимо только на проверочной
выкатке без реальных людей и без сертификата: refresh-токен пойдёт по открытому каналу.
Делается это строкой `REFRESH_COOKIE_SECURE='false'` в `/opt/uits/backend/.env` и `up -d`;
следующий деплой перепишет `.env` из секретов, и флаг вернётся в `true` сам.

### 1.3 Скрипты бэкапа на сервер не попадают

`deploy.yml` копирует только `docker-compose.prod.yml`. Скрипты `backend/ops/backup.sh`,
`restore-check.sh` и `offsite.sh` кладутся на сервер вручную (§7, §9.1), и после правки
скрипта в репозитории копия на сервере сама не обновляется: её нужно скопировать заново.

## 2. Подготовка сервера — один раз

1. VPS: Ubuntu 24.04, минимум 2 vCPU / 4 ГБ / 40 ГБ. Ориентир по памяти — лимиты
   в `docker-compose.prod.yml`: backend 1536 МБ, postgres 512 МБ, schedule-service 512 МБ,
   nginx 128 МБ, плюс сама система.
2. Отдельный пользователь для деплоя, вход по ssh-ключу. В `sshd_config` отключить
   парольную аутентификацию и вход под root. На стенде парольный вход оставлен включённым
   осознанно, вход под root — только по ключу (п. 9).
3. Файрвол: 22, 80, 443. Порт 8080 наружу не открывать — приложение доступно
   только через nginx: в обход него не действуют ни лимит размера тела, ни перезапись
   `X-Forwarded-For`, на которой держится лимит попыток входа по IP.
4. Docker Engine и compose plugin; пользователь деплоя — в группе `docker`:
   `deploy.yml` вызывает `docker` без `sudo`.
5. `mkdir -p /opt/uits/backend`, владелец — пользователь деплоя. Именно этот путь
   ждёт `deploy.yml`.
6. Имя для сертификата: A-запись домена на адрес сервера либо бесплатное имя
   `<ip через дефис>.sslip.io` (§8), без покупки домена.
7. **Проверить `docker pull` с самого сервера — и из GHCR, и с Docker Hub.** Три образа
   проекта лежат в GHCR, но `postgres:17-alpine` из прод-compose и `alpine:3.20` из скриптов
   бэкапа тянутся с Docker Hub, а он ограничивает загрузку с российских адресов
   (ARCHITECTURE §7.2, пункт 5). Если Docker Hub не отвечает — настроить registry-mirror
   в `/etc/docker/daemon.json` или перенести оба образа в GHCR. Узнать об этом лучше
   до выкатки: без базы стек не поднимется. С адреса нынешнего стенда загрузка проходит:
   с Docker Hub приехали `postgres:17-alpine`, `alpine:3.20`, `nginx:alpine`, `certbot` и `rclone`.
8. Ротация логов Docker в том же `/etc/docker/daemon.json`:
   `"log-driver": "json-file", "log-opts": {"max-size": "10m", "max-file": "3"}`, затем
   `systemctl restart docker`. Без неё логи контейнеров растут, пока не займут диск;
   настройка действует на контейнеры, созданные после перезапуска, — то есть ставится
   до первого деплоя. Задана ли ротация на нынешнем стенде, не проверялось (T-97, п. 2).
9. Защита от подбора паролей и устаревших пакетов (проверено на стенде 2026-10-17; на новом
   VPS уже в первые сутки приходит десяток неудачных парольных входов от ботов):
   * `apt install fail2ban` и файл `/etc/fail2ban/jail.d/sshd-local.conf` с секцией `[sshd]`:
     `enabled = true`, `maxretry = 5`, `findtime = 10m`, `bantime = 1h`. Проверка:
     `fail2ban-client status sshd` под root.
   * `/etc/ssh/sshd_config.d/00-hardening.conf` со строкой `PermitRootLogin prohibit-password`,
     затем `sshd -t` и `systemctl reload ssh`. Префикс `00-` важен: в sshd первое значение
     побеждает, а у cloud-init-образов в `50-cloud-init.conf` стоит `PasswordAuthentication yes`.
     Новые сессии (root и пользователь деплоя) проверять до закрытия рабочей.
   * `unattended-upgrades` с файлом `/etc/apt/apt.conf.d/20auto-upgrades`
     (`Update-Package-Lists "1"`, `Unattended-Upgrade "1"`). Только обновления безопасности,
     без автоперезагрузки: появление `/var/run/reboot-required` проверяется вручную.

## 3. Секреты

Заводятся в environment `production`, а не в секретах репозитория: секрет репозитория
читает любой job любого workflow на любой ветке (T-43).

| Секрет | Чем заполняется |
|---|---|
| `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_PORT` | доступ к серверу |
| `POSTGRES_DB`, `POSTGRES_USER` | имя базы и учётка приложения, не суперпользователь кластера |
| `POSTGRES_PASSWORD` | `openssl rand -base64 32` |
| `JWT_SECRET_KEY` | `openssl rand -base64 32` |
| `CORS_ALLOWED_ORIGINS` | `https://<домен>`, со схемой и без слеша на конце |
| `SERPER_API_KEY` | ключ Serper; без него поиск публикаций отвечает 503, остальной портал работает |

Генерация через `openssl rand -base64 32` выбрана не только за стойкость: алфавит
base64 не содержит одинарной кавычки, а она уронит шаг записи `.env`. Так задумано —
значение с кавычкой иначе молча превратилось бы в пустую строку (§4.1).

### 3.1 Ротация секретов

Деплой пишет `.env` из секретов, поэтому новое значение вступает в силу только после деплоя.
Без изменений в коде деплой перезапускается кнопкой **Re-run all jobs** на странице последнего
запуска `deploy.yml` (в окне подтверждения нажать зелёную **Re-run jobs**) либо новым мержем в `main`.

* **`JWT_SECRET_KEY`.** Заменить секрет, перезапустить деплой. Все выданные токены перестают
  приниматься, нужен один новый вход.
* **`POSTGRES_PASSWORD`.** Образ postgres читает переменную только при создании пустой базы,
  поэтому заменой секрета пароль в базе не меняется. Compose при этом пересоздаёт контейнер
  postgres (данные в томе целы), а бэкенд с новым паролем в `.env` в базу не входит. Порядок,
  в котором пароль нигде не копируется руками: заменить секрет, перезапустить деплой, затем на сервере
  выставить в базе значение из нового `.env` и перезапустить бэкенд (пока идёт этот порядок, портал
  отвечает `502`, на стенде это минуты):

  ```
  cd /opt/uits/backend
  set -a; . ./.env; set +a
  docker compose -f docker-compose.prod.yml exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -v u="$POSTGRES_USER" -v p="$POSTGRES_PASSWORD" <<'SQL'
  ALTER USER :"u" PASSWORD :'p';
  SQL
  docker compose -f docker-compose.prod.yml restart backend
  ```

  Обратный порядок (сначала `ALTER USER` с вводом пароля в терминале, потом секрет) без простоя
  возможен, но требует, чтобы введённое и сохранённое в секрет значения совпали до символа. На стенде
  2026-10-17 они разошлись (в буфере обмена оказался другой текст), и после деплоя портал лёг.
  Проверка совпадения без вывода пароля: вход по сети (`psql -h postgres`) со значением из `.env`
  должен проходить, а со старым — отклоняться.

## 4. Как устроен деплой

Запускается автоматически на push в `main` с изменениями в `backend/**`,
`schedule-service/**`, `frontend/**` или `.github/workflows/**`. Ручного шага нет: релиз — это merge PR
из `dev` в `main`. Файлы `.md` внутри этих каталогов и каталог `docs/` деплой не запускают.

Порядок работы `deploy.yml`:

1. Вызов `ci.yml` — тесты бэкенда и микросервиса, публикация трёх образов в GHCR
   тегом `github.sha`.
2. Вызов `frontend.yml` — линт, тесты и сборка фронтенда. Без этого шага на `main`
   фронтовые проверки не запускались бы вовсе.
3. Копирование `docker-compose.prod.yml` в `/opt/uits/backend/`: scp сохраняет путь
   `backend/` из репозитория.
4. Запись `.env` на сервер из секретов.
5. `docker login` → `pull` всех образов → `docker logout` → `up -d --wait --wait-timeout 240`
   → `docker image prune -f`.

### 4.1 Почему значения `.env` пишутся в кавычках

Содержимое `.env` docker compose интерполирует. Пароль вида `p$ss…`, записанный
без кавычек, превращается в `p…`: подстрока `$ss` читается как пустая переменная.
Решётка после пробела обрезает хвост значения как комментарий. Оба случая тихие —
приложение просто получает не тот пароль. Кавычки снимают их, а секрет
с одинарной кавычкой внутри валит шаг явной ошибкой.

Проверять такое через `docker compose config` бесполезно: он показывает `$` удвоенным
и выглядит сломанным там, где всё правильно. Достоверный способ — запустить контейнер
и сравнить байты.

### 4.2 Почему деплой ждёт готовности, а не запуска

`docker compose up -d` сообщает, что контейнер запущен, а не что приложение готово.
Деплой с таким шагом считался бы успешным и тогда, когда бэкенд падает на миграциях.
Поэтому у бэкенда есть healthcheck по `/actuator/health/readiness`, а запуск идёт
через `up -d --wait`: шаг держится до зелёных проб всех сервисов и отдаёт ненулевой
код, если не дождался. При падении печатаются `ps` и последние 200 строк логов бэкенда.

## 5. Проверка после выкатки

`/actuator` наружу намеренно не проксируется, поэтому состояние смотрится по ssh:

```
ssh <user>@<host> 'cd /opt/uits/backend && docker compose -f docker-compose.prod.yml ps'
```

Все четыре сервиса должны быть `healthy`. Снаружи проверяются редирект и сертификат:

```
curl -sI http://<имя>/ | head -n 3        # 301 и Location: https://<имя>/
curl -s -o /dev/null -w "%{http_code} %{ssl_verify_result}\n" https://<имя>/   # 200 0
```

Дальше — открыть адрес в браузере и проверить вход, в том числе после обновления страницы:
именно вход ломается первым, если TLS не работает (§1.2).

Один раз после первого деплоя — проверить подсеть docker-сети:

```
docker network inspect uits_network --format '{{(index .IPAM.Config 0).Subnet}}'
```

Приложение верит `X-Forwarded-For` только от адресов `172.16.0.0/12`
(`server.tomcat.remoteip.internal-proxies`), куда Docker кладёт сети по умолчанию.
Если подсеть вне этого диапазона — например, `192.168.x`, когда пул `172.x` занят, —
лимит попыток входа по IP молча превращается в одно ведро на всех, и список доверенных
прокси нужно расширить.

## 6. Откат

Версия на стенде задаётся строкой `IMAGE_TAG` в `/opt/uits/backend/.env`,
и откат не требует прогона workflow:

```
ssh <user>@<host>
cd /opt/uits/backend
sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG='<предыдущий sha>'/" .env
docker compose -f docker-compose.prod.yml up -d
```

Кавычки вокруг значения обязательны по той же причине, что и при записи `.env`
из workflow (§4.1).

Образы прежнего релиза остаются на сервере локально (`docker image prune -f` убирает только
образы без тега), поэтому доступ к GHCR при откате не нужен. Откат проверен на стенде 2026-10-16.
Откат на релиз до T-94 (с TLS) оставляет https недоступным: образ nginx без блока 8443 не отвечает
на порту 443, который compose уже пробрасывает. Через эту границу вместе с образом откатывается
и `docker-compose.prod.yml` на сервере.

Теги образов — sha коммитов, а не `latest`: подвижная метка не говорит, какая версия
запущена, `up` без `pull` молча берёт образ, лежащий локально, а откатываться при ней
не на что — предыдущая сборка под тем же именем уже перезаписана.

## 7. Сразу после первого успешного деплоя

1. Скопировать `backend/ops/backup.sh` и `restore-check.sh` в `/opt/uits/backend/ops/`
   и выдать право на запуск (`chmod +x`): в git у скриптов бита исполнения нет.
   `offsite.sh` кладётся туда же при настройке увоза (§9.1).
2. Создать каталог для копий и поставить ночной бэкап в cron пользователя деплоя
   (`crontab -e`). Каталог `/opt/uits/backups` создаётся без `sudo`, и на стенде
   использован именно он; `/var/backups/uits` с файлом `/var/log/uits-backup.log`
   требует `sudo` и `chown`, итог тот же:

   ```
   15 3 * * * cd /opt/uits/backend && BACKUP_ROOT=/opt/uits/backups ops/backup.sh >> /opt/uits/backups/backup.log 2>&1
   ```

   Локальные копии хранятся 14 дней (`KEEP_DAYS`). Если снятие падает, скрипт удаляет
   недоснятый каталог и выходит с ошибкой, а кроме журнала об этом никто не узнает.
3. Настроить увоз копий за пределы машины (T-95). Бэкап на том же диске, что и база,
   спасает от ошибки оператора, но не от потери сервера, — и это названо самым
   большим инфраструктурным риском проекта (T-74 в `docs/BACKLOG.md`). Порядок — в §9.
4. Проверить восстановление: `restore-check.sh` разворачивает бэкап в одноразовые
   тома и контейнер, рабочих данных не касаясь. Бэкап, который ни разу
   не восстанавливали, бэкапом не является.

На стенде все четыре пункта выполнены (2026-10-16…17), расписание — в начале документа.

## 8. TLS: выпуск и продление сертификата

Решение — nginx и certbot (ARCHITECTURE §7, T-94). Имя на стенде — `168-113-168-29.sslip.io`:
сервис возвращает адрес, зашитый в имени, поэтому домен покупать не нужно. Для настоящего домена
достаточно A-записи, замены имени в командах ниже и в секрете `CORS_ALLOWED_ORIGINS`
(`https://<имя>`, без слеша на конце).

**Порядок обязателен: сертификат должен лежать в томе `uits_letsencrypt` до выкатки образа
с блоком 443.** Без файла сертификата nginx не стартует, и стенд ляжет.

### 8.1 Первый выпуск

Один раз, по ssh из `/opt/uits/backend`. Стенд на это время недоступен: порт 80 нужен
временному серверу для файла-проверки.

```
docker compose -f docker-compose.prod.yml stop nginx
docker run -d --rm --name acme-tmp -p 80:80 -v uits_certbot_webroot:/usr/share/nginx/html nginx:alpine
docker run --rm -v uits_letsencrypt:/etc/letsencrypt -v uits_certbot_webroot:/var/www/certbot \
  certbot/certbot:v5.8.0 certonly --webroot -w /var/www/certbot --cert-name uits \
  -d <имя> --email <почта> --agree-tos --no-eff-email --staging \
  --deploy-hook "chmod -R a+rX /etc/letsencrypt/archive /etc/letsencrypt/live"
```

После тестового выпуска та же команда без `--staging` и с `--force-renewal` заменяет
сертификат боевым. Затем `docker stop acme-tmp` и `docker compose -f docker-compose.prod.yml up -d nginx`.
Тома, созданные `docker run`, compose подхватывает без ошибок.

* `--staging` сначала: у боевого Let's Encrypt жёсткие лимиты на неудачные попытки.
* `--cert-name uits`: путь `live/uits/` в `nginx.conf` не зависит от домена.
* `--deploy-hook`: certbot создаёт ключ с правами только для root, а nginx в контейнере
  работает не под root и без смены прав ключ не прочитает.
* Если certbot после успешной проверки не возвращает управление, наличие сертификата
  смотрится командой `docker run --rm -v uits_letsencrypt:/etc/letsencrypt certbot/certbot:v5.8.0 certificates`;
  у боевого сертификата нет пометки `TEST_CERT`.

### 8.2 Продление

Сервис `certbot` в compose стоит под профилем `tools`, поэтому `up -d --wait` его не запускает.
Продление — недельный cron пользователя деплоя; certbot меняет сертификат, только когда до конца
срока остаётся меньше 30 дней, после чего nginx перечитывает файлы:

```
0 4 * * 1 cd /opt/uits/backend && { docker compose -f docker-compose.prod.yml --profile tools run --rm certbot renew --quiet && docker exec uits_nginx nginx -s reload; } >> /opt/uits/backups/renew.log 2>&1
```

Проверка без траты лимитов: `docker compose -f docker-compose.prod.yml --profile tools run --rm certbot renew --dry-run`.
Продление работает по тому же webroot: путь `/.well-known/acme-challenge/` отдаётся по http,
редирект на него не распространяется.

## 9. Увоз бэкапов за пределы машины

Решение T-95: ночная копия уходит в приватный бакет S3-совместимого хранилища (на стенде —
Timeweb Cloud, `https://s3.twcstorage.ru`) через `rclone`. Он запускается одноразовым контейнером
`rclone/rclone:1.75.2`, ставить пакет на сервер не нужно.

### 9.1 Один раз

1. В панели хранилища создать **приватный** бакет и пару ключей доступа. Secret Key показывается
   только при создании.
2. На сервере создать конфиг. Ключи вводятся в терминале и не попадают ни в историю команд,
   ни в репозиторий, ни в секреты workflow:

   ```
   mkdir -p ~/.config/rclone && chmod 700 ~/.config/rclone
   read -rp "Access Key: " AK
   read -rsp "Secret Key: " SK; echo
   umask 077
   cat > ~/.config/rclone/rclone.conf <<EOF
   [timeweb]
   type = s3
   provider = Other
   access_key_id = $AK
   secret_access_key = $SK
   endpoint = https://s3.twcstorage.ru
   region = ru-1
   acl = private
   EOF
   unset AK SK
   ```

3. Проверить доступ: `docker run --rm -v ~/.config/rclone:/config/rclone rclone/rclone:1.75.2 lsd timeweb:`
   должен показать бакет.
4. Добавить зашифрованный слой поверх бакета. Пароли генерируются на сервере и выводятся только
   в терминал; **оба пароля сразу сохранить в менеджер паролей**: без них копии в облаке
   расшифровать невозможно, в том числе при потере сервера.

   ```
   P1=$(openssl rand -base64 32 | tr -d '\n')
   P2=$(openssl rand -base64 32 | tr -d '\n')
   O1=$(docker run --rm rclone/rclone:1.75.2 obscure "$P1")
   O2=$(docker run --rm rclone/rclone:1.75.2 obscure "$P2")
   umask 077
   cat >> ~/.config/rclone/rclone.conf <<EOF

   [timeweb-crypt]
   type = crypt
   remote = timeweb:<бакет>/stand-enc
   password = $O1
   password2 = $O2
   filename_encryption = standard
   directory_name_encryption = true
   EOF
   echo "Пароль 1: $P1"
   echo "Пароль 2: $P2"
   unset P1 P2 O1 O2
   ```

   Проверка: файл, записанный через `timeweb-crypt:`, в бакете лежит под нечитаемым именем,
   а через `timeweb-crypt:` читается обратно.
5. Скопировать `backend/ops/offsite.sh` в `/opt/uits/backend/ops/` и выдать право на запуск
   (`chmod +x`), как остальные скрипты (§7).
6. Поставить задание в cron пользователя деплоя через 30 минут после ночного бэкапа:

   ```
   45 3 * * * cd /opt/uits/backend && BACKUP_ROOT=/opt/uits/backups ops/offsite.sh >> /opt/uits/backups/offsite.log 2>&1
   ```

### 9.2 Как устроен скрипт

* Берётся самый свежий каталог бэкапа не старше суток. Если ночной бэкап не отработал, скрипт
  падает, а не выгружает вчерашнее и не рапортует об успехе.
* В каталоге должны быть непустые `db.dump`, `media.tar.gz` и `meta.txt`.
* Выгрузка идёт через зашифрованный слой `timeweb-crypt:` (`REMOTE`): содержимое файлов и имена
  файлов и каталогов шифруются на сервере, до облака доходит только шифртекст.
* `rclone copy`, затем `rclone cryptcheck`: после загрузки зашифрованные файлы в бакете
  сверяются с локальными по хешам.
* Копии старше 30 суток (`REMOTE_KEEP_DAYS`) удаляются в бакете только после успешной загрузки
  и сверки. Это не даёт чистке опустошить бакет, если бэкапы встанут надолго. По той же причине
  использован `copy`, а не `sync`: `sync` удалил бы в облаке всё, чего нет локально.
* Каталог бэкапов смонтирован в контейнер только на чтение.

### 9.3 Проверка

Выгрузка не считается настроенной, пока копия из бакета ни разу не восстанавливалась: скачать
каталог бэкапа с расшифровкой (`rclone copy timeweb-crypt:<дата> <каталог>`) и прогнать
`ops/restore-check.sh <каталог>`. На стенде это проверено 2026-10-17 на зашифрованной копии.

### 9.4 Пароли шифрования

Дамп содержит хеши паролей и персональные данные, поэтому копии шифруются. Расшифровать их
можно только двумя паролями из конфига `timeweb-crypt`, которые хранятся вне сервера, в менеджере
паролей. При потере сервера конфиг собирается заново теми же паролями (`rclone obscure` и секция
`[timeweb-crypt]` из §9.1), указывая на тот же `<бакет>/stand-enc`. Потеря паролей означает потерю
всех облачных копий.
