# Контракт API для фронтенда

> Актуально на 2026-08-30. Источник правды по эндпоинтам и схемам —
> **Swagger UI** запущенного бэкенда: `http://localhost:8080/swagger-ui/index.html`
> (сырая спека — `/v3/api-docs`). Этот документ описывает то, чего в Swagger нет:
> соглашения, формат ошибок и планируемые изменения контракта.

## Базовое

* Base URL локально — `http://localhost:8080`. Все пути начинаются с `/api`.
* Все тела запросов и ответов — JSON, имена полей — **camelCase**.
* Поле тела запроса, которого нет в схеме, молча игнорируется: форма может
  отправлять обратно объект из ответа целиком (вместе с `id` и `createdAt`),
  это не ошибка.
* Пустая или пробельная строка в строковом поле тела равносильна отсутствию
  значения: сервер превращает её в `null` до валидации, поэтому конвертировать
  пустые поля формы в `null` на клиенте не нужно. Исключение одно — `text`
  раздела, где пустая строка означает «очистить раздел»
  (см. «Редактируемые страницы»).
* Правило выше действует только на **строковые** поля. Словарные коды
  (`degree`, `rank`) и массивы (`subjectIds`) пустую строку не принимают:
  ответ будет `400` без словаря `errors` — тело не разобралось, и до проверки
  полей дело не дошло. Такие поля либо не отправлять вовсе, либо слать `null`.
* **Строковое поле — плоский текст, если в его разделе не сказано иное.**
  Сервер чистит от небезопасной разметки только поля, помеченные как
  rich-text: `content` новости, конференции и достижения, `education`
  и `qualification` карточки ППС. Остальные строки уходят наружу ровно
  такими, какими их прислал редактор, и выводить их следует текстовым узлом,
  а не через `dangerouslySetInnerHTML`. Отдельный случай — `text`
  редактируемого раздела: это Markdown, см. «Редактируемые страницы».
* Тестовые логины и пароли — в [backend/README.md](../backend/README.md),
  раздел «Тестовые данные».

## Аутентификация

Работают два токена с разным сроком жизни: короткий access в теле ответа
и длинный refresh в httpOnly-cookie.

1. `POST /api/users/auth/login` с телом `{"username": "...", "password": "..."}`.
2. В ответе — `{"accessToken": "<JWT>"}` и заголовок `Set-Cookie` с refresh-токеном.
   Access живёт **15 минут**, refresh — **14 дней**.
3. Access передаётся в каждом запросе к закрытым эндпоинтам заголовком
   `Authorization: Bearer <JWT>` и хранится в памяти вкладки. В `localStorage`
   он переживает закрытие вкладки и доступен любому скрипту страницы —
   ради этого refresh и вынесен в cookie, которую JS не видит.
4. Refresh-токен хранит и отправляет сам браузер. Cookie помечена `HttpOnly`,
   `SameSite=Lax`, `Path=/api/users/auth` — она уезжает только на ручки блока
   `auth` (`login`, `refresh`, `logout`), в обычных запросах её нет. На `login`
   сервер присланную cookie не читает и всегда выдаёт новую сессию.
5. `POST /api/users/auth/refresh` без тела: в ответе новый `accessToken`
   и новая cookie взамен прежней; прежний refresh-токен гасится.
6. `POST /api/users/auth/logout` без тела закрывает сессию на сервере
   и стирает cookie, ответ — `204`.

Пароли из старого портала работают как есть: учётные записи, перенесённые
скриптом, входят прежними паролями. Django-хеш (`pbkdf2_sha256$…`) проверяется
наравне с BCrypt и при первом успешном входе молча заменяется на BCrypt —
контракт входа при этом не меняется ни на поле, и сессия не рвётся: поменялась
форма хранения пароля, а не сам пароль.

Заголовок `Authorization` к ручкам блока `auth` прикладывать **нельзя**.
JWT-фильтр разбирает его на каждом запросе, включая `permitAll`, и просроченный
токен даёт `401` ещё до контроллера — при живой cookie и совершенно правильном
запросе. Обменивают токен ровно тогда, когда он просрочен, поэтому `login`,
`refresh` и `logout` уходят без заголовка (проверено на живом бэкенде
2026-08-28). Побочная выгода: без `Authorization` кросс-доменный `refresh`
становится «простым» запросом и обходится без preflight.

Запросы к `refresh` и `logout` обязаны идти с `credentials: "include"`
(в axios — `withCredentials: true`), иначе браузер cookie не приложит. CORS
на бэкенде этот режим разрешает, но только для origin'ов из белого списка.

Из заголовков ответа браузер отдаёт коду только безопасный набор — остальные
не видны, даже когда пришли по сети. Бэкенд открывает два сверх набора:
`Location` (адрес созданной записи, см. таблицу эндпоинтов) и `Retry-After`
(сколько ждать после `429`). Читать их из ответа можно, остальные заголовки —
нет, пока они не добавлены в этот список на бэкенде.

Реакция на **401**: от закрытого эндпоинта — один раз сходить на `refresh`
и повторить запрос; от самого `refresh` — сессии больше нет, на страницу
логина. Повторный `refresh` в ответ на 401 от `refresh` даёт бесконечный цикл.

Повторное использование уже обменянного refresh-токена сервер считает кражей
и гасит всю цепочку токенов этой сессии: разлогинены оказываются оба
её держателя, вернуться можно только по паролю. Обмен одним и тем же токеном
дважды в пределах минуты кражей не считается — это гонка двух вкладок.

Смена пароля закрывает все сессии учётной записи и обрывает выданные ранее
access-токены, не дожидаясь их истечения.

## Формат ошибок

Любая ошибка — [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457),
`Content-Type: application/problem+json`:

```json
{
  "title": "Unauthorized",
  "status": 401,
  "detail": "Требуется аутентификация.",
  "instance": "/api/users/profile",
  "timestamp": "2026-07-28T16:10:39.141549900Z"
}
```

Поля `type` в ответах нет: по RFC 9457 его значение по умолчанию —
`about:blank`, и Spring такое значение не сериализует. Появится оно только
вместе с собственными типами ошибок, если они когда-нибудь понадобятся.

Поля `instance` (путь запроса) и `timestamp` заполняются во всех ошибках,
включая 401 из JWT-фильтра (нет токена / битый токен / заблокированный
или удалённый пользователь) и ошибку валидации формы.

Ошибка валидации формы дополнительно несёт словарь `errors`
(имя поля → список сообщений, пригодных для показа пользователю):

```json
{
  "title": "Ошибка валидации",
  "status": 400,
  "detail": "Ошибка валидации.",
  "instance": "/api/users/change-password",
  "timestamp": "2026-07-28T16:10:39.141549900Z",
  "errors": {
    "newPassword": ["Пароль должен быть минимум 8 символов", "Новый пароль обязателен"]
  }
}
```

На одно поле может прийти несколько сообщений — порядок в списке
не гарантирован, полагаться на него нельзя.

Семантика статусов:

| Статус | Значение | Реакция фронта |
|---|---|---|
| 400 | невалидные данные формы (`errors`) или неверный старый пароль при смене | показать ошибки у полей |
| 401 | нет/протух access-токен; неверные логин-пароль на `/login` | один раз сходить на `/api/users/auth/refresh` и повторить запрос; на логин уводить, только если 401 пришёл от самого `refresh` (подробный порядок — в разделе «Аутентификация»). На форме логина — «неверный логин или пароль» |
| 403 | пользователь узнан, но прав не хватает | показать «недостаточно прав», на логин не уводить |
| 404 | ресурс не найден | страница/плашка «не найдено» |
| 409 | конфликт данных | показать сообщение, предложить повторить |
| 429 | слишком много попыток входа с одного адреса | показать «повторите позже»; сколько ждать — в заголовке `Retry-After`, в секундах |
| 500 | ошибка сервера | общая плашка ошибки; это баг бэкенда, о нём сообщать |

Важно: `/login` с несуществующим логином и с неверным паролем отвечает
**одинаково** (401, «Неверный логин или пароль.») — это сделано намеренно,
чтобы не раскрывать, какие логины существуют.

**Роли.** Их четыре: `admin` (суперпользователь), `moderator`, `teacher`
и обычный `user`. Права сегодня даёт только пара админ/модератор —
управление всем контентом из таблицы выше: новостями, конференциями,
достижениями, разделами, карточками ППС и УВП, дисциплинами и файлами; между собой
эти две роли различаются в одном месте — учётными записями (`GET /api/users`
и `GET /api/users/{id}`) распоряжается только `admin`, модератор получает там `403`.
Роль `teacher` открывает свою карточку ППС (`GET` и `PUT /api/teachers/me`),
календарь событий (`/api/events`) и справочник учёток преподавателей
(`GET /api/users/directory`), без которого некого назначить на событие;
на всех остальных закрытых ручках преподаватель получает `403` наравне
с обычным пользователем.

Отказы различаются: без токена или с негодным токеном приходит `401`,
с исправным токеном и недостаточной ролью — `403`. Колонка «кому доступно»
проверяется целиком, ручка × роль, в `EndpointAccessMatrixTest`; таблица
в этом тесте и есть источник правды, а ручка, которой в ней нет, роняет сборку.

Схемы тел — в Swagger. **Swagger доступен только вне прод-профиля**: на боевом
стенде `/swagger-ui/**` и `/v3/api-docs` отвечают `404`, чтобы не раздавать
карту API наружу. Локально и на dev-стенде всё как прежде.

Нюансы, которые из Swagger не видны:

* незаполненные поля приходят как `null` (например, `avatar`,
  `previewImage`) — фронт должен это ожидать;
* `createdAt` — ISO-8601 со смещением, например `2026-07-24T10:15:30.123456+04:00`;
* `postType` новости — `news` или `announcements`;
* булевы поля профиля называются `teacher`, `moderator`, `superuser` — без
  префикса `is`;
* у новости и у объявления о конференции три поля про обложку:
  `previewImage` — ключ файла, `previewImageUrl` — готовый адрес для показа,
  `previewImageDescription` — текст для `alt`; подробности в разделе
  «Обложка новости».

## Смена пароля

`POST /api/users/change-password` с телом `{"oldPassword": "...", "newPassword": "..."}`,
ответ — `200` с пустым телом.

| Поле | Обязательно | Ограничения |
|---|---|---|
| `oldPassword` | да | непустой; не совпал с текущим — `400` |
| `newPassword` | да | от 8 символов и **не длиннее 72 байт в UTF-8** |

Верхняя граница — в байтах, а не в символах: это предел алгоритма bcrypt.
Для кириллицы символ занимает два байта, то есть 36 русских букв уже упираются
в лимит. Клиентская проверка должна считать байты
(`new TextEncoder().encode(password).length`), иначе пользователь увидит `400`
там, где по числу символов всё выглядит допустимым.

Смена пароля закрывает все сессии учётной записи — см. «Аутентификация».

## Профиль пользователя

`GET /api/users/profile` отдаёт карточку текущего пользователя:

```json
{
  "id": 42,
  "username": "prof_ivanov",
  "firstName": "Иван",
  "lastName": "Иванов",
  "email": "ivanov@stankin.ru",
  "avatar": "avatars/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "avatarUrl": "/media/avatars/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "teacher": true,
  "moderator": false,
  "superuser": false
}
```

`avatar` — ключ файла, он же отправляется обратно при правке; `avatarUrl` — адрес
для `<img src>`. У пользователя без аватара оба поля приходят как `null`.

**Правка** — `PUT /api/users/profile`. Тело:

| Поле | Обязательно | Значение |
|---|---|---|
| `firstName` | нет | имя, до 150 символов |
| `lastName` | нет | фамилия, до 150 символов |
| `avatar` | нет | ключ файла из раздела `avatars` |

Ответ — `200` и профиль целиком, в том же виде, что у `GET`.

**Запрос заменяет карточку целиком.** Поле, которого в теле нет или которое пришло
как `null`, очищается: `PUT` с одним лишь `avatar` сотрёт имя и фамилию. Форма правки
обязана отправлять все три поля, включая неизменённые.

**Что этой ручкой не меняется:** логин, почта, telegram-код и флаги ролей. Такие поля
в теле игнорируются молча — запрос остаётся успешным, значения в базе не меняются.
Смена логина и почты из личного кабинета не предусмотрена вовсе.

Пустая строка в любом из трёх полей равносильна `null` — этим занимается общая
нормализация тела запроса, описанная в «Базовом».

**Аватар.** Сначала `POST /api/files` с `category: avatars`, затем `key` из ответа
уходит в поле `avatar`. Ключ обязан указывать на существующий файл раздела `avatars`:
ключ чужого раздела отвергается с `400`, даже если такой файл существует. Прежний файл
удаляется с диска после успешного сохранения; `avatar: null` очищает аватар и тоже
удаляет файл.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | имя или фамилия длиннее 150 символов — со словарём `errors`; ключ аватара не найден в разделе `avatars` — с причиной в `detail` |
| `401` | нет токена или он протух |

## Учётные записи (админ)

`GET /api/users` отдаёт страницу учётных записей. Ручка админская: модератор,
преподаватель и обычный пользователь получают `403`.

```json
{
  "content": [
    {
      "id": 42,
      "username": "prof_ivanov",
      "firstName": "Иван",
      "lastName": "Иванов",
      "email": "ivanov@stankin.ru",
      "avatarUrl": "/media/avatars/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
      "teacher": true,
      "moderator": false,
      "superuser": false,
      "active": true,
      "lastLogin": "2026-08-27T10:15:30.123456+04:00",
      "dateJoined": "2026-07-01T09:00:00+04:00"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 34,
  "totalPages": 2
}
```

Отличия от `GET /api/users/profile`: добавлены `active`, `lastLogin` и `dateJoined`,
убран ключ файла `avatar` — остаётся только готовый адрес `avatarUrl`. Хеш пароля
и telegram-код не отдаются. `lastLogin` у пользователя, ни разу не входившего
на портал, приходит как `null`.

**Параметры отбора** — все необязательные, комбинируются между собой:

| Параметр | Значение |
|---|---|
| `q` | подстрока логина, имени, фамилии или почты; регистр не важен. Пустое значение равносильно отсутствию параметра |
| `active` | `true` — только действующие учётки, `false` — только заблокированные |
| `role` | `admin`, `moderator`, `teacher` или `user` |

Роли друг друга не исключают: учётка может быть одновременно `moderator` и `teacher`
и попадёт в выдачу обоих фильтров. `role=user` отбирает тех, у кого не выставлено
ни одной роли.

Сортировка по умолчанию — `username` по возрастанию, параметр `?sort=` работает как
у остальных списков; пагинация описана в разделе «Пагинация списков».

`GET /api/users/{id}` отдаёт одну такую же карточку.

**Создание** — `POST /api/users`. Регистрации в портале нет, и это единственный способ
завести аккаунт. Тело:

| Поле | Обязательно | Значение |
|---|---|---|
| `username` | да | логин, до 150 символов; занятый логин отвергается |
| `password` | да | не короче 8 символов |
| `email` | нет | адрес почты, до 254 символов |
| `firstName`, `lastName` | нет | до 150 символов каждое |
| `superuser`, `moderator`, `teacher` | нет | флаги ролей, по умолчанию `false` |

Ответ — `201`, заголовок `Location` с адресом новой учётки и тело в том же виде, что
у `GET`. Учётная запись создаётся действующей (`active: true`). Пароль в ответе
не возвращается.

**Правка** — `PUT /api/users/{id}`. Тело:

| Поле | Обязательно | Значение |
|---|---|---|
| `email` | нет | адрес почты, до 254 символов |
| `firstName`, `lastName` | нет | до 150 символов каждое |
| `superuser`, `moderator`, `teacher` | да | флаги ролей |
| `active` | да | `false` блокирует учётную запись |

Запрос заменяет карточку целиком: необязательное поле, которого в теле нет, очищается.
Четыре флага при этом обязательны — тело без любого из них отвергается `400`, чтобы
правка почты не сняла заодно роль и не заблокировала человека.

Логин и пароль этой ручкой не меняются: логин не меняется нигде, пароль — своей
отдельной ручкой.

Себе админ не может ни снять `superuser`, ни выставить `active: false`. Это и есть
гарантия того, что действующий администратор в системе не кончится.

Блокировка обрывает доступ сразу: следующий запрос с прежним access-токеном получает
`401`, обновление сессии по refresh-cookie отклоняется.

**Сброс пароля** — `POST /api/users/{id}/reset-password` с телом
`{"newPassword": "..."}`, не короче 8 символов. Старый пароль не спрашивается: админ
его не знает. Ответ — `204` без тела, пароль в ответе не возвращается.

**Завершение сессий** — `POST /api/users/{id}/logout`, без тела, ответ `204`. Пароль
остаётся прежним, и человек может войти заново; обрываются только открытые сессии.

Обе ручки действуют одинаково и немедленно: все выданные ранее access-токены
перестают приниматься, а попытка обновиться по refresh-cookie отвечает `401`
и закрывает сессию окончательно. Отдельного «выхода со всех устройств» для самого
пользователя в контракте нет — это делает `POST /api/users/auth/logout` для текущей
сессии.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | `role` вне списка выше, занятый логин, попытка разжаловать или заблокировать себя — причина в `detail`; нарушение ограничений формы — со словарём `errors` |
| `403` | запрос не от админа |
| `404` | учётной записи с таким `id` нет |

### Справочник учёток преподавателей

`GET /api/users/directory` — постраничный список учётных записей, которым можно
что-то назначить. Ручка открыта админу, модератору и преподавателю; обычный
пользователь получает `403`.

```json
{
  "content": [
    { "id": 42, "lastName": "Иванов", "firstName": "Иван" }
  ],
  "page": 0,
  "size": 50,
  "totalElements": 12,
  "totalPages": 1
}
```

В справочнике только `id` и ФИО. Логина и почты в нём нет намеренно: ручка
доступна любому преподавателю, а перебор страниц с `username` в ответе выгружал
бы логины портала в обход админской проверки — ровно та утечка, которую закрыли
в карточках календаря (T-54b).

В выдачу попадают учётки с ролью `teacher`, действующие (`active: true`).
Заблокированная учётка в портал не войдёт, и назначать на неё событие
или привязывать к ней карточку ППС бессмысленно.

Сортировка по умолчанию — `lastName`, `firstName`, `id`; размер страницы
по умолчанию 50. Полный список учётных записей со всеми полями остаётся
админским (`GET /api/users`).

Справочник закрывает две дырки формы: `assignedUserIds` у события календаря
и `userId` у карточки ППС — в обоих местах в теле запроса едет `id` учётки,
а взять его до этой ручки было неоткуда.

## Новость: форма ответа

Так выглядит новость в ответе — и в списке (`content[]`), и поштучно:

```json
{
  "id": 42,
  "title": "Конференция кафедры",
  "shortDescription": "Краткий анонс для карточки",
  "postType": "news",
  "previewImage": "news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "previewImageUrl": "/media/news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "previewThumbnailUrl": "/media/news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002_thumb.jpg",
  "previewImageDescription": "Участники конференции",
  "content": "<p>Полный текст новости</p>",
  "createdAt": "2026-08-28T06:05:49.985493Z",
  "display": true,
  "authorName": "Иван Иванов"
}
```

`authorName` — имя и фамилия автора одной строкой, собирается на бэкенде.
Приходит `null`, если у автора не заполнены ни имя, ни фамилия; если заполнена
только одна часть, придёт она одна. Поле только для чтения: в запросах
на создание и правку его нет, автора проставляет сервер по токену.

Даты приходят строкой ISO-8601 со смещением (`Z` — UTC), пригодной
для `new Date(...)` без предобработки. Смещение зависит от сервера,
привязываться к конкретному (`+03:00`) нельзя.

Поля обложки могут быть `null` все три сразу — это новость без картинки.

## Новости: фильтр по типу записи

Новости и объявления кафедры хранятся вместе и по умолчанию приходят одним
списком. Разделить их — необязательный параметр `postType` у `GET /api/public/news`
и `GET /api/news`:

| Запрос | Что приходит |
|---|---|
| `?postType=news` | только новости |
| `?postType=announcements` | только объявления |
| параметр не передан | и то и другое — поведение прежнее |
| `?postType=` (пустое значение) | и то и другое: пустой фильтр — это «все типы» |
| любое другое значение | `400` с `ProblemDetail`, значение названо в `detail` |

Значение вне словаря — именно ошибка, а не пустая страница. Опечатка вроде
`?postType=announcement` иначе выглядела бы как «объявлений пока нет», и причину
искали бы в контенте, а не в запросе.

**`totalElements` и `totalPages` считаются с учётом фильтра.** Это делает фильтр
пригодным для пагинации: отбор на клиенте уменьшил бы список на экране, но не
счётчики — те приходят от базы, и пагинатор продолжал бы обещать страницы,
которых нет.

Параметр складывается с `page`, `size` и `sort`: `?postType=news&page=1&size=10`.

## Новости: создание, правка, удаление

`POST /api/news` отвечает **201** и кладёт путь созданной новости в заголовок
`Location` (`/api/news/{id}`); тело ответа — та же новость, включая `id`.
Прежнее «200 с пустым телом» больше не приходит.

`PUT /api/news/{id}` — **полная замена** состояния новости, а не частичное
обновление. Поле, не пришедшее в теле запроса, обнуляется: форма редактирования
обязана отправлять все поля, включая незатронутые. Валидация та же, что
у создания.

Правила для тела `POST` и `PUT`:

| Поле | Обязательно | Ограничения |
|---|---|---|
| `title` | да | **от 5** до 100 символов — единственное поле в API с нижней границей |
| `postType` | да | только `news` или `announcements` |
| `content` | да | должен остаться непустым после чистки HTML |
| `display` | да | `true` или `false`; поле без значения — `400`, а не «скрыта по умолчанию» |
| `shortDescription` | нет | до 255 символов |
| `previewImage` | нет | до 100 символов, ключ из раздела `news` |
| `previewImageDescription` | нет | до 256 символов |

`DELETE /api/news/{id}` удаляет новость физически и отвечает **204** без тела.
Скрыть новость, не удаляя, — это `PUT` с `display: false`.

Удаление и правка несуществующей новости дают `404`. Скрытая новость
(`display: false`) для публичных эндпоинтов неотличима от несуществующей —
тоже `404`, а не `403`: иначе перебором `id` можно было бы пересчитать
неопубликованные черновики.

В теле новости есть поле `display` — оно нужно админскому списку, чтобы
отличать опубликованные новости от скрытых. В публичной выдаче там всегда `true`.

**Текст чистится от небезопасной разметки**, и проверка обязательности выполняется
по результату чистки: тело, от которого после удаления скриптов ничего не осталось
(`<script>alert(1)</script>`), даёт `400` со словарём `errors` по полю `content`,
а не сохранённую новость с пустым текстом. То же правило у содержания достижения.

Rich-text в новости только `content`. `title`, `shortDescription`
и `previewImageDescription` — плоский текст по общему правилу из «Базового»:
сервер их не чистит и не экранирует, `<b>` в кратком описании вернётся из API
теми же байтами, какими пришёл.

## Загрузка файлов

Файлы загружаются отдельным запросом, до сохранения сущности. Причина в rich-text:
картинка внутри `content` существует как `<img src="...">`, то есть адрес нужен
редактору в момент вставки, за несколько минут до нажатия «Сохранить». Обложка
(`previewImage`) идёт через ту же ручку, чтобы механизм был один.

**Запрос** — `POST /api/files`, `Content-Type: multipart/form-data`, две части:

| Часть | Обязательна | Значение |
|---|---|---|
| `file` | да | сам файл |
| `category` | нет, по умолчанию `news` | раздел хранилища: `news`, `avatars`, `publications`, `achievements` |

Права зависят от раздела: `avatars` открыт любому авторизованному — свой аватар
меняет владелец учётной записи, а не редактор. Остальные разделы остаются за
админом и модератором: содержимое портала наполняют они.

**Ответ** — `201`:

```json
{
  "key": "news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "url": "/media/news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg"
}
```

* `key` — то, что отправляется в `previewImage` при создании или правке новости
  и хранится в базе. Формат ключа — деталь бэкенда, разбирать его на фронте не нужно.
  Ключ принимается только тем полем, чей раздел совпадает с разделом загрузки:
  обложки новостей и конференций — из `news`, обложки достижений — из `achievements`,
  аватары — из `avatars`. Ключ существующего файла из чужого раздела даёт `400`.
* `url` — адрес для показа: подставляется в `<img src>` для предпросмотра сразу
  после загрузки и в `content` при вставке картинки в текст. Адрес относительный,
  без домена: браузер достроит его от текущего origin.

**Ограничения.** Принимаются только JPEG и PNG размером до 15 МБ и не более
25 мегапикселей. Формат определяется по содержимому файла, а не по расширению
и не по `Content-Type`: переименованный `.exe` получит `400`. WebP, GIF и SVG
отклоняются — последний принципиально, поскольку SVG может содержать
исполняемый код.

Ограничение на мегапиксели существует отдельно от ограничения на мегабайты:
PNG со сплошной заливкой сжимается тысячекратно, и пятнадцати мегабайт файла
хватает на изображение в двадцать тысяч точек по стороне — оно развернулось бы
в памяти сервера в полтора гигабайта. Размеры читаются из заголовка файла,
до разбора пикселей, поэтому такой запрос стоит серверу почти ничего
и получает `400` (T-54d). Снимок с телефона в 12 или 24 мегапикселя проходит
свободно.

**Что происходит с файлом.** Изображение перекодируется и, если превышает
1600 пикселей по стороне, уменьшается с сохранением пропорций; меньшие не
растягиваются. Перекодирование удаляет EXIF, включая координаты съёмки.
JPEG остаётся JPEG, PNG остаётся PNG — прозрачность не теряется. Загруженный
файл на диске отличается от исходного, и сравнивать их размеры бессмысленно.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | не изображение, неподдерживаемый формат, больше 25 мегапикселей, пустой файл, неизвестная `category` |
| `401` | нет токена или он протух |
| `403` | раздел не `avatars`, а роль не админ и не модератор |
| `413` | файл больше допустимого размера |

В `detail` — человекочитаемая причина, её можно показывать пользователю.

**Раздача.** `GET /media/{key}` открыт всем и токена не требует: картинки видны
посетителям сайта. Метод только `GET`.

**Один файл у нескольких записей.** Один и тот же `key` можно поставить обложкой
нескольким записям — например, повторно выбрав уже загруженную картинку. Файл
удаляется с диска только вместе с последней ссылкой на него: правка или удаление
одной записи не ломает картинку у остальных.

**Сироты.** Файл, загруженный, но не сохранённый ни в одной сущности (модератор
передумал и закрыл форму), убирает фоновая задача — раз в сутки, и только файлы
старше `ORPHAN_CLEANUP_MIN_AGE` (по умолчанию 24 часа). Удалять их с фронта
не нужно.

Отсюда одно следствие для черновиков: ключ, полученный из `POST /api/files`
и пролежавший в неотправленной форме дольше суток, к моменту сохранения может
исчезнуть — сохранение вернёт `400` «файл не найден». Долгоживущий черновик
надёжнее пересохранять картинку заново, чем держать старый ключ.

Занятым считается файл, на который ссылается либо колонка обложки или аватара,
либо `<img>` внутри `content`. Разделы без владельца (сейчас `publications`)
задача не трогает вовсе: удалять то, чью занятость спросить не у кого, нельзя.

## Обложка новости

За обложку отвечают три поля:

| Поле | Направление | Значение |
|---|---|---|
| `previewImage` | запрос и ответ | ключ файла в хранилище — тот, что вернул `POST /api/files` |
| `previewImageUrl` | только ответ | готовый адрес картинки для `<img src>` |
| `previewThumbnailUrl` | только ответ | адрес уменьшенной копии (до 240 px) для ленты |
| `previewImageDescription` | запрос и ответ | текст для атрибута `alt` |

**Миниатюра.** При загрузке картинки в раздел `news` хранилище кладёт рядом
уменьшенную копию — тот же ключ с суффиксом `_thumb` перед расширением.
Клиенту про это знать не нужно: он по-прежнему отправляет один `previewImage`,
а бэкенд сам находит миниатюру при сохранении новости и отдаёт её адрес
в `previewThumbnailUrl`. У новостей, заведённых до появления миниатюр, второго
файла нет, и поле приходит как `null` — ленте следует откатываться
на `previewImageUrl`.

Отправляется **ключ**, показывается **адрес**. Собирать адрес на фронте не нужно
и не следует: правило сборки — деталь бэкенда, и при переносе файлов на объектное
хранилище или CDN изменится только `previewImageUrl`, а `previewImage` и код клиента
останутся прежними. Форма редактирования отправляет обратно тот же `previewImage`,
который пришёл в ответе.

Обложки может не быть — тогда все три поля приходят как `null`.

**Проверка ключа.** Ключ проверяется при создании и при правке новости. Если файла
по нему в хранилище нет, приходит `400` с текстом «Файл обложки не найден: ...»,
и новость не создаётся и не изменяется. Тот же `400` — на ключ, уводящий за пределы
хранилища. Пустая строка ключом не считается: по правилу из «Базового» она
равносильна `null`, то есть снятию обложки, — а снятие удаляет старый файл. Практический вывод для клиента: `previewImage` заполняется значением
из ответа `POST /api/files`, а не собирается руками.

**Уборка файлов.** Файл, переставший быть обложкой, удаляется с диска: при замене
картинки на другую, при снятии обложки и при удалении новости. Правка новости
без смены обложки файл не трогает. Удаление происходит после успешного сохранения,
поэтому неудачный запрос картинку не портит.

## Редактируемые страницы

Тринадцать текстовых разделов сайта, содержимое которых правит модератор: контакты,
нормативные документы, учебные планы, блоки главной страницы. Никакой логики, кроме
хранения текста, за ними нет.

Раздел адресуется **слагом** — коротким латинским идентификатором в пути
(`contacts`, а не `7`). Слаг стабилен: он не зависит от того, какие `id` выдала
конкретная база, и переживает перенос данных со старого портала.

Набор разделов **закрыт**: тринадцать слагов создаются миграцией при первом запуске,
создать четырнадцатый или удалить существующий через API нельзя. Слаг захардкожен
в маршрутах фронтенда, поэтому удаление раздела означало бы неустранимую дырку
в навигации. По той же причине `PUT` по неизвестному слагу отвечает `404`,
а не создаёт новый раздел.

| Слаг | Раздел старого портала |
|---|---|
| `fields-of-study` | О кафедре → Направления подготовки |
| `contacts` | О кафедре → Контакты |
| `documents-department` | О кафедре → Нормативные документы → Кафедры |
| `documents-university` | О кафедре → Нормативные документы → Университета |
| `bachelor-edu-plans` | Учебная деятельность → Бакалавриат → Учебные планы |
| `bachelor-graduate` | Учебная деятельность → Бакалавриат → Защита ВКР |
| `bachelor-practices` | Учебная деятельность → Бакалавриат → Практики |
| `master-edu-plans` | Учебная деятельность → Магистратура → Учебные планы |
| `master-graduate` | Учебная деятельность → Магистратура → Защита ВКР |
| `master-practices` | Учебная деятельность → Магистратура → Практики |
| `scientific-activity-postgraduate` | Научная деятельность → Аспирантура |
| `home-before` | блок над лентой новостей на главной |
| `home-after` | блок под лентой новостей на главной |

Последние два — не страницы: собственного адреса у них нет, они выводятся
на главной над и под лентой новостей.

Ответ `GET /api/public/pages/contacts`:

```json
{
  "slug": "contacts",
  "title": "Контакты",
  "text": "## Как нас найти\n\nМосква, Вадковский переулок, 1",
  "createdAt": "2026-08-26T12:00:00+03:00",
  "updatedAt": "2026-08-26T14:30:00+03:00"
}
```

Тело `PUT /api/pages/contacts`:

```json
{ "title": "Контакты", "text": "## Как нас найти\n\n..." }
```

Слаг в теле запроса не передаётся: он берётся из пути и не редактируется.
Поля `id` в ответе нет — раздел адресуется только слагом.

**`text` — исходник Markdown, а не HTML.** Это единственное отличие от `content`
новости, где в базе лежит готовый HTML из редактора. Отсюда два следствия:

* рендерить `text` следует через `react-markdown` **без** `rehype-raw`. По умолчанию
  сырой HTML внутри Markdown этот пакет не исполняет; `rehype-raw` его включает —
  вместе с XSS. `dangerouslySetInnerHTML` неприменим по той же причине;
* бэкенд `text` не санитизирует. Санитайзер работает с HTML: применённый к исходнику
  Markdown, он экранирует служебные символы и портит разметку, которую модератор
  увидит в форме при следующей правке. Гарантия «браузер не исполнит чужой HTML»
  обеспечивается на шаге рендера.

**Пустая строка в `text` — легальное значение**: раздел нельзя удалить,
но можно опустошить, и `PUT` с `text: ""` делает именно это. Это единственное
поле, на которое не действует правило «пустая строка = `null`» из «Базового».

**`title` — подпись раздела для списка в админ-панели**, а не заголовок публичной
страницы: на старом портале заголовок рисовала навигация, и это поведение сохраняется.
В ответе поле может прийти `null` — в перенесённых со старого портала строках оно
заполнено не везде.

Но **на запись `title` обязателен**: `PUT` требует непустую подпись до 255 символов,
а `text` — присутствия поля (пустая строка допустима, `null` — нет). Из-за правила
«пустая строка = `null`» из «Базового» `title: ""` и `title: null` дают одинаковый
`400`. Практическое следствие: раздел, прочитанный с `title: null`, сохранить,
не заполнив подпись, нельзя — форма правки обязана требовать `title` как поле
с обязательной звёздочкой.

## Преподаватели

Карточки профессорско-преподавательского состава. Публичные ручки две: список
для страницы «Преподаватели» и полная карточка. Правка — ниже, в подразделе
«Создание и правка карточек».

Карточка живёт отдельно от учётной записи: фамилия, имя, отчество и фото
хранятся в самой карточке, а не в профиле пользователя. Учётная запись
у преподавателя может быть, а может отсутствовать — на ответ публичных ручек
это не влияет.

Элемент списка `GET /api/public/teachers` (обёртка — страница, как у новостей):

```json
{
  "id": 3,
  "lastName": "Иванова",
  "firstName": "Мария",
  "patronymic": "Петровна",
  "position": "доцент",
  "degree": "CANDIDATE_TECH",
  "rank": "READER",
  "avatarUrl": "/media/avatars/2026/08/a3f9.jpg"
}
```

Ответ `GET /api/public/teachers/{id}` — то же плюс остальные поля:

```json
{
  "id": 3,
  "userId": 7,
  "lastName": "Иванова",
  "firstName": "Мария",
  "patronymic": "Петровна",
  "position": "доцент",
  "degree": "CANDIDATE_TECH",
  "rank": "READER",
  "avatar": "avatars/2026/08/a3f9.jpg",
  "avatarUrl": "/media/avatars/2026/08/a3f9.jpg",
  "phoneNumber": "+7 (499) 972-95-84",
  "email": "m.ivanova@stankin.ru",
  "messenger": "@m_ivanova",
  "experience": 15,
  "professionalExperience": 8,
  "education": "МГТУ «СТАНКИН», специальность «Информационные системы»",
  "qualification": "инженер",
  "bio": "…",
  "examScheduleGraduation": "https://stankin.ru/uploads/exams-graduation.pdf",
  "examScheduleNonGraduation": null,
  "subjects": [
    { "id": 1, "name": "Базы данных", "description": "Реляционная модель, SQL" },
    { "id": 4, "name": "Проектирование информационных систем", "description": null }
  ]
}
```

Пояснения к полям:

* `avatar` — ключ файла фото, `avatarUrl` — адрес для `<img src>`; ключ есть
  только в детальной карточке, в элементе списка остаётся один адрес;
* `userId` — учётная запись, привязанная к карточке, или `null`; тоже только
  в детальной карточке. По этой связи работает `GET /api/teachers/me`, и её же
  принимает форма правки — см. «Создание и правка карточек»;
* `email` и `phoneNumber` — рабочие контакты из карточки, а не из учётной
  записи; заполняет модератор;
* `experience` — общий стаж в годах, `professionalExperience` — стаж
  по специальности;
* `examScheduleGraduation` / `examScheduleNonGraduation` — ссылки на PDF
  с расписанием экзаменов выпускных и невыпускных курсов;
* `subjects` — дисциплины преподавателя, по алфавиту названий. Только
  в детальной карточке, в списке их нет;
* `education` и `qualification` — **rich-text HTML**, как `content` новости:
  на старом портале оба поля выводились через `[innerHTML]` и в перенесённых
  строках лежит разметка. Сервер чистит их при сохранении по тому же белому
  списку, поэтому `<script>` и обработчики событий до браузера не доходят;
* `bio` — **плоский текст**, несмотря на соседство с двумя предыдущими:
  на старом портале поле не выводилось ни на одной странице, и разметке
  в нём взяться неоткуда. Сервер его не чистит, фронт выводит текстовым узлом.
  Прочие строки карточки — `position`, `messenger`, ФИО — тоже плоский текст;
* любое незаполненное поле приходит как `null` — включая `degree`, `rank`
  и `patronymic`.

**`degree` и `rank` — коды из закрытых словарей**, подписи рисует фронт —
так же, как с `postType` у новостей:

| `degree` | Подпись |
|---|---|
| `CANDIDATE_TECH` | кандидат технических наук |
| `DOCTOR_TECH` | доктор технических наук |
| `CANDIDATE_PHYS_MATH` | кандидат физико-математических наук |
| `DOCTOR_PHYS_MATH` | доктор физико-математических наук |
| `CANDIDATE_ECONOM` | кандидат экономических наук |
| `DOCTOR_ECONOM` | доктор экономических наук |
| `CANDIDATE_PED` | кандидат педагогических наук |
| `null` | без степени |

| `rank` | Подпись |
|---|---|
| `READER` | доцент |
| `PROFESSOR` | профессор |
| `null` | без звания |

Коды повторяют старый портал буква в букву, включая неудачный `READER`
вместо `DOCENT`: в старой базе лежат именно эти строки, и совпадение кодов
делает перенос данных копированием колонки без преобразований — по той же
причине, по которой сохранены старые имена таблиц. Должность (`position`) —
свободная строка, словаря у неё нет.

Сортировка списка — по умолчанию `lastName`, `firstName`, `id`; в `sort`
передаются поля карточки (`lastName`), путь `user.lastName` больше не работает.

### Создание и правка карточек

Права распределены как на старом портале: модератор (и админ) управляет любыми
карточками, преподаватель правит свою — целиком, кроме дисциплин. Дисциплины
назначает только модератор: так было и в старом (они правились через
Django-админку и в сериализатор ЛК не входили).

Тело `POST /api/teachers` и `PUT /api/teachers/{id}`:

```json
{
  "userId": 7,
  "lastName": "Иванова",
  "firstName": "Мария",
  "patronymic": "Петровна",
  "position": "доцент",
  "degree": "CANDIDATE_TECH",
  "rank": "READER",
  "avatar": "avatars/2026/08/a3f9.jpg",
  "phoneNumber": "+7 (499) 972-95-84",
  "email": "m.ivanova@stankin.ru",
  "messenger": "@m_ivanova",
  "experience": 15,
  "professionalExperience": 8,
  "education": "МГТУ «СТАНКИН», специальность «Информационные системы»",
  "qualification": "инженер",
  "bio": "…",
  "examScheduleGraduation": "https://stankin.ru/uploads/exams-graduation.pdf",
  "examScheduleNonGraduation": null,
  "subjectIds": [1, 4]
}
```

Правила — те же, что у новостей:

* `PUT` — **полная замена**: поле, не пришедшее в теле, обнуляется, форма
  отправляет все поля;
* обязательны только `lastName`, `firstName` и `position` — как в старой
  модели; всё остальное может быть `null`;
* `avatar` — ключ файла, загруженного заранее через
  `POST /api/files?category=avatars`, по той же схеме, что обложка новости;
  ключ несуществующего файла — `400`; ключ уже сохранённого фото приходит
  в ответе полем `avatar` и отправляется обратно при правке — иначе фото
  считается снятым и файл удаляется с диска;
* неизвестный код в `degree` или `rank` — `400` с `ProblemDetail`;
* `subjectIds` — `id` существующих дисциплин, неизвестный `id` — `400`;
* `userId` — привязка карточки к учётной записи: `id` существующей учётки
  или `null`. Учётка есть не у каждой карточки, и это штатно. Три причины
  для `400`: неизвестный `id`, учётка уже занята другой карточкой (связь один
  к одному) и учётка без роли `teacher` — с ней «моя карточка» всё равно
  ответила бы `403`, и молча сохранённая связь превратилась бы в необъяснимую
  ошибку у преподавателя. Поле подчиняется правилу полной замены: не пришло
  в теле `PUT` — связь снята, поэтому форма отправляет обратно `userId`
  из ответа. Идентификатор берётся из справочника `GET /api/users/directory` —
  в нём учётки без роли и не показываются;
* `education` и `qualification` чистятся от небезопасной разметки на всех
  трёх путях записи — `POST`, `PUT` и `PUT /api/teachers/me`; содержимое,
  вычищенное до пустоты, сохраняется как `null`, а не как пустая строка;
* `DELETE` удаляет карточку физически и отвечает `204`; привязанная учётная
  запись при этом не удаляется и работать не перестаёт.

**Своя карточка** (`/api/teachers/me`) — те же тела, что выше, с двумя
отличиями: в теле `PUT` игнорируются `subjectIds` и `userId`, а ответы обеих
ручек — полная карточка с дисциплинами, как публичная детальная. Привязку
к учётной записи преподаватель себе не меняет: иначе он переписал бы её
на чужую учётку и увёл карточку. Это дело модератора.
`me` определяется по токену; если к учётной записи карточка не привязана,
обе ручки отвечают `404`.

**Дисциплины** (`GET` / `POST /api/subjects`) — словарь для формы карточки:
`{ "id": 1, "name": "Базы данных", "description": "Реляционная модель, SQL" }`,
список постранично, сортировка по `name`. Создание — `{ "name": "...",
"description": "..." }`, имя обязательно и уникально, дубль — `409`;
описание необязательно и приходит как `null`, если не заполнено. Схема
дисциплины одна на все места: те же три поля приходят и в списке `subjects`
внутри детальной карточки ППС. Правки и удаления дисциплин в T-26 нет — появятся вместе
с админ-панелью, если понадобятся.

Что меняется против прежнего ответа списка (сводка для F-21):

* ФИО и фото приходят из карточки; поля учётной записи `userId` и `email`
  из элемента списка исчезают (`email` остаётся только в детальной карточке
  и означает рабочий контакт);
* добавляется `patronymic`;
* `degree` и `rank` — коды словарей вместо произвольного текста;
* вместо `avatar` (имя файла без адреса) приходит `avatarUrl` — готовый адрес
  для `<img>`;
* сортировка — `lastName` вместо `user.lastName`;
* появляется детальная ручка.

## Учебно-вспомогательный персонал (УВП)

Лаборанты, инженеры, методисты — карточки без степеней, званий, дисциплин
и учётных записей. Одна публичная ручка списка и модераторский CRUD;
детальной ручки нет — карточка целиком помещается в элементе списка.

Элемент списка `GET /api/public/helpers` (обёртка — страница):

```json
{
  "id": 2,
  "lastName": "Кузнецова",
  "firstName": "Анна",
  "patronymic": "Сергеевна",
  "position": "инженер кафедры",
  "avatar": "avatars/2026/08/c7d1.jpg",
  "avatarUrl": "/media/avatars/2026/08/c7d1.jpg"
}
```

Тело `POST /api/helpers` и `PUT /api/helpers/{id}` — те же поля без `id`
и `avatarUrl`: фото задаётся ключом `avatar` (файл из
`POST /api/files?category=avatars`), он же приходит в ответе и отправляется
обратно при правке.
Правила — как у карточек преподавателей: `PUT` — полная замена, обязательны
только `lastName`, `firstName` и `position`, ключ несуществующего файла — `400`,
`DELETE` — физическое удаление с `204`. Сортировка по умолчанию — `lastName`,
`firstName`, `id`.

## Конференции

Объявления о научных конференциях: даты проведения, организатор, контакты
и rich-text-содержимое. На старом портале — раздел «Научная деятельность →
Конференции».

Публичных ручек две. Список отдаёт страницу только видимых объявлений —
скрытые (`display: false`) из выдачи исключаются. Детальная на скрытое
или несуществующее объявление отвечает `404`: как и у новостей, скрытое
неотличимо от несуществующего. Модераторский CRUD устроен
как у новостей: `GET /api/conferences` и `GET /api/conferences/{id}` видят
скрытые, `POST` отвечает `201` с заголовком `Location` и созданным
объявлением в теле, `PUT` — **полная замена** (поле, не пришедшее в теле,
обнуляется), `DELETE` — физическое удаление с `204`.

Ответ `GET /api/public/conferences/{id}` (элемент списка — та же схема,
обёртка списка — страница, как у новостей):

```json
{
  "id": 5,
  "title": "Информационные технологии в промышленности — 2026",
  "description": "Ежегодная научно-практическая конференция кафедры.",
  "startDate": "2026-10-14",
  "endDate": "2026-10-16",
  "time": "10:00",
  "organizer": "кафедра УИТС, МГТУ «СТАНКИН»",
  "contactEmail": "conf@stankin.ru",
  "contactPhone": "+7 (499) 972-95-84",
  "content": "<p>Приглашаем к участию…</p>",
  "previewImage": "news/2026/08/a3f9.jpg",
  "previewImageUrl": "/media/news/2026/08/a3f9.jpg",
  "previewImageDescription": "Афиша конференции",
  "createdAt": "2026-08-27T12:00:00+03:00",
  "display": true
}
```

Пояснения к полям:

* `startDate` и `endDate` — календарные даты `YYYY-MM-DD`, `time` — время
  начала `HH:mm`; секунды, если клиент их пришлёт, при сохранении
  отбрасываются, и в ответе время всегда с точностью до минуты. Смещения зоны у них нет сознательно: конференция проходит
  «14 октября в 10:00» по местному времени площадки, а не в момент на шкале
  UTC — в отличие от `createdAt`, который остаётся ISO-8601 со смещением;
* однодневная конференция — `endDate: null`, и это единственное её
  представление: `endDate`, присланный равным `startDate`, при сохранении
  нормализуется в `null`, так что проверять равенство дат при рендере
  не нужно;
* `content` — rich-text HTML, как у новости; при сохранении сервер вычищает
  из него всё, что не входит в белый список тегов и атрибутов, поэтому
  `<script>` и обработчики событий до браузера не доходят. Содержимое,
  вычищенное до пустоты, сохраняется как `null`: у «пустого» `content`
  одно представление, а не два;
* rich-text здесь только `content`. Остальные строковые поля — `title`,
  `description`, `organizer`, `previewImageDescription` — плоский текст:
  сервер их не чистит и не обязан, а фронт обязан выводить их текстовым
  узлом, а не через `dangerouslySetInnerHTML`;
* обложка — тройка `previewImage` / `previewImageUrl` /
  `previewImageDescription` по правилам раздела «Обложка новости», включая
  проверку ключа и уборку файлов; загружается через `POST /api/files`
  с категорией `news`;
* автора у объявления нет — его не было и в старой модели;
* незаполненное поле приходит как `null`.

Тело `POST /api/conferences` и `PUT /api/conferences/{id}` — те же поля
без `id`, `createdAt` и `previewImageUrl`. Валидация:

* обязательны только `title` (до 255 символов) и `display` — тело без
  `display` даёт `400`, а не молча скрытое объявление;
* `endDate` и `time` имеют смысл только при заданном `startDate`:
  присланные без него — `400`; `endDate` раньше `startDate` — тоже `400`.
  Сообщения этих проверок приходят в `errors` под ключами `endDate`
  и `time` соответственно;
* некорректный адрес в `contactEmail` — `400`; пустая строка — это `null`,
  а не ошибка (общее правило из «Базового»);
* лимиты длины остальных строк: `organizer` — 255, `contactEmail` — 254,
  `contactPhone` — 32, `previewImageDescription` — 256; `description`
  и `content` длиной не ограничены.

Для F-24: поле `is_hidden` старой модели заменено на `display` с обратным
смыслом — соглашение о видимости у всех сущностей одно, как и предлагал
комментарий к типу в `planned.types.ts`. Против того же типа все
необязательные поля стали nullable (в нём они объявлены как `string`),
а однодневность кодируется только как `endDate: null`.

## Достижения кафедры

Награды, гранты и победы в конкурсах: краткое описание, rich-text-содержимое,
обязательная обложка и необязательная привязка к преподавателю. На старом
портале — раздел «Научная деятельность → Достижения».

Публичных ручек три. Список отдаёт страницу только видимых достижений —
скрытые (`display: false`) из выдачи исключаются. Детальная на скрытое
или несуществующее достижение отвечает `404`. Третья —
`GET /api/public/teachers/{teacherId}/achievements` — страница опубликованных
достижений одного преподавателя; её использует карточка ППС. Несуществующий
`teacherId` даёт не `404`, а пустую страницу: ручка фильтрует достижения
по ссылке, а не проверяет карточку. Модераторский CRUD устроен как
у конференций: `GET /api/achievements` и `GET /api/achievements/{id}` видят
скрытые, `POST` отвечает `201` с заголовком `Location`, `PUT` — **полная
замена**, `DELETE` — физическое удаление с `204`.

Ответ `GET /api/public/achievements/{id}` (элемент списка — та же схема,
обёртка списка — страница):

```json
{
  "id": 3,
  "title": "Победа в конкурсе «Инженер года»",
  "description": "Преподаватель кафедры стал лауреатом всероссийского конкурса.",
  "content": "<p>Награда присуждена за работы в области автоматизации…</p>",
  "previewImage": "achievements/2026/08/b41e.jpg",
  "previewImageUrl": "/media/achievements/2026/08/b41e.jpg",
  "createdAt": "2026-08-27T12:00:00+03:00",
  "display": true,
  "teacherId": 7,
  "teacherName": "Иванова Мария Петровна"
}
```

Пояснения к полям:

* `teacherId` и `teacherName` — привязка к карточке ППС. Достижение может
  быть кафедральным, а не персональным, и тогда оба поля — `null`.
  `teacherName` собирается сервером из фамилии, имени и отчества карточки:
  отдельный запрос за преподавателем ради подписи не нужен, а за ссылкой
  на карточку берётся `teacherId`;
* привязка переживает удаление карточки: если преподавателя удалили,
  достижение остаётся, а `teacherId` становится `null`;
* `content` — rich-text HTML, как у новости и конференции: сервер вычищает
  из него всё вне белого списка тегов и атрибутов. Отличие от конференции
  в том, что содержание **обязательно**, поэтому тело, вычищенное до пустоты
  (например, единственный `<iframe>`), — это `400`, а не сохранённый `null`;
* rich-text здесь только `content`. `title` и `description` — плоский текст:
  сервер их не чистит, фронт обязан выводить их текстовым узлом;
* обложка — пара `previewImage` / `previewImageUrl` по правилам раздела
  «Обложка новости», включая проверку ключа и уборку файла при замене
  и удалении записи; загружается через `POST /api/files` с категорией
  `achievements`. Поля `previewImageDescription` у достижения нет —
  его не было и в старой модели;
* автора у достижения нет — его не было и в старой модели;
* незаполненных полей, кроме пары `teacherId` / `teacherName`, у достижения
  не бывает: остальные обязательны.

Тело `POST /api/achievements` и `PUT /api/achievements/{id}` — те же поля
без `id`, `createdAt`, `previewImageUrl` и `teacherName`; вместо `teacherName`
приходит только `teacherId`. Валидация:

* обязательны `title` (до 100 символов), `description`, `content`,
  `previewImage` и `display` — тело без `display` даёт `400`, а не молча
  скрытое достижение;
* обложку нельзя снять правкой: `PUT` без `previewImage` — это `400`,
  а не достижение без картинки;
* `teacherId` необязателен; ссылка на несуществующую карточку — `400`;
* ключ несуществующего файла в `previewImage` — `400`;
* `description` и `content` длиной не ограничены.

Расхождения со старой моделью, важные для фронта: поле `is_published`
переименовано в `display`, поле `image` — в пару `previewImage` /
`previewImageUrl`; смысл обоих сохранён. Имена приведены к тем, что уже
используются у новостей и конференций, — общий сервис списка контента
на четыре раздела работает с одной схемой. Вместо строки `teacher`
с полным именем и отдельного `teacher_id` приходит пара
`teacherId` / `teacherName`.

## Импорт расписания преподавателя

Расписание не редактируется по полям: администратор загружает PDF из системы
СТАНКИНа, бэкенд отдаёт его микросервису разбора и сохраняет результат.

`POST /api/teachers/{id}/schedule/import` — `multipart/form-data`, единственное
поле `file` с PDF-файлом. Ответ `200`:

```json
{
  "teacherId": 3,
  "teacherName": "Чеканин Владимир Алексеевич",
  "lessons": [
    {
      "id": 41,
      "weekNumber": 1,
      "classTime": 1,
      "group": "ИДБ-25-11",
      "name": "Технические средства информационных систем",
      "type": "Лабораторная",
      "subgroup": "Б",
      "cabinet": "216",
      "dates": [
        {"id": 88, "startDate": "16.03", "endDate": "27.04", "alternativelyPeriod": true},
        {"id": 89, "startDate": "18.04", "endDate": null, "alternativelyPeriod": false}
      ]
    }
  ]
}
```

**Имени загруженного файла в ответе нет.** Оно запоминается в базе служебной
пометкой, но наружу не выходит: та же схема обслуживает публичное чтение, и имя
файла с машины модератора — операционная деталь, которой в публичном ответе
делать нечего. В старом портале сериализатор расписания вёл себя так же (T-54c).

**Как читать поля.** `teacherName` — фамилия, имя и отчество через пробел,
незаполненные части пропускаются. `weekNumber` — день недели, 1 (понедельник) … 6 (суббота).
`classTime` — номер пары, 1 … 8; соответствие номеров времени фиксировано:
1 — 8:30, 2 — 10:20, 3 — 12:20, 4 — 14:10, 5 — 16:00, 6 — 18:00, 7 — 19:40,
8 — 21:20. `group` — строка как в PDF: у лекции потоку это перечень групп через
запятую. `subgroup` — буква без скобок (`А`, `Б`) или `null`. `cabinet` — как
в расписании (`216`, `0804(КК)`, `ИГ-2`) или `null`, если аудитория не указана.

**Даты.** У каждого периода есть свой `id` — им удобно ключевать элементы
списка на клиенте; при переимпорте расписания идентификаторы меняются, поэтому
хранить их дольше одного ответа нельзя. `startDate` и `endDate` — в формате `ДД.ММ` **без года**: года нет
в исходном PDF, и восстановить его нечем. `endDate: null` означает разовое
занятие в `startDate`. `alternativelyPeriod: true` — занятие идёт через неделю
(в расписании это `ч.н.`), `false` — каждую неделю (`к.н.`). У одной пары
несколько периодов — норма.

**Импорт заменяет расписание целиком.** Прежние пары и даты преподавателя
удаляются, вместо них записываются разобранные из файла. Замена идёт одной
транзакцией: если разбор или сохранение упали, прежнее расписание остаётся
нетронутым.

Файл, из которого не удалось достать ни одного занятия, отклоняется с `400`
и прежнее расписание не трогает: иначе неверный PDF молча стирал бы расписание,
а восстановить его нечем — ручки удаления и правки в API нет.

Порядок пар в ответе импорта — тот, в котором они разобраны из PDF, а не тот,
в котором приходят из ручек чтения; полагаться на него не нужно.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | файл не выбран, пуст или больше 5 МБ; файл не удалось разобрать — причина в `detail` («в PDF не найдено ни одной таблицы расписания»); в файле нет ни одного занятия; поле занятия длиннее, чем позволяет база, — в `detail` указаны день, пара и поле |
| `401` | нет токена или он протух |
| `403` | роль ниже модератора |
| `404` | преподавателя с таким `id` нет |
| `409` | расписание этого преподавателя в тот же момент импортирует кто-то ещё; повторить попытку |
| `413` | файл больше 15 МБ — отклоняется контейнером до контроллера |
| `503` | микросервис разбора расписания недоступен, не ответил вовремя или вернул неполные данные |

Различать `400` и `503` важно: первое чинит человек, загрузивший файл (взять
правильный PDF), второе — администратор сервера, пользователю остаётся повторить
попытку позже.

Предел размера — 5 МБ, он проверяется до обращения к микросервису, поэтому
слишком большой файл не занимает ни сеть, ни время разбора. Файл крупнее 15 МБ
отклоняет сам контейнер (`413`, до контроллера дело не доходит), а запрос тяжелее
16 МБ он обрывает без ответа вовсе — на такой случай у клиента должна быть ветка
сетевой ошибки, а не разбор кода состояния.

## Импорт расписания экзаменов преподавателя

Отдельный документ и отдельная ручка. Расписание экзаменов приходит кафедральной
рассылкой — своим PDF, не тем, в котором пары. Разбирает его тот же микросервис,
но другим эндпоинтом, и файлы не взаимозаменяемы: расписание пар, отправленное
сюда, отклоняется с `400`, и наоборот.

`POST /api/teachers/{id}/exams/import` — `multipart/form-data`,
единственное поле `file` с PDF-файлом. Ответ `200`:

```json
{
  "teacherId": 3,
  "teacherName": "Ибатулин Марат Юрьевич",
  "exams": [
    {
      "id": 12,
      "date": "2025-05-15",
      "timeStart": "16:00",
      "timeEnd": "21:10",
      "group": "ИДБ-21-11",
      "name": "Применение методов машинного обучения в информационно обоснованных решениях",
      "cabinet": "308",
      "consultation": {"date": "2025-05-14", "time": "16:00", "cabinet": "308"}
    },
    {
      "id": 13,
      "date": "2025-05-14",
      "timeStart": "08:30",
      "timeEnd": "14:00",
      "group": "ИДБ-21-09",
      "name": "Системы интеллектуального анализа данных",
      "cabinet": "0402",
      "consultation": null
    }
  ]
}
```

**Как читать поля.** `date` — дата экзамена в ISO (`ГГГГ-ММ-ДД`); в отличие
от расписания пар год здесь есть, он написан в самом документе. `timeStart`
и `timeEnd` — `ЧЧ:ММ` с ведущим нулём. `group` — код группы; если экзамен
у нескольких групп, они перечислены через запятую, как в расписании пар.
`cabinet` — как в документе (`209`, `306(а)`, `0402`); скобка здесь литера
аудитории, а не подгруппа.

**Дня недели в ответе нет** — он полностью выводится из `date`, и хранить его
копию значило бы завести поле, способное разойтись с датой.

**`consultation` может быть `null`.** Во всех известных рассылках консультация
есть у каждого экзамена, но формат её отсутствие допускает. Половинчатой
консультации не бывает: либо объект со всеми тремя полями, либо `null` —
это же правило закреплено в базе ограничением. Дата консультации может попасть
в другой год, чем дата экзамена (консультация 28.12.2024 к экзамену 09.01.2025),
поэтому выводить год консультации из периода сессии нельзя.

**Импорт заменяет расписание экзаменов целиком** — как и у пар. Прежние экзамены
преподавателя удаляются, вместо них записываются разобранные из файла, всё одной
транзакцией: упавший разбор оставляет прежние данные нетронутыми. Расписание пар
этот импорт не трогает вовсе, это независимые данные.

Файл, из которого не удалось достать ни одного экзамена, отклоняется с `400`.

**Ошибки** — те же коды и та же логика, что у импорта расписания пар:

| Код | Когда |
|---|---|
| `400` | файл не выбран, пуст или больше 5 МБ; файл не удалось разобрать — причина в `detail` («в PDF не найдено ни одной таблицы экзаменов»); в файле нет ни одного экзамена; поле экзамена длиннее, чем позволяет база |
| `401` | нет токена или он протух |
| `403` | роль ниже модератора |
| `404` | преподавателя с таким `id` нет |
| `409` | расписание экзаменов этого преподавателя в тот же момент импортирует кто-то ещё |
| `413` | файл больше 15 МБ — отклоняется контейнером до контроллера |
| `503` | микросервис недоступен, не ответил вовремя или вернул неполные либо неразбираемые данные |

Не путать с `GET /api/public/exams/files` — та ручка отдаёт ссылки на PDF-файлы
из карточек преподавателей и к разобранным данным отношения не имеет
(раздел «Расписание экзаменов: ссылки на PDF из карточек ППС» ниже).

## Расписание экзаменов: публичное чтение

Две ручки без авторизации, устроенные так же, как чтение расписания пар:
одна отдаёт экзамены преподавателя, вторая — сводное по всем.

`GET /api/public/teachers/{id}/exams` — схема тела та же, что у ответа импорта
(`teacherId`, `teacherName`, `exams`). У преподавателя без загруженного
расписания экзаменов — `200` и пустой `exams`, а не `404`: страница
преподавателя открывается всегда, просто раздел пуст. Несуществующий `id` —
`404`.

`GET /api/public/exams` — массив таких же объектов, по одному на преподавателя.
Преподаватели, у которых экзаменов нет, в выдачу не попадают вовсе. Порядок —
по фамилии и имени; экзамены внутри — по дате и времени начала.

Фильтры:

```
GET /api/public/exams?teacherId=3&teacherId=7
GET /api/public/exams?group=ИДБ-21-10
GET /api/public/exams?teacherId=3&group=ИДБ-21-10
```

`teacherId` повторяемый, как у `/api/public/schedule`. `group` отбирает экзамены
по коду группы и выбрасывает из выдачи преподавателей, у которых после отбора
не осталось ни одного экзамена, — иначе список был бы полон пустых карточек.

**Как сравнивается группа.** У экзамена в поле `group` может стоять несколько
кодов через запятую (`«ИДБ-21-09, ИДБ-21-10»`) — так же, как у лекции потоку
в расписании пар. Фильтр сравнивает не строку целиком, а каждый код по
отдельности: `?group=ИДБ-21-10` найдёт и такой экзамен. Регистр не важен.
Неизвестная группа — пустой массив, а не `404`: справочника групп в базе нет,
и отличить опечатку от группы без экзаменов нечем.

Пустое значение (`?group=`) считается отсутствием фильтра — так клиент присылает
выбор «все группы».

## Расписание преподавателя: публичное чтение

`GET /api/public/teachers/{id}/schedule` — без авторизации, схема тела та же,
что у импорта выше.

Пары отсортированы по дню недели, затем по номеру пары, затем по `id`;
даты внутри пары — по `id`. Порядок задан на стороне базы, сортировать
повторно не нужно.

У преподавателя, чьё расписание ещё не загружали, ответ `200`:

```json
{"teacherId": 3, "teacherName": "Чеканин Владимир Алексеевич", "lessons": []}
```

Пустой список, а не `404`, — намеренно: «преподавателя нет» и «расписание
не загружено» требуют от интерфейса разного, и один код на оба случая эту
разницу стирает. `404` остаётся только за несуществующим `id`.

**Ошибки:**

| Код | Когда |
|---|---|
| `404` | преподавателя с таким `id` нет |

## Сводное расписание

`GET /api/public/schedule` — без авторизации. Отдаёт массив расписаний в той же
схеме, что и две ручки выше: одна схема на импорт, чтение одного преподавателя
и сводную выборку.

Без параметров приходят расписания всех преподавателей, у кого они загружены;
преподаватели без расписания в ответ не попадают — пустые объекты сводной сетке
не нужны. Порядок — по фамилии и имени преподавателя, пары внутри расписания —
как в одиночной ручке.

Фильтр — повторяемый параметр `teacherId`:

```
GET /api/public/schedule?teacherId=3&teacherId=7
```

Неизвестный `teacherId` не ошибка: он просто не даёт строк, и при полностью
неизвестном фильтре приходит `200` с пустым массивом. Отдельного кода для
«такого преподавателя нет» здесь нет намеренно — фильтр отбирает из того, что
есть, а не адресует конкретный ресурс.

Пагинации у этой ручки нет: страница сводного расписания показывает неделю
целиком, и порционная выдача ей ничего не даёт.

**Что фронт собирает из ответа.** `teacherName` приходит вместе с расписанием,
поэтому за списком ППС отдельно ходить не нужно: имени хватает и на легенду,
и на подпись пары. Даты по-прежнему в формате `ДД.ММ` без года, и разворачивать
период в конкретные занятия — работа клиента.

## Расписание экзаменов: ссылки на PDF из карточек ППС

Это не разобранные экзамены, а ссылки на файлы, которые модератор вписывает
в карточку преподавателя, — перенос того, как экзамены показывал старый портал.
Разобранные в данные экзамены живут в `GET /api/public/exams`
и `GET /api/public/teachers/{id}/exams`; путь `.../exams/files` назван так, чтобы
эти две вещи не путались.

`GET /api/public/exams/files` — без авторизации. Отдаёт массив преподавателей,
у которых заполнена хотя бы одна ссылка на PDF с расписанием экзаменов:

```json
[
  {
    "teacherId": 3,
    "teacherName": "Чеканин Владимир Алексеевич",
    "examScheduleGraduation": "https://stankin.ru/uploads/exams-graduation.pdf",
    "examScheduleNonGraduation": null
  }
]
```

Фильтр по типу курса — параметр `type` со значениями `GRADUATION`
и `NON_GRADUATION`:

```
GET /api/public/exams/files?type=GRADUATION
```

С фильтром приходят только те, у кого заполнена соответствующая ссылка;
без параметра — все, у кого заполнена хотя бы одна. Значение вне словаря даёт
`400`, пустое (`?type=`) считается отсутствием фильтра. В старом портале под
это были две отдельные ручки — `with-graduation-exam-schedule`
и `with-non-graduation-exam-schedule`; здесь один ресурс с фильтром, как
у новостей с `?postType=`.

Ссылки — те же поля, что и в детальной карточке ППС; отдельной сущности
расписания экзаменов нет. Незаполненная ссылка приходит как `null`, пустая
строка в базе считается незаполненной наравне с отсутствием значения.
Преподаватель, у которого пусты обе ссылки, в выдачу не попадает.
Порядок — по фамилии и имени, как у сводного расписания. Пагинации нет.

`teacherName` склеен из фамилии, имени и отчества — той же схемой, что и в
остальных ручках расписаний, поэтому за списком ППС ради подписи ходить
не нужно.

**Схема ссылки проверяется при сохранении карточки.** `POST /api/teachers`
и `PUT /api/teachers/{id}` принимают только `http`, `https` и относительный
путь внутри портала (`/media/exams/ivanov.pdf`); всё остальное — `javascript:`,
`data:`, `file:` и протокол-относительный `//host/file.pdf` — даёт `400`.
Причина в том, что страница экзаменов подставляет ссылку в `iframe`, и адрес
со схемой `javascript:` выполнился бы как код на публичной странице. Проверка
стоит на записи, а не на отдаче: ручек, отдающих эти поля, три, и фильтр
пришлось бы держать в каждой.

## Аспирантура

`GET /api/public/postgraduates` — без авторизации, постранично. Элемент списка:

```json
{
  "id": 12,
  "studentId": 34,
  "studentName": "Абрамов Пётр Сергеевич",
  "speciality": "2.3.1",
  "diplomaTheme": "Методы анализа промышленных данных",
  "admissionYear": 2024,
  "teacherId": 3,
  "teacherName": "Чеканин Владимир Алексеевич"
}
```

Порядок — по фамилии и имени аспиранта. Незаполненный руководитель приходит
как `null` в обоих полях (`teacherId` и `teacherName`), а не строкой-заглушкой:
подпись «не назначен» рисует интерфейс.

Фильтры, оба необязательные и совместимые друг с другом:

```
GET /api/public/postgraduates?teacherId=3&speciality=2.3.1
```

Пустое значение (`?speciality=`) считается отсутствием фильтра — так фронт
присылает несделанный выбор. Неизвестный `teacherId` не ошибка: приходит
`200` с пустой страницей.

Записи создаёт и правит модератор или администратор:

* `GET /api/postgraduates/{id}` — одна запись в составе полей формы правки;
* `POST /api/postgraduates` — `201`, заголовок `Location`, тело — созданная запись;
* `PUT /api/postgraduates/{id}` — `200`, запись после правки;
* `DELETE /api/postgraduates/{id}` — `204` без тела.

Тело запроса на создание и правку одинаковое: данные аспиранта вложены,
руководитель — идентификатором.

```json
{
  "student": {
    "lastName": "Абрамов",
    "firstName": "Пётр",
    "patronymic": "Сергеевич",
    "group": "ИДМ-24-01",
    "educationLevel": "POSTGRADUATE",
    "speciality": "2.3.1",
    "diplomaTheme": "Методы анализа промышленных данных",
    "admissionYear": 2024
  },
  "teacherId": 3
}
```

`GET /api/postgraduates/{id}` отдаёт ровно то, что принимает `PUT`, плюс `id`:

```json
{
  "id": 12,
  "student": {
    "lastName": "Абрамов",
    "firstName": "Пётр",
    "patronymic": null,
    "group": "ИДМ-24-01",
    "educationLevel": "POSTGRADUATE",
    "speciality": "2.3.1",
    "diplomaTheme": "Методы анализа промышленных данных",
    "admissionYear": 2024
  },
  "teacherId": 3
}
```

Состав полей совпадает с телом запроса не случайно: `PUT` — полная замена,
и форма правки собирается из этого ответа один в один. Публичный список для этого
не годится: ФИО там склеено в `studentName`, а группы нет вовсе — она не уходила
наружу и на старом портале. Ручка закрыта ролью модератора или администратора,
несуществующая запись даёт `404`.

Отдельной ручки у студентов нет: человек заводится вместе с записью
аспирантуры и удаляется вместе с ней. `educationLevel` — код закрытого словаря
(`BACHELOR`, `MASTER`, `POSTGRADUATE`, `SPECIALIST`), подписи рисует фронт,
как у `degree` и `rank` в карточке ППС.

Что даёт `400`: уровень образования, отличный от `POSTGRADUATE` (в записи
аспирантуры может состоять только аспирант — проверяется и при создании,
и при правке), год поступления в будущем или раньше 2000, неизвестный
`teacherId`. Несуществующая запись в пути даёт `404`.

Удаление карточки преподавателя не удаляет записи аспирантуры — у них
обнуляется руководитель, как у достижений кафедры.

## Научные публикации и теги

### Теги

`GET /api/public/tags` — без авторизации, массив по алфавиту:

```json
[ { "id": 4, "name": "Оптимизация" } ]
```

`POST /api/tags` (`201`, заголовок `Location`) и `DELETE /api/tags/{id}` (`204`) —
администратору или модератору. Имя обрезается по краям; повтор без учёта
регистра даёт `400`. Уникальность продублирована в схеме, поэтому два
одновременных запроса с одним именем дают `409`, а не вторую строку.

Удаление тега не трогает публикации — у них просто пропадает эта метка.

### Публикации

`GET /api/public/publications` — без авторизации, постранично, по убыванию года:

```json
{
  "id": 7,
  "name": "Методы упаковки в задачах раскроя",
  "authors": ["Чеканин В.А.", "Чеканин А.В."],
  "description": "…",
  "url": "https://elibrary.ru/item.asp?id=1",
  "file": "publications/2026/08/9f3c.pdf",
  "fileUrl": "/media/publications/2026/08/9f3c.pdf",
  "year": 2024,
  "source": "Вестник МГТУ «Станкин», №3",
  "pages": "45–52",
  "volN": "т. 12, № 3",
  "isbn": "978-5-00000-000-0",
  "tags": [ { "id": 4, "name": "Оптимизация" } ]
}
```

`GET /api/public/publications/{id}` отдаёт ту же схему одной карточкой,
несуществующий id — `404`.

`GET /api/public/publications/authors` — плоский массив уникальных авторов
по всем публикациям, по алфавиту:

```json
["Разумовский А.И.", "Чеканин А.В.", "Чеканин В.А."]
```

Он нужен фильтру: значение из этого списка подставляется в `?author=`.
Путь с литеральным `authors` не конфликтует с `{id}` — Spring выбирает
точное совпадение раньше переменной, и это закреплено тестом.

Фильтры, все необязательные и совместимые друг с другом:

```
GET /api/public/publications?tagId=4&author=Чеканин&year=2024
```

`author` — подстрока в списке авторов без учёта регистра, `tagId` — публикации
с этим тегом, `year` — точный год. Пустое значение считается отсутствием
фильтра.

`POST /api/publications`, `PUT /api/publications/{id}` и `DELETE /api/publications/{id}` —
администратору или модератору. Тело создания и правки:

```json
{
  "name": "Методы упаковки в задачах раскроя",
  "authors": ["Чеканин В.А."],
  "description": "…",
  "url": "https://elibrary.ru/item.asp?id=1",
  "file": "publications/2026/08/9f3c.pdf",
  "year": 2024,
  "source": "Вестник МГТУ «Станкин», №3",
  "pages": "45–52",
  "volN": "т. 12, № 3",
  "isbn": "978-5-00000-000-0",
  "tagIds": [4, 9]
}
```

`PUT` — полная замена, включая набор тегов: список `tagIds` заменяет прежний
целиком, а не дополняет его.

Что даёт `400`: пустой список авторов, неизвестный `tagId`, ключ файла,
которого нет в разделе `publications`, ссылка со схемой, отличной от `http`,
`https` или относительного пути (`javascript:` в поле `url` — тот же риск,
что и у ссылок на расписание экзаменов, проверка та же).

**Файл.** `file` — ключ в хранилище, `fileUrl` — готовый адрес для скачивания;
ключ отдаётся потому, что его же принимает форма правки. В старом портале PDF
лежал прямо в базе строкой base64 и уезжал в каждом элементе списка — здесь он
лежит в хранилище, как обложки новостей.

Сам файл загружается заранее через `POST /api/files` с `category=publications`,
ответ отдаёт ключ, который и кладётся в поле `file`. В этом разделе принимается
только PDF, в остальных — только изображения; тип определяется по содержимому
файла, а не по расширению или заголовку запроса. Не-PDF в разделе публикаций
и PDF в разделе новостей одинаково дают `400`.

## Календарь событий

Раздел доступен только преподавателю и администратору: остальным ролям
приходит `403`, анониму — `401`. Событие видят владелец и назначенные на него,
и никто больше — администратор не исключение, чужой календарь ему не
показывается.

`GET /api/events` — постранично, по возрастанию начала:

```json
{
  "id": 12,
  "name": "Заседание кафедры",
  "description": "Обсуждение нагрузки на весенний семестр",
  "startedAt": "2026-09-01T10:00:00+03:00",
  "endedAt": "2026-09-01T11:30:00+03:00",
  "allDay": false,
  "color": "#3F51B5",
  "status": "NOT_STARTED",
  "notificationFrequency": "WEEKLY",
  "nextNotificationAt": null,
  "owner": { "id": 3, "firstName": "Владимир", "lastName": "Чеканин" },
  "assignedUsers": [
    { "id": 5, "firstName": "Анна", "lastName": "Абрамова" }
  ]
}
```

В выдачу попадают события, где пользователь владелец **или** назначенный.
Одно событие приходит один раз, даже если он и владелец, и назначенный.

**Логина в карточках владельца и назначенных нет** — только `id` и ФИО. Список
учётных записей закрыт ролью администратора (`GET /api/users`), а календарь
доступен любому преподавателю: с `username` в ответе перебор `assignedUserIds`
выгружал бы логины всего портала в обход этой проверки (T-54b). Для подписи
в интерфейсе достаточно имени, для формы правки — `id`.

Идентификаторы для `assignedUserIds` берутся из справочника
`GET /api/users/directory` — он отдаёт учётки преподавателей в том же составе
полей (`id` и ФИО) и открыт той же роли, что и календарь.

Фильтр `?status=` принимает `NOT_STARTED`, `IN_PROGRESS` или `COMPLETED`.
Значение вне словаря — `400`; пустое (`?status=`) считается отсутствием фильтра.

`GET /api/events/{id}` отдаёт ту же карточку. Чужое событие даёт `404`, а не
`403`: существование чужой записи наружу не подтверждается.

`POST /api/events` (`201`, заголовок `Location`), `PUT /api/events/{id}` и
`DELETE /api/events/{id}` (`204`). Тело создания и правки:

```json
{
  "name": "Заседание кафедры",
  "description": "Обсуждение нагрузки на весенний семестр",
  "startedAt": "2026-09-01T10:00:00+03:00",
  "endedAt": "2026-09-01T11:30:00+03:00",
  "allDay": false,
  "color": "#3F51B5",
  "status": "NOT_STARTED",
  "notificationFrequency": "WEEKLY",
  "assignedUserIds": [5, 7]
}
```

Обязательны все поля, кроме `description` и `assignedUserIds`. `PUT` — полная
замена, включая список назначенных: он заменяет прежний целиком, а не
дополняет его.

**Владелец берётся из токена.** Поля `user` и `owner` в теле игнорируются —
подставить чужую учётную запись владельцем нельзя ни при создании, ни при
правке. В назначенных владелец автоматически не появляется: кто получит
напоминания, задаёт только `assignedUserIds`.

Править и удалять событие может владелец и любой назначенный — так же, как
в старом портале: назначенный отмечает свою часть работы сменой `status`.

Что даёт `400`: дата окончания раньше даты начала (равные — допустимы), цвет
не вида `#RRGGBB` (ровно семь символов: решётка и шесть шестнадцатеричных
цифр), неизвестный id в `assignedUserIds`, значение вне словаря в `status`
или `notificationFrequency`, отсутствие обязательного поля.

**Поля планировщика.** `nextNotificationAt` — только для чтения; его двигает
планировщик напоминаний (модуль 19), через API оно не задаётся и при правке
события не сбрасывается. Внутренний признак «уведомление о старте отправлено»
наружу не отдаётся вовсе.

Отличия от старого портала, которые видит клиент:

- вместо `PATCH` — `PUT`, полная замена, как во всём остальном API;
- значения `status` и `notificationFrequency` — латиницей в верхнем регистре
  (`NOT_STARTED` вместо `not_started`); регистр раскладывает скрипт переноса данных;
- `assignedUserIds` принимается от всех: в оригинале запрос преподавателя молча
  подменялся на «назначить самого себя», и назначить коллегу было нельзя;
- `status` берётся из тела и при создании — оригинал молча ставил `not_started`;
- список постраничный, в оригинале приходил целиком.

## Пагинация списков

`GET /api/public/news`, `GET /api/news`, `GET /api/public/teachers`,
`GET /api/public/helpers`, `GET /api/public/conferences`,
`GET /api/conferences`, `GET /api/public/achievements`,
`GET /api/public/teachers/{teacherId}/achievements`, `GET /api/achievements`,
`GET /api/public/postgraduates`, `GET /api/public/publications`,
`GET /api/events`, `GET /api/subjects` и `GET /api/pages`
отдают не массив, а объект-страницу:

```json
{
  "content": [ ... ],
  "page": 0,
  "size": 20,
  "totalElements": 137,
  "totalPages": 7
}
```

`content` — элементы текущей страницы (схема элемента — в Swagger),
`page` — номер страницы, **счёт с нуля**, `totalElements` — сколько элементов
всего с учётом фильтров, `totalPages` — сколько всего страниц при текущем `size`.

Управление — query-параметрами, все необязательны:

| Параметр | По умолчанию | Пример |
|---|---|---|
| `page` | `0` | `?page=2` — третья страница |
| `size` | `20` | `?size=5`, максимум `100` |
| `sort` | у каждого эндпоинта свой, см. ниже | `?sort=title,asc` |
| `postType` | нет фильтра | `?postType=announcements` — только у списков новостей, см. «Новости: фильтр по типу записи» |

Сортировка по умолчанию: новости, конференции и достижения — по `createdAt`
по убыванию (новые сверху); преподаватели и УВП — по фамилии, затем имени по алфавиту;
дисциплины — по `name`; разделы (`GET /api/pages`) — по `id`; события календаря —
по `startedAt` по возрастанию, ближайшие сверху, и размер страницы там по умолчанию
не `20`, а `50`: месяц календаря не должен обрезаться на первой странице. Последним ключом
сортировки везде идёт уникальное поле: без него порядок записей с одинаковой датой
или фамилией не определён, и при листании одна запись приходила бы дважды,
а другая не приходила бы вовсе. Если запрошенная страница
за пределами данных, приходит `200` с пустым `content` — это не ошибка.
Передача в `sort` несуществующего поля — `400` с `ProblemDetail`, в `detail`
указано имя неизвестного поля; фронту слать только поля из схемы.

**`size` ограничен сотней сверху**, и запрошенный больший размер молча
урезается до неё: ошибки не будет, но в ответе придут `size: 100` и своя
`totalPages`. Ограничение нужно потому, что списки новостей, конференций
и достижений несут `content` целиком, и одна страница на тысячу записей —
это десятки мегабайт по одному анонимному запросу (T-54d). Клиенту,
которому нужно больше сотни записей, следует листать страницы.
