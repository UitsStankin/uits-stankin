# Контракт API для фронтенда

> Актуально на 2026-08-17. Источник правды по эндпоинтам и схемам —
> **Swagger UI** запущенного бэкенда: `http://localhost:8080/swagger-ui/index.html`
> (сырая спека — `/v3/api-docs`). Этот документ описывает то, чего в Swagger нет:
> соглашения, формат ошибок и планируемые изменения контракта.

## Базовое

* Base URL локально — `http://localhost:8080`. Все пути начинаются с `/api`.
* Все тела запросов и ответов — JSON, имена полей — **camelCase**.
* Тестовые логины и пароли — в [backend/README.md](../backend/README.md),
  раздел «Тестовые данные».

## Аутентификация

1. `POST /api/users/auth/login` с телом `{"username": "...", "password": "..."}`.
2. В ответе — `{"accessToken": "<JWT>"}`. Токен живёт 24 часа.
3. Токен передаётся в каждом запросе к закрытым эндпоинтам заголовком
   `Authorization: Bearer <JWT>`.
4. Ответ **401** от любого эндпоинта означает «токен отсутствует, протух или
   невалиден»: токен стереть, пользователя отправить на страницу логина.

Refresh-токена пока нет — после истечения суток пользователь логинится заново.
Cookie не используются, поэтому CORS-режим `credentials` фронту не нужен.

## Формат ошибок

Любая ошибка — [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457),
`Content-Type: application/problem+json`:

```json
{
  "title": "Unauthorized",
  "status": 401,
  "detail": "Требуется аутентификация.",
  "instance": "/api/users/profile",
  "timestamp": "2026-07-28T16:10:39.141549900Z"
}
```

Поля `type` в ответах нет: по RFC 9457 его значение по умолчанию —
`about:blank`, и Spring такое значение не сериализует. Появится оно только
вместе с собственными типами ошибок, если они когда-нибудь понадобятся.

Поля `instance` (путь запроса) и `timestamp` заполняются во всех ошибках,
включая 401 из JWT-фильтра (нет токена / битый токен / заблокированный
или удалённый пользователь) и ошибку валидации формы.

Ошибка валидации формы дополнительно несёт словарь `errors`
(имя поля → список сообщений, пригодных для показа пользователю):

```json
{
  "title": "Ошибка валидации",
  "status": 400,
  "detail": "Ошибка валидации.",
  "instance": "/api/users/change-password",
  "timestamp": "2026-07-28T16:10:39.141549900Z",
  "errors": {
    "newPassword": ["Пароль должен быть минимум 8 символов", "Новый пароль обязателен"]
  }
}
```

На одно поле может прийти несколько сообщений — порядок в списке
не гарантирован, полагаться на него нельзя.

Семантика статусов:

| Статус | Значение | Реакция фронта |
|---|---|---|
| 400 | невалидные данные формы (`errors`) или неверный старый пароль при смене | показать ошибки у полей |
| 401 | нет/протух токен; неверные логин-пароль на `/login` | стереть токен, на страницу логина (на самой форме логина — «неверный логин или пароль») |
| 403 | пользователь узнан, но прав не хватает | показать «недостаточно прав», на логин не уводить |
| 404 | ресурс не найден | страница/плашка «не найдено» |
| 409 | конфликт данных | показать сообщение, предложить повторить |
| 500 | ошибка сервера | общая плашка ошибки; это баг бэкенда, о нём сообщать |

Важно: `/login` с несуществующим логином и с неверным паролем отвечает
**одинаково** (401, «Неверный логин или пароль.») — это сделано намеренно,
чтобы не раскрывать, какие логины существуют.

## Эндпоинты

| Метод и путь | Токен | Ответ |
|---|---|---|
| `POST /api/users/auth/login` | — | `{"accessToken": "..."}` |
| `GET /api/public/news` | — | страница новостей (только `display=true`, новые сверху) |
| `GET /api/public/teachers` | — | страница карточек преподавателей (по алфавиту фамилий) |
| `GET /api/users/profile` | да | профиль текущего пользователя |
| `POST /api/users/change-password` | да | `200` с пустым телом |
| `GET /api/public/news/{id}` | — | одна новость; скрытая или несуществующая — `404` |
| `GET /api/news` | да, роль админа или модератора | страница всех новостей, включая скрытые |
| `GET /api/news/{id}` | да, роль админа или модератора | одна новость, включая скрытую |
| `POST /api/news` | да, роль админа или модератора | `201`, заголовок `Location`, тело — созданная новость |
| `PUT /api/news/{id}` | да, роль админа или модератора | `200`, тело — новость после правки |
| `DELETE /api/news/{id}` | да, роль админа или модератора | `204` без тела |
| `POST /api/files` | да, роль админа или модератора | `201`, тело — `{"key": "...", "url": "..."}` |
| `GET /media/{key}` | — | сам файл; отдаётся как статика |
| `GET /actuator/health` | — | `{"status":"UP"}` — служебный, для деплоя и мониторинга |

Схемы тел — в Swagger. **Swagger доступен только вне прод-профиля**: на боевом
стенде `/swagger-ui/**` и `/v3/api-docs` отвечают `404`, чтобы не раздавать
карту API наружу. Локально и на dev-стенде всё как прежде.

Нюансы, которые из Swagger не видны:

* незаполненные поля приходят как `null` (например, `avatar`,
  `previewImage`) — фронт должен это ожидать;
* `createdAt` — ISO-8601 со смещением, например `2026-07-24T10:15:30.123456+04:00`;
* `postType` новости — `news` или `announcements`;
* булевы поля профиля называются `teacher`, `moderator`, `superuser` — без
  префикса `is`;
* у новости два поля про обложку: `previewImage` — ключ файла, `previewImageUrl` —
  готовый адрес для показа; подробности в разделе «Обложка новости».

## Новости: создание, правка, удаление

`POST /api/news` отвечает **201** и кладёт путь созданной новости в заголовок
`Location` (`/api/news/{id}`); тело ответа — та же новость, включая `id`.
Прежнее «200 с пустым телом» больше не приходит.

`PUT /api/news/{id}` — **полная замена** состояния новости, а не частичное
обновление. Поле, не пришедшее в теле запроса, обнуляется: форма редактирования
обязана отправлять все поля, включая незатронутые. Валидация та же, что
у создания.

`DELETE /api/news/{id}` удаляет новость физически и отвечает **204** без тела.
Скрыть новость, не удаляя, — это `PUT` с `display: false`.

Удаление и правка несуществующей новости дают `404`. Скрытая новость
(`display: false`) для публичных эндпоинтов неотличима от несуществующей —
тоже `404`, а не `403`: иначе перебором `id` можно было бы пересчитать
неопубликованные черновики.

В теле новости есть поле `display` — оно нужно админскому списку, чтобы
отличать опубликованные новости от скрытых. В публичной выдаче там всегда `true`.

## Загрузка файлов

Файлы загружаются отдельным запросом, до сохранения сущности. Причина в rich-text:
картинка внутри `content` существует как `<img src="...">`, то есть адрес нужен
редактору в момент вставки, за несколько минут до нажатия «Сохранить». Обложка
(`previewImage`) идёт через ту же ручку, чтобы механизм был один.

**Запрос** — `POST /api/files`, `Content-Type: multipart/form-data`, две части:

| Часть | Обязательна | Значение |
|---|---|---|
| `file` | да | сам файл |
| `category` | нет, по умолчанию `news` | раздел хранилища: `news`, `avatars`, `publications` |

**Ответ** — `201`:

```json
{
  "key": "news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "url": "/media/news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg"
}
```

* `key` — то, что отправляется в `previewImage` при создании или правке новости
  и хранится в базе. Формат ключа — деталь бэкенда, разбирать его на фронте не нужно.
* `url` — адрес для показа: подставляется в `<img src>` для предпросмотра сразу
  после загрузки и в `content` при вставке картинки в текст. Адрес относительный,
  без домена: браузер достроит его от текущего origin.

**Ограничения.** Принимаются только JPEG и PNG размером до 15 МБ. Формат
определяется по содержимому файла, а не по расширению и не по `Content-Type`:
переименованный `.exe` получит `400`. WebP, GIF и SVG отклоняются — последний
принципиально, поскольку SVG может содержать исполняемый код.

**Что происходит с файлом.** Изображение перекодируется и, если превышает
1600 пикселей по стороне, уменьшается с сохранением пропорций; меньшие не
растягиваются. Перекодирование удаляет EXIF, включая координаты съёмки.
JPEG остаётся JPEG, PNG остаётся PNG — прозрачность не теряется. Загруженный
файл на диске отличается от исходного, и сравнивать их размеры бессмысленно.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | не изображение, неподдерживаемый формат, пустой файл, неизвестная `category` |
| `401` | нет токена или он протух |
| `403` | токен есть, но роль не админ и не модератор |
| `413` | файл больше допустимого размера |

В `detail` — человекочитаемая причина, её можно показывать пользователю.

**Раздача.** `GET /media/{key}` открыт всем и токена не требует: картинки видны
посетителям сайта. Метод только `GET`.

**Сироты.** Файл, загруженный, но не сохранённый ни в одной сущности (модератор
передумал и закрыл форму), остаётся на диске. Автоматической чистки пока нет,
удалять его с фронта не нужно.

## Обложка новости

За обложку отвечают три поля:

| Поле | Направление | Значение |
|---|---|---|
| `previewImage` | запрос и ответ | ключ файла в хранилище — тот, что вернул `POST /api/files` |
| `previewImageUrl` | только ответ | готовый адрес картинки для `<img src>` |
| `previewImageDescription` | запрос и ответ | текст для атрибута `alt` |

Отправляется **ключ**, показывается **адрес**. Собирать адрес на фронте не нужно
и не следует: правило сборки — деталь бэкенда, и при переносе файлов на объектное
хранилище или CDN изменится только `previewImageUrl`, а `previewImage` и код клиента
останутся прежними. Форма редактирования отправляет обратно тот же `previewImage`,
который пришёл в ответе.

Обложки может не быть — тогда все три поля приходят как `null`.

**Проверка ключа.** Ключ проверяется при создании и при правке новости. Если файла
по нему в хранилище нет, приходит `400` с текстом «Файл обложки не найден: ...»,
и новость не создаётся и не изменяется. Тот же `400` — на ключ, уводящий за пределы
хранилища. Практический вывод для клиента: `previewImage` заполняется значением
из ответа `POST /api/files`, а не собирается руками.

**Уборка файлов.** Файл, переставший быть обложкой, удаляется с диска: при замене
картинки на другую, при снятии обложки и при удалении новости. Правка новости
без смены обложки файл не трогает. Удаление происходит после успешного сохранения,
поэтому неудачный запрос картинку не портит.

## Пагинация списков

`GET /api/public/news`, `GET /api/news` и `GET /api/public/teachers` отдают не массив,
а объект-страницу:

```json
{
  "content": [ ... ],
  "page": 0,
  "size": 20,
  "totalElements": 137,
  "totalPages": 7
}
```

`content` — элементы текущей страницы (схема элемента — в Swagger),
`page` — номер страницы, **счёт с нуля**, `totalElements` — сколько элементов
всего с учётом фильтров, `totalPages` — сколько всего страниц при текущем `size`.

Управление — query-параметрами, все необязательны:

| Параметр | По умолчанию | Пример |
|---|---|---|
| `page` | `0` | `?page=2` — третья страница |
| `size` | `20` | `?size=5` |
| `sort` | у каждого эндпоинта свой, см. ниже | `?sort=title,asc` |

Сортировка по умолчанию: новости — по `createdAt` по убыванию (новые сверху);
преподаватели — по фамилии, затем имени по алфавиту. Если запрошенная страница
за пределами данных, приходит `200` с пустым `content` — это не ошибка.
Передача в `sort` несуществующего поля — `400` с `ProblemDetail`, в `detail`
указано имя неизвестного поля; фронту слать только поля из схемы.
