# Контракт API для фронтенда

> Актуально на 2026-08-27. Источник правды по эндпоинтам и схемам —
> **Swagger UI** запущенного бэкенда: `http://localhost:8080/swagger-ui/index.html`
> (сырая спека — `/v3/api-docs`). Этот документ описывает то, чего в Swagger нет:
> соглашения, формат ошибок и планируемые изменения контракта.

## Базовое

* Base URL локально — `http://localhost:8080`. Все пути начинаются с `/api`.
* Все тела запросов и ответов — JSON, имена полей — **camelCase**.
* Поле тела запроса, которого нет в схеме, молча игнорируется: форма может
  отправлять обратно объект из ответа целиком (вместе с `id` и `createdAt`),
  это не ошибка.
* Пустая или пробельная строка в строковом поле тела равносильна отсутствию
  значения: сервер превращает её в `null` до валидации, поэтому конвертировать
  пустые поля формы в `null` на клиенте не нужно. Исключение одно — `text`
  раздела, где пустая строка означает «очистить раздел»
  (см. «Редактируемые страницы»).
* Тестовые логины и пароли — в [backend/README.md](../backend/README.md),
  раздел «Тестовые данные».

## Аутентификация

Работают два токена с разным сроком жизни: короткий access в теле ответа
и длинный refresh в httpOnly-cookie.

1. `POST /api/users/auth/login` с телом `{"username": "...", "password": "..."}`.
2. В ответе — `{"accessToken": "<JWT>"}` и заголовок `Set-Cookie` с refresh-токеном.
   Access живёт **15 минут**, refresh — **14 дней**.
3. Access передаётся в каждом запросе к закрытым эндпоинтам заголовком
   `Authorization: Bearer <JWT>` и хранится в памяти вкладки. В `localStorage`
   он переживает закрытие вкладки и доступен любому скрипту страницы —
   ради этого refresh и вынесен в cookie, которую JS не видит.
4. Refresh-токен хранит и отправляет сам браузер. Cookie помечена `HttpOnly`,
   `SameSite=Lax`, `Path=/api/users/auth` — она уезжает только на ручки блока
   `auth` (`login`, `refresh`, `logout`), в обычных запросах её нет. На `login`
   сервер присланную cookie не читает и всегда выдаёт новую сессию.
5. `POST /api/users/auth/refresh` без тела: в ответе новый `accessToken`
   и новая cookie взамен прежней; прежний refresh-токен гасится.
6. `POST /api/users/auth/logout` без тела закрывает сессию на сервере
   и стирает cookie, ответ — `204`.

Запросы к `refresh` и `logout` обязаны идти с `credentials: "include"`
(в axios — `withCredentials: true`), иначе браузер cookie не приложит. CORS
на бэкенде этот режим разрешает, но только для origin'ов из белого списка.

Реакция на **401**: от закрытого эндпоинта — один раз сходить на `refresh`
и повторить запрос; от самого `refresh` — сессии больше нет, на страницу
логина. Повторный `refresh` в ответ на 401 от `refresh` даёт бесконечный цикл.

Повторное использование уже обменянного refresh-токена сервер считает кражей
и гасит всю цепочку токенов этой сессии: разлогинены оказываются оба
её держателя, вернуться можно только по паролю. Обмен одним и тем же токеном
дважды в пределах минуты кражей не считается — это гонка двух вкладок.

Смена пароля закрывает все сессии учётной записи и обрывает выданные ранее
access-токены, не дожидаясь их истечения.

## Формат ошибок

Любая ошибка — [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457),
`Content-Type: application/problem+json`:

```json
{
  "title": "Unauthorized",
  "status": 401,
  "detail": "Требуется аутентификация.",
  "instance": "/api/users/profile",
  "timestamp": "2026-07-28T16:10:39.141549900Z"
}
```

Поля `type` в ответах нет: по RFC 9457 его значение по умолчанию —
`about:blank`, и Spring такое значение не сериализует. Появится оно только
вместе с собственными типами ошибок, если они когда-нибудь понадобятся.

Поля `instance` (путь запроса) и `timestamp` заполняются во всех ошибках,
включая 401 из JWT-фильтра (нет токена / битый токен / заблокированный
или удалённый пользователь) и ошибку валидации формы.

Ошибка валидации формы дополнительно несёт словарь `errors`
(имя поля → список сообщений, пригодных для показа пользователю):

```json
{
  "title": "Ошибка валидации",
  "status": 400,
  "detail": "Ошибка валидации.",
  "instance": "/api/users/change-password",
  "timestamp": "2026-07-28T16:10:39.141549900Z",
  "errors": {
    "newPassword": ["Пароль должен быть минимум 8 символов", "Новый пароль обязателен"]
  }
}
```

На одно поле может прийти несколько сообщений — порядок в списке
не гарантирован, полагаться на него нельзя.

Семантика статусов:

| Статус | Значение | Реакция фронта |
|---|---|---|
| 400 | невалидные данные формы (`errors`) или неверный старый пароль при смене | показать ошибки у полей |
| 401 | нет/протух access-токен; неверные логин-пароль на `/login` | один раз сходить на `/api/users/auth/refresh` и повторить запрос; на логин уводить, только если 401 пришёл от самого `refresh` (подробный порядок — в разделе «Аутентификация»). На форме логина — «неверный логин или пароль» |
| 403 | пользователь узнан, но прав не хватает | показать «недостаточно прав», на логин не уводить |
| 404 | ресурс не найден | страница/плашка «не найдено» |
| 409 | конфликт данных | показать сообщение, предложить повторить |
| 429 | слишком много попыток входа с одного адреса | показать «повторите позже»; сколько ждать — в заголовке `Retry-After`, в секундах |
| 500 | ошибка сервера | общая плашка ошибки; это баг бэкенда, о нём сообщать |

Важно: `/login` с несуществующим логином и с неверным паролем отвечает
**одинаково** (401, «Неверный логин или пароль.») — это сделано намеренно,
чтобы не раскрывать, какие логины существуют.

**Роли.** Их четыре: `admin` (суперпользователь), `moderator`, `teacher`
и обычный `user`. Права сегодня даёт только пара админ/модератор —
управление всем контентом из таблицы выше: новостями, конференциями,
достижениями, разделами, карточками ППС и УВП, дисциплинами и файлами; между собой
эти две роли не различаются нигде. Роль `teacher` открывает ровно две ручки — `GET` и `PUT`
`/api/teachers/me`, свою карточку ППС; на всех остальных закрытых ручках
преподаватель получает `403` наравне с обычным пользователем.

Отказы различаются: без токена или с негодным токеном приходит `401`,
с исправным токеном и недостаточной ролью — `403`. Колонка «кому доступно»
проверяется целиком, ручка × роль, в `EndpointAccessMatrixTest`; таблица
в этом тесте и есть источник правды, а ручка, которой в ней нет, роняет сборку.

Схемы тел — в Swagger. **Swagger доступен только вне прод-профиля**: на боевом
стенде `/swagger-ui/**` и `/v3/api-docs` отвечают `404`, чтобы не раздавать
карту API наружу. Локально и на dev-стенде всё как прежде.

Нюансы, которые из Swagger не видны:

* незаполненные поля приходят как `null` (например, `avatar`,
  `previewImage`) — фронт должен это ожидать;
* `createdAt` — ISO-8601 со смещением, например `2026-07-24T10:15:30.123456+04:00`;
* `postType` новости — `news` или `announcements`;
* булевы поля профиля называются `teacher`, `moderator`, `superuser` — без
  префикса `is`;
* у новости и у объявления о конференции три поля про обложку:
  `previewImage` — ключ файла, `previewImageUrl` — готовый адрес для показа,
  `previewImageDescription` — текст для `alt`; подробности в разделе
  «Обложка новости».

## Профиль пользователя

`GET /api/users/profile` отдаёт карточку текущего пользователя:

```json
{
  "id": 42,
  "username": "prof_ivanov",
  "firstName": "Иван",
  "lastName": "Иванов",
  "email": "ivanov@stankin.ru",
  "avatar": "avatars/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "avatarUrl": "/media/avatars/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "teacher": true,
  "moderator": false,
  "superuser": false
}
```

`avatar` — ключ файла, он же отправляется обратно при правке; `avatarUrl` — адрес
для `<img src>`. У пользователя без аватара оба поля приходят как `null`.

**Правка** — `PUT /api/users/profile`. Тело:

| Поле | Обязательно | Значение |
|---|---|---|
| `firstName` | нет | имя, до 150 символов |
| `lastName` | нет | фамилия, до 150 символов |
| `avatar` | нет | ключ файла из раздела `avatars` |

Ответ — `200` и профиль целиком, в том же виде, что у `GET`.

**Запрос заменяет карточку целиком.** Поле, которого в теле нет или которое пришло
как `null`, очищается: `PUT` с одним лишь `avatar` сотрёт имя и фамилию. Форма правки
обязана отправлять все три поля, включая неизменённые.

**Что этой ручкой не меняется:** логин, почта, telegram-код и флаги ролей. Такие поля
в теле игнорируются молча — запрос остаётся успешным, значения в базе не меняются.
Смена логина и почты из личного кабинета не предусмотрена вовсе.

Пустая строка в любом из трёх полей равносильна `null` — этим занимается общая
нормализация тела запроса, описанная в «Базовом».

**Аватар.** Сначала `POST /api/files` с `category: avatars`, затем `key` из ответа
уходит в поле `avatar`. Ключ обязан указывать на существующий файл раздела `avatars`:
ключ чужого раздела отвергается с `400`, даже если такой файл существует. Прежний файл
удаляется с диска после успешного сохранения; `avatar: null` очищает аватар и тоже
удаляет файл.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | имя или фамилия длиннее 150 символов — со словарём `errors`; ключ аватара не найден в разделе `avatars` — с причиной в `detail` |
| `401` | нет токена или он протух |

## Новости: создание, правка, удаление

`POST /api/news` отвечает **201** и кладёт путь созданной новости в заголовок
`Location` (`/api/news/{id}`); тело ответа — та же новость, включая `id`.
Прежнее «200 с пустым телом» больше не приходит.

`PUT /api/news/{id}` — **полная замена** состояния новости, а не частичное
обновление. Поле, не пришедшее в теле запроса, обнуляется: форма редактирования
обязана отправлять все поля, включая незатронутые. Валидация та же, что
у создания.

`DELETE /api/news/{id}` удаляет новость физически и отвечает **204** без тела.
Скрыть новость, не удаляя, — это `PUT` с `display: false`.

Удаление и правка несуществующей новости дают `404`. Скрытая новость
(`display: false`) для публичных эндпоинтов неотличима от несуществующей —
тоже `404`, а не `403`: иначе перебором `id` можно было бы пересчитать
неопубликованные черновики.

В теле новости есть поле `display` — оно нужно админскому списку, чтобы
отличать опубликованные новости от скрытых. В публичной выдаче там всегда `true`.

**Текст чистится от небезопасной разметки**, и проверка обязательности выполняется
по результату чистки: тело, от которого после удаления скриптов ничего не осталось
(`<script>alert(1)</script>`), даёт `400` со словарём `errors` по полю `content`,
а не сохранённую новость с пустым текстом. То же правило у содержания достижения.

## Загрузка файлов

Файлы загружаются отдельным запросом, до сохранения сущности. Причина в rich-text:
картинка внутри `content` существует как `<img src="...">`, то есть адрес нужен
редактору в момент вставки, за несколько минут до нажатия «Сохранить». Обложка
(`previewImage`) идёт через ту же ручку, чтобы механизм был один.

**Запрос** — `POST /api/files`, `Content-Type: multipart/form-data`, две части:

| Часть | Обязательна | Значение |
|---|---|---|
| `file` | да | сам файл |
| `category` | нет, по умолчанию `news` | раздел хранилища: `news`, `avatars`, `publications`, `achievements` |

Права зависят от раздела: `avatars` открыт любому авторизованному — свой аватар
меняет владелец учётной записи, а не редактор. Остальные разделы остаются за
админом и модератором: содержимое портала наполняют они.

**Ответ** — `201`:

```json
{
  "key": "news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg",
  "url": "/media/news/2026/08/a3f9c1d2-4b7e-11f0-9c3a-0242ac120002.jpg"
}
```

* `key` — то, что отправляется в `previewImage` при создании или правке новости
  и хранится в базе. Формат ключа — деталь бэкенда, разбирать его на фронте не нужно.
  Ключ принимается только тем полем, чей раздел совпадает с разделом загрузки:
  обложки новостей и конференций — из `news`, обложки достижений — из `achievements`,
  аватары — из `avatars`. Ключ существующего файла из чужого раздела даёт `400`.
* `url` — адрес для показа: подставляется в `<img src>` для предпросмотра сразу
  после загрузки и в `content` при вставке картинки в текст. Адрес относительный,
  без домена: браузер достроит его от текущего origin.

**Ограничения.** Принимаются только JPEG и PNG размером до 15 МБ. Формат
определяется по содержимому файла, а не по расширению и не по `Content-Type`:
переименованный `.exe` получит `400`. WebP, GIF и SVG отклоняются — последний
принципиально, поскольку SVG может содержать исполняемый код.

**Что происходит с файлом.** Изображение перекодируется и, если превышает
1600 пикселей по стороне, уменьшается с сохранением пропорций; меньшие не
растягиваются. Перекодирование удаляет EXIF, включая координаты съёмки.
JPEG остаётся JPEG, PNG остаётся PNG — прозрачность не теряется. Загруженный
файл на диске отличается от исходного, и сравнивать их размеры бессмысленно.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | не изображение, неподдерживаемый формат, пустой файл, неизвестная `category` |
| `401` | нет токена или он протух |
| `403` | раздел не `avatars`, а роль не админ и не модератор |
| `413` | файл больше допустимого размера |

В `detail` — человекочитаемая причина, её можно показывать пользователю.

**Раздача.** `GET /media/{key}` открыт всем и токена не требует: картинки видны
посетителям сайта. Метод только `GET`.

**Один файл у нескольких записей.** Один и тот же `key` можно поставить обложкой
нескольким записям — например, повторно выбрав уже загруженную картинку. Файл
удаляется с диска только вместе с последней ссылкой на него: правка или удаление
одной записи не ломает картинку у остальных.

**Сироты.** Файл, загруженный, но не сохранённый ни в одной сущности (модератор
передумал и закрыл форму), остаётся на диске. Автоматической чистки пока нет,
удалять его с фронта не нужно.

## Обложка новости

За обложку отвечают три поля:

| Поле | Направление | Значение |
|---|---|---|
| `previewImage` | запрос и ответ | ключ файла в хранилище — тот, что вернул `POST /api/files` |
| `previewImageUrl` | только ответ | готовый адрес картинки для `<img src>` |
| `previewImageDescription` | запрос и ответ | текст для атрибута `alt` |

Отправляется **ключ**, показывается **адрес**. Собирать адрес на фронте не нужно
и не следует: правило сборки — деталь бэкенда, и при переносе файлов на объектное
хранилище или CDN изменится только `previewImageUrl`, а `previewImage` и код клиента
останутся прежними. Форма редактирования отправляет обратно тот же `previewImage`,
который пришёл в ответе.

Обложки может не быть — тогда все три поля приходят как `null`.

**Проверка ключа.** Ключ проверяется при создании и при правке новости. Если файла
по нему в хранилище нет, приходит `400` с текстом «Файл обложки не найден: ...»,
и новость не создаётся и не изменяется. Тот же `400` — на ключ, уводящий за пределы
хранилища. Пустая строка ключом не считается: по правилу из «Базового» она
равносильна `null`, то есть снятию обложки, — а снятие удаляет старый файл. Практический вывод для клиента: `previewImage` заполняется значением
из ответа `POST /api/files`, а не собирается руками.

**Уборка файлов.** Файл, переставший быть обложкой, удаляется с диска: при замене
картинки на другую, при снятии обложки и при удалении новости. Правка новости
без смены обложки файл не трогает. Удаление происходит после успешного сохранения,
поэтому неудачный запрос картинку не портит.

## Редактируемые страницы

Тринадцать текстовых разделов сайта, содержимое которых правит модератор: контакты,
нормативные документы, учебные планы, блоки главной страницы. Никакой логики, кроме
хранения текста, за ними нет.

Раздел адресуется **слагом** — коротким латинским идентификатором в пути
(`contacts`, а не `7`). Слаг стабилен: он не зависит от того, какие `id` выдала
конкретная база, и переживает перенос данных со старого портала.

Набор разделов **закрыт**: тринадцать слагов создаются миграцией при первом запуске,
создать четырнадцатый или удалить существующий через API нельзя. Слаг захардкожен
в маршрутах фронтенда, поэтому удаление раздела означало бы неустранимую дырку
в навигации. По той же причине `PUT` по неизвестному слагу отвечает `404`,
а не создаёт новый раздел.

| Слаг | Раздел старого портала |
|---|---|
| `fields-of-study` | О кафедре → Направления подготовки |
| `contacts` | О кафедре → Контакты |
| `documents-department` | О кафедре → Нормативные документы → Кафедры |
| `documents-university` | О кафедре → Нормативные документы → Университета |
| `bachelor-edu-plans` | Учебная деятельность → Бакалавриат → Учебные планы |
| `bachelor-graduate` | Учебная деятельность → Бакалавриат → Защита ВКР |
| `bachelor-practices` | Учебная деятельность → Бакалавриат → Практики |
| `master-edu-plans` | Учебная деятельность → Магистратура → Учебные планы |
| `master-graduate` | Учебная деятельность → Магистратура → Защита ВКР |
| `master-practices` | Учебная деятельность → Магистратура → Практики |
| `scientific-activity-postgraduate` | Научная деятельность → Аспирантура |
| `home-before` | блок над лентой новостей на главной |
| `home-after` | блок под лентой новостей на главной |

Последние два — не страницы: собственного адреса у них нет, они выводятся
на главной над и под лентой новостей.

Ответ `GET /api/public/pages/contacts`:

```json
{
  "slug": "contacts",
  "title": "Контакты",
  "text": "## Как нас найти\n\nМосква, Вадковский переулок, 1",
  "createdAt": "2026-08-26T12:00:00+03:00",
  "updatedAt": "2026-08-26T14:30:00+03:00"
}
```

Тело `PUT /api/pages/contacts`:

```json
{ "title": "Контакты", "text": "## Как нас найти\n\n..." }
```

Слаг в теле запроса не передаётся: он берётся из пути и не редактируется.
Поля `id` в ответе нет — раздел адресуется только слагом.

**`text` — исходник Markdown, а не HTML.** Это единственное отличие от `content`
новости, где в базе лежит готовый HTML из редактора. Отсюда два следствия:

* рендерить `text` следует через `react-markdown` **без** `rehype-raw`. По умолчанию
  сырой HTML внутри Markdown этот пакет не исполняет; `rehype-raw` его включает —
  вместе с XSS. `dangerouslySetInnerHTML` неприменим по той же причине;
* бэкенд `text` не санитизирует. Санитайзер работает с HTML: применённый к исходнику
  Markdown, он экранирует служебные символы и портит разметку, которую модератор
  увидит в форме при следующей правке. Гарантия «браузер не исполнит чужой HTML»
  обеспечивается на шаге рендера.

**Пустая строка в `text` — легальное значение**: раздел нельзя удалить,
но можно опустошить, и `PUT` с `text: ""` делает именно это. Это единственное
поле, на которое не действует правило «пустая строка = `null`» из «Базового».

**`title` — подпись раздела для списка в админ-панели**, а не заголовок публичной
страницы: на старом портале заголовок рисовала навигация, и это поведение сохраняется.
Поле может прийти `null` — в перенесённых со старого портала строках оно заполнено
не везде.

## Преподаватели

Карточки профессорско-преподавательского состава. Публичные ручки две: список
для страницы «Преподаватели» и полная карточка. Правка — ниже, в подразделе
«Создание и правка карточек».

Карточка живёт отдельно от учётной записи: фамилия, имя, отчество и фото
хранятся в самой карточке, а не в профиле пользователя. Учётная запись
у преподавателя может быть, а может отсутствовать — на ответ публичных ручек
это не влияет.

Элемент списка `GET /api/public/teachers` (обёртка — страница, как у новостей):

```json
{
  "id": 3,
  "lastName": "Иванова",
  "firstName": "Мария",
  "patronymic": "Петровна",
  "position": "доцент",
  "degree": "CANDIDATE",
  "rank": "DOCENT",
  "avatarUrl": "/media/avatars/2026/08/a3f9.jpg"
}
```

Ответ `GET /api/public/teachers/{id}` — то же плюс остальные поля:

```json
{
  "id": 3,
  "lastName": "Иванова",
  "firstName": "Мария",
  "patronymic": "Петровна",
  "position": "доцент",
  "degree": "CANDIDATE",
  "rank": "DOCENT",
  "avatarUrl": "/media/avatars/2026/08/a3f9.jpg",
  "phoneNumber": "+7 (499) 972-95-84",
  "email": "m.ivanova@stankin.ru",
  "messenger": "@m_ivanova",
  "experience": 15,
  "professionalExperience": 8,
  "education": "МГТУ «СТАНКИН», специальность «Информационные системы»",
  "qualification": "инженер",
  "bio": "…",
  "examScheduleGraduation": "https://stankin.ru/uploads/exams-graduation.pdf",
  "examScheduleNonGraduation": null,
  "subjects": [
    { "id": 1, "name": "Базы данных" },
    { "id": 4, "name": "Проектирование информационных систем" }
  ]
}
```

Пояснения к полям:

* `email` и `phoneNumber` — рабочие контакты из карточки, а не из учётной
  записи; заполняет модератор;
* `experience` — общий стаж в годах, `professionalExperience` — стаж
  по специальности;
* `examScheduleGraduation` / `examScheduleNonGraduation` — ссылки на PDF
  с расписанием экзаменов выпускных и невыпускных курсов;
* `subjects` — дисциплины преподавателя, по алфавиту названий. Только
  в детальной карточке, в списке их нет;
* любое незаполненное поле приходит как `null` — включая `degree`, `rank`
  и `patronymic`.

**`degree` и `rank` — коды из закрытых словарей**, подписи рисует фронт —
так же, как с `postType` у новостей:

| `degree` | Подпись |
|---|---|
| `CANDIDATE_TECH` | кандидат технических наук |
| `DOCTOR_TECH` | доктор технических наук |
| `CANDIDATE_PHYS_MATH` | кандидат физико-математических наук |
| `DOCTOR_PHYS_MATH` | доктор физико-математических наук |
| `CANDIDATE_ECONOM` | кандидат экономических наук |
| `DOCTOR_ECONOM` | доктор экономических наук |
| `CANDIDATE_PED` | кандидат педагогических наук |
| `null` | без степени |

| `rank` | Подпись |
|---|---|
| `READER` | доцент |
| `PROFESSOR` | профессор |
| `null` | без звания |

Коды повторяют старый портал буква в букву, включая неудачный `READER`
вместо `DOCENT`: в старой базе лежат именно эти строки, и совпадение кодов
делает перенос данных копированием колонки без преобразований — по той же
причине, по которой сохранены старые имена таблиц. Должность (`position`) —
свободная строка, словаря у неё нет.

Сортировка списка — по умолчанию `lastName`, `firstName`, `id`; в `sort`
передаются поля карточки (`lastName`), путь `user.lastName` больше не работает.

### Создание и правка карточек

Права распределены как на старом портале: модератор (и админ) управляет любыми
карточками, преподаватель правит свою — целиком, кроме дисциплин. Дисциплины
назначает только модератор: так было и в старом (они правились через
Django-админку и в сериализатор ЛК не входили).

Тело `POST /api/teachers` и `PUT /api/teachers/{id}`:

```json
{
  "lastName": "Иванова",
  "firstName": "Мария",
  "patronymic": "Петровна",
  "position": "доцент",
  "degree": "CANDIDATE_TECH",
  "rank": "READER",
  "avatar": "avatars/2026/08/a3f9.jpg",
  "phoneNumber": "+7 (499) 972-95-84",
  "email": "m.ivanova@stankin.ru",
  "messenger": "@m_ivanova",
  "experience": 15,
  "professionalExperience": 8,
  "education": "МГТУ «СТАНКИН», специальность «Информационные системы»",
  "qualification": "инженер",
  "bio": "…",
  "examScheduleGraduation": "https://stankin.ru/uploads/exams-graduation.pdf",
  "examScheduleNonGraduation": null,
  "subjectIds": [1, 4]
}
```

Правила — те же, что у новостей:

* `PUT` — **полная замена**: поле, не пришедшее в теле, обнуляется, форма
  отправляет все поля;
* обязательны только `lastName`, `firstName` и `position` — как в старой
  модели; всё остальное может быть `null`;
* `avatar` — ключ файла, загруженного заранее через
  `POST /api/files?category=avatars`, по той же схеме, что обложка новости;
  ключ несуществующего файла — `400`;
* неизвестный код в `degree` или `rank` — `400` с `ProblemDetail`;
* `subjectIds` — `id` существующих дисциплин, неизвестный `id` — `400`;
* `DELETE` удаляет карточку физически и отвечает `204`; привязанная учётная
  запись при этом не удаляется и работать не перестаёт.

**Своя карточка** (`/api/teachers/me`) — те же тела, что выше, с двумя
отличиями: в теле `PUT` нет `subjectIds` (пришедшее поле игнорируется),
а ответы обеих ручек — полная карточка с дисциплинами, как публичная детальная.
`me` определяется по токену; если к учётной записи карточка не привязана,
обе ручки отвечают `404`.

**Дисциплины** (`GET` / `POST /api/subjects`) — словарь для формы карточки:
`{ "id": 1, "name": "Базы данных" }`, список постранично, сортировка
по `name`. Создание — `{ "name": "..." }`, имя обязательно и уникально,
дубль — `409`. Правки и удаления дисциплин в T-26 нет — появятся вместе
с админ-панелью, если понадобятся.

Что меняется против прежнего ответа списка (сводка для F-21):

* ФИО и фото приходят из карточки; поля учётной записи `userId` и `email`
  из элемента списка исчезают (`email` остаётся только в детальной карточке
  и означает рабочий контакт);
* добавляется `patronymic`;
* `degree` и `rank` — коды словарей вместо произвольного текста;
* вместо `avatar` (имя файла без адреса) приходит `avatarUrl` — готовый адрес
  для `<img>`;
* сортировка — `lastName` вместо `user.lastName`;
* появляется детальная ручка.

## Учебно-вспомогательный персонал (УВП)

Лаборанты, инженеры, методисты — карточки без степеней, званий, дисциплин
и учётных записей. Одна публичная ручка списка и модераторский CRUD;
детальной ручки нет — карточка целиком помещается в элементе списка.

Элемент списка `GET /api/public/helpers` (обёртка — страница):

```json
{
  "id": 2,
  "lastName": "Кузнецова",
  "firstName": "Анна",
  "patronymic": "Сергеевна",
  "position": "инженер кафедры",
  "avatarUrl": "/media/avatars/2026/08/c7d1.jpg"
}
```

Тело `POST /api/helpers` и `PUT /api/helpers/{id}` — те же поля без `id`,
вместо `avatarUrl` — `avatar` (ключ файла из `POST /api/files?category=avatars`).
Правила — как у карточек преподавателей: `PUT` — полная замена, обязательны
только `lastName`, `firstName` и `position`, ключ несуществующего файла — `400`,
`DELETE` — физическое удаление с `204`. Сортировка по умолчанию — `lastName`,
`firstName`, `id`.

## Конференции

Объявления о научных конференциях: даты проведения, организатор, контакты
и rich-text-содержимое. На старом портале — раздел «Научная деятельность →
Конференции».

Публичных ручек две. Список отдаёт страницу только видимых объявлений —
скрытые (`display: false`) из выдачи исключаются. Детальная на скрытое
или несуществующее объявление отвечает `404`: как и у новостей, скрытое
неотличимо от несуществующего. Модераторский CRUD устроен
как у новостей: `GET /api/conferences` и `GET /api/conferences/{id}` видят
скрытые, `POST` отвечает `201` с заголовком `Location` и созданным
объявлением в теле, `PUT` — **полная замена** (поле, не пришедшее в теле,
обнуляется), `DELETE` — физическое удаление с `204`.

Ответ `GET /api/public/conferences/{id}` (элемент списка — та же схема,
обёртка списка — страница, как у новостей):

```json
{
  "id": 5,
  "title": "Информационные технологии в промышленности — 2026",
  "description": "Ежегодная научно-практическая конференция кафедры.",
  "startDate": "2026-10-14",
  "endDate": "2026-10-16",
  "time": "10:00",
  "organizer": "кафедра УИТС, МГТУ «СТАНКИН»",
  "contactEmail": "conf@stankin.ru",
  "contactPhone": "+7 (499) 972-95-84",
  "content": "<p>Приглашаем к участию…</p>",
  "previewImage": "news/2026/08/a3f9.jpg",
  "previewImageUrl": "/media/news/2026/08/a3f9.jpg",
  "previewImageDescription": "Афиша конференции",
  "createdAt": "2026-08-27T12:00:00+03:00",
  "display": true
}
```

Пояснения к полям:

* `startDate` и `endDate` — календарные даты `YYYY-MM-DD`, `time` — время
  начала `HH:mm`; секунды, если клиент их пришлёт, при сохранении
  отбрасываются, и в ответе время всегда с точностью до минуты. Смещения зоны у них нет сознательно: конференция проходит
  «14 октября в 10:00» по местному времени площадки, а не в момент на шкале
  UTC — в отличие от `createdAt`, который остаётся ISO-8601 со смещением;
* однодневная конференция — `endDate: null`, и это единственное её
  представление: `endDate`, присланный равным `startDate`, при сохранении
  нормализуется в `null`, так что проверять равенство дат при рендере
  не нужно;
* `content` — rich-text HTML, как у новости; при сохранении сервер вычищает
  из него всё, что не входит в белый список тегов и атрибутов, поэтому
  `<script>` и обработчики событий до браузера не доходят. Содержимое,
  вычищенное до пустоты, сохраняется как `null`: у «пустого» `content`
  одно представление, а не два;
* rich-text здесь только `content`. Остальные строковые поля — `title`,
  `description`, `organizer`, `previewImageDescription` — плоский текст:
  сервер их не чистит и не обязан, а фронт обязан выводить их текстовым
  узлом, а не через `dangerouslySetInnerHTML`;
* обложка — тройка `previewImage` / `previewImageUrl` /
  `previewImageDescription` по правилам раздела «Обложка новости», включая
  проверку ключа и уборку файлов; загружается через `POST /api/files`
  с категорией `news`;
* автора у объявления нет — его не было и в старой модели;
* незаполненное поле приходит как `null`.

Тело `POST /api/conferences` и `PUT /api/conferences/{id}` — те же поля
без `id`, `createdAt` и `previewImageUrl`. Валидация:

* обязательны только `title` (до 255 символов) и `display` — тело без
  `display` даёт `400`, а не молча скрытое объявление;
* `endDate` и `time` имеют смысл только при заданном `startDate`:
  присланные без него — `400`; `endDate` раньше `startDate` — тоже `400`.
  Сообщения этих проверок приходят в `errors` под ключами `endDate`
  и `time` соответственно;
* некорректный адрес в `contactEmail` — `400`; пустая строка — это `null`,
  а не ошибка (общее правило из «Базового»);
* лимиты длины остальных строк: `organizer` — 255, `contactEmail` — 254,
  `contactPhone` — 32, `previewImageDescription` — 256; `description`
  и `content` длиной не ограничены.

Для F-24: поле `is_hidden` старой модели заменено на `display` с обратным
смыслом — соглашение о видимости у всех сущностей одно, как и предлагал
комментарий к типу в `planned.types.ts`. Против того же типа все
необязательные поля стали nullable (в нём они объявлены как `string`),
а однодневность кодируется только как `endDate: null`.

## Достижения кафедры

Награды, гранты и победы в конкурсах: краткое описание, rich-text-содержимое,
обязательная обложка и необязательная привязка к преподавателю. На старом
портале — раздел «Научная деятельность → Достижения».

Публичных ручек три. Список отдаёт страницу только видимых достижений —
скрытые (`display: false`) из выдачи исключаются. Детальная на скрытое
или несуществующее достижение отвечает `404`. Третья —
`GET /api/public/teachers/{teacherId}/achievements` — страница опубликованных
достижений одного преподавателя; её использует карточка ППС. Несуществующий
`teacherId` даёт не `404`, а пустую страницу: ручка фильтрует достижения
по ссылке, а не проверяет карточку. Модераторский CRUD устроен как
у конференций: `GET /api/achievements` и `GET /api/achievements/{id}` видят
скрытые, `POST` отвечает `201` с заголовком `Location`, `PUT` — **полная
замена**, `DELETE` — физическое удаление с `204`.

Ответ `GET /api/public/achievements/{id}` (элемент списка — та же схема,
обёртка списка — страница):

```json
{
  "id": 3,
  "title": "Победа в конкурсе «Инженер года»",
  "description": "Преподаватель кафедры стал лауреатом всероссийского конкурса.",
  "content": "<p>Награда присуждена за работы в области автоматизации…</p>",
  "previewImage": "achievements/2026/08/b41e.jpg",
  "previewImageUrl": "/media/achievements/2026/08/b41e.jpg",
  "createdAt": "2026-08-27T12:00:00+03:00",
  "display": true,
  "teacherId": 7,
  "teacherName": "Иванова Мария Петровна"
}
```

Пояснения к полям:

* `teacherId` и `teacherName` — привязка к карточке ППС. Достижение может
  быть кафедральным, а не персональным, и тогда оба поля — `null`.
  `teacherName` собирается сервером из фамилии, имени и отчества карточки:
  отдельный запрос за преподавателем ради подписи не нужен, а за ссылкой
  на карточку берётся `teacherId`;
* привязка переживает удаление карточки: если преподавателя удалили,
  достижение остаётся, а `teacherId` становится `null`;
* `content` — rich-text HTML, как у новости и конференции: сервер вычищает
  из него всё вне белого списка тегов и атрибутов. Отличие от конференции
  в том, что содержание **обязательно**, поэтому тело, вычищенное до пустоты
  (например, единственный `<iframe>`), — это `400`, а не сохранённый `null`;
* rich-text здесь только `content`. `title` и `description` — плоский текст:
  сервер их не чистит, фронт обязан выводить их текстовым узлом;
* обложка — пара `previewImage` / `previewImageUrl` по правилам раздела
  «Обложка новости», включая проверку ключа и уборку файла при замене
  и удалении записи; загружается через `POST /api/files` с категорией
  `achievements`. Поля `previewImageDescription` у достижения нет —
  его не было и в старой модели;
* автора у достижения нет — его не было и в старой модели;
* незаполненных полей, кроме пары `teacherId` / `teacherName`, у достижения
  не бывает: остальные обязательны.

Тело `POST /api/achievements` и `PUT /api/achievements/{id}` — те же поля
без `id`, `createdAt`, `previewImageUrl` и `teacherName`; вместо `teacherName`
приходит только `teacherId`. Валидация:

* обязательны `title` (до 100 символов), `description`, `content`,
  `previewImage` и `display` — тело без `display` даёт `400`, а не молча
  скрытое достижение;
* обложку нельзя снять правкой: `PUT` без `previewImage` — это `400`,
  а не достижение без картинки;
* `teacherId` необязателен; ссылка на несуществующую карточку — `400`;
* ключ несуществующего файла в `previewImage` — `400`;
* `description` и `content` длиной не ограничены.

Расхождения со старой моделью, важные для фронта: поле `is_published`
переименовано в `display`, поле `image` — в пару `previewImage` /
`previewImageUrl`; смысл обоих сохранён. Имена приведены к тем, что уже
используются у новостей и конференций, — общий сервис списка контента
на четыре раздела работает с одной схемой. Вместо строки `teacher`
с полным именем и отдельного `teacher_id` приходит пара
`teacherId` / `teacherName`.

## Пагинация списков

`GET /api/public/news`, `GET /api/news`, `GET /api/public/teachers`,
`GET /api/public/helpers`, `GET /api/public/conferences`,
`GET /api/conferences`, `GET /api/public/achievements`,
`GET /api/public/teachers/{teacherId}/achievements`, `GET /api/achievements`,
`GET /api/subjects` и `GET /api/pages`
отдают не массив, а объект-страницу:

```json
{
  "content": [ ... ],
  "page": 0,
  "size": 20,
  "totalElements": 137,
  "totalPages": 7
}
```

`content` — элементы текущей страницы (схема элемента — в Swagger),
`page` — номер страницы, **счёт с нуля**, `totalElements` — сколько элементов
всего с учётом фильтров, `totalPages` — сколько всего страниц при текущем `size`.

Управление — query-параметрами, все необязательны:

| Параметр | По умолчанию | Пример |
|---|---|---|
| `page` | `0` | `?page=2` — третья страница |
| `size` | `20` | `?size=5` |
| `sort` | у каждого эндпоинта свой, см. ниже | `?sort=title,asc` |

Сортировка по умолчанию: новости, конференции и достижения — по `createdAt`
по убыванию (новые сверху); преподаватели и УВП — по фамилии, затем имени по алфавиту;
дисциплины — по `name`; разделы (`GET /api/pages`) — по `id`. Последним ключом
сортировки везде идёт уникальное поле: без него порядок записей с одинаковой датой
или фамилией не определён, и при листании одна запись приходила бы дважды,
а другая не приходила бы вовсе. Если запрошенная страница
за пределами данных, приходит `200` с пустым `content` — это не ошибка.
Передача в `sort` несуществующего поля — `400` с `ProblemDetail`, в `detail`
указано имя неизвестного поля; фронту слать только поля из схемы.
