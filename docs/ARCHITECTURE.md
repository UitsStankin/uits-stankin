## 0. Трезвая оценка текущего состояния

### 0.1 Действующий сайт (uits_portal) — «работающий прототип с дырами»

**Что работает.** Сайт жив на uits.stankin.ru и реально закрывает процессы кафедры (~34 сотрудника + студенты):
новости/объявления, карточки ППС с расписанием и дисциплинами, база публикаций с тегами и поиском через Google
Scholar, календарь событий с напоминаниями в Telegram, 13 Markdown-разделов, аспирантура, достижения, конференции —
это и есть эталон функционала (матрица — MIGRATION.md §3). Ценность продукта подтверждена эксплуатацией.

**Но по коду** это студенческий проект, который нельзя развивать дальше без рисков:

**Критические проблемы безопасности (подтверждены по коду):**
- `SECRET_KEY` захардкожен в `settings.py` и закоммичен. `production.py` существует, но **не переопределяет
  `DEBUG=True`** — прод работает в debug-режиме при любом сценарии загрузки настроек. Более того, все entrypoints
  (`manage.py`, `wsgi.py`, `celery.py`) дефолтятся на `uits.settings`, а deploy.yml задаёт только
  `DB_ENVIRONMENT_FILE` — то есть, скорее всего, `production.py` вообще не загружается и прод живёт с
  `ALLOWED_HOSTS=['*']`.
- `TeacherAPIViewSet`, `HelpersEmployeeViewSet`, все вьюхи Excel-подсистемы — **без `permission_classes` → AllowAny**:
  аноним может создавать/править/удалять преподавателей и заливать PDF.
- SerpApi-ключ печатается в лог (`print(search_url)`); эндпоинт поиска — безлимитный `while True` по пагинации,
  сжигающий месячную квоту бесплатного тарифа SerpApi (100 запросов).
- `telegram_code` (секрет привязки) отдаётся в API-ответе и **перегенерируется при каждом `save()`** — привязка
  Telegram фактически сломана.

**Критические функциональные баги (подтверждены):**
- Парсер расписания читает **только последнюю страницу PDF** (`parse_schedule.py:16-21`, цикл затирает `table`).
- Напоминания календаря не работают как задумано: `next_notification_at` с `auto_now=True` затирается «сейчас»
  при каждом сохранении; celery-beat на float-интервалах (месяц = 28 дней) дрейфует от рестартов.
- PDF публикаций хранятся **base64 в TEXT-поле** и отдаются целиком списочным эндпоинтом.

**Систематические проблемы:** ноль автотестов (11 файлов `tests.py` — заглушки), CI без единой проверки деплоит
`git pull` прямо в прод, 44 отладочных `print()` (включая `print('ыыы')`), два параллельных семейства моделей
Teacher/Student, мёртвые приложения и роуты, платный шаблон Espire с целыми неиспользуемыми разделами в прод-бандле.

**Вывод:** переписывание оправдано. Но эталон — это *поведение* сайта, а не его код. Ни одно техническое решение
старого кода не переносим без проверки (список «не переносить» — [MIGRATION.md §7](MIGRATION.md)).

## 1. Репозитории: монорепо. Точка.

**Решение: один репозиторий** с каталогами `backend/`, `frontend/`, `schedule-service/`, `infra/`, `docs/`.

Почему монорепо, а не «по-взрослому» разнести:
- Вас **двое**. Продукт **один**, деплоится **вместе**. Разделение репозиториев — инструмент для независимых команд
  с независимыми релизными циклами; у вас его цена (дрейф API-контракта, синхронизация версий, три набора CI,
  PR-жонглирование при каждой сквозной фиче) не окупается ничем.
- Атомарные изменения контракта: поменял DTO на бэке + типы на фронте **одним PR** — это главное преимущество,
  его теряют первым при разносе.
- Единые docs/, единый набор compose-файлов, одна точка входа для нового участника.

«Сомнительно» — это не про монорепо, а про его текущую гигиену. Что чинить:

```
uits-stankin/
├── backend/              # Spring Boot
├── frontend/             # React (публичная зона + админка)
├── schedule-service/     # Python FastAPI (парсинг PDF) — создан в T-39/T-40
├── infra/
│   ├── docker-compose.yml        # дев: postgres (+ schedule-service)
│   ├── docker-compose.prod.yml   # прод: все сервисы
│   └── nginx/nginx.conf          # TLS, статика, /api, /media
├── docs/                 # ⚠️ сейчас НЕ закоммичены — добавить в git немедленно
└── .github/workflows/    # CI с path-фильтрами
```

CI для монорепо — **path-фильтры**, а не отдельные репо:

```yaml
on:
  pull_request:            # проверки на КАЖДЫЙ PR, не только main
  push: { branches: [main, dev] }
# jobs c условием изменённых путей:
#   backend-ci:  paths: backend/**      → gradle build + testcontainers
#   frontend-ci: paths: frontend/**     → tsc && eslint && vite build (+vitest)
#   schedule-ci: paths: schedule-service/** → pytest
#   deploy: только main, needs: [все ci]
```

Разносить репозитории имеет смысл ровно в одном будущем сценарии: портал передают другой команде по частям.
Не ваш случай.

## 2. База данных: PostgreSQL. MongoDB — категорическое нет

Данные портала — **реляционные насквозь**: `User↔Teacher` (1:1), `Teacher↔Subject` (M2M),
`Publication↔Tag` (M2M), `UserEvent↔User` (M2M assignees), `Schedule→Lesson→LessonDate` (иерархия с FK),
`Postgraduate` (два FK). Плюс:

- Миграция данных со старого сайта — **Postgres → Postgres с теми же именами таблиц** (конвенция уже принята).
  Mongo убивает это преимущество и превращает перенос в ETL-проект.
- FK-целостность, транзакции на несколько таблиц, JOIN-фильтры публикаций — всё это в Mongo придётся
  эмулировать руками.
- Никаких данных с «гибкой схемой» на портале нет. Rich-text HTML и Markdown прекрасно лежат в `TEXT`.

**Liquibase:** остаётся, работает с PostgreSQL как сейчас (yaml-ченджсеты, `ddl-auto: validate`).
Вопрос «как Liquibase работает с MongoDB» снимается вместе с MongoDB (расширение `liquibase-mongodb` существует,
но применять его незачем). Что добавить в существующие ченджсеты: **индексы** (Postgres не индексирует FK
автоматически: `news_post.author_id`, `news_post(display, created_at)`), rollback-блоки, сид админа, 13 слагов
Markdown-страниц и таблицу `refresh_token` (см. §4.5).

**Версия Postgres:** новый сайт стартует на **актуальном мажоре (17)**, а не копирует 15 из старого стека:
`pg_dump → restore` переносится между мажорными версиями, а EOL PG 15 — ноябрь 2027, прямо внутри горизонта
«минимальной поддержки». *Факт (2026-07-28): переход выполнен в T-19 — все compose-файлы и тестовый
контейнер на `postgres:17-alpine`. На сервере каталог данных от 15-й версии, если он там остался,
придётся переносить через `pg_dump`/`pg_restore` — учтено в T-17b.*

## 3. Redis, RabbitMQ, Kafka, MinIO — что из этого нужно

Масштаб системы: ~34 сотрудника, единицы уведомлений в день, новости 2/мес. Отсюда:

| Технология | Вердикт | Обоснование |
|---|---|---|
| **Kafka** | ⛔ никогда (здесь) | Event-streaming для кафедрального портала — resume-driven development. Удвоит ops-поверхность, не решив ни одной реальной задачи. |
| **RabbitMQ** | ⛔ нет | Все «очереди» проекта — это рассылка десятков Telegram-сообщений. Паттерн **transactional outbox в Postgres** (см. §4) даёт гарантию доставки без единого нового контейнера. |
| **Redis** | ⛔ сейчас нет; 🔭 позже возможно | Кандидаты на кэш: ответы SerpApi (но квота — месячная, кэш должен переживать рестарт → таблица в Postgres лучше), rate-limit логина (bucket4j in-memory достаточно для одной ноды). Redis вернётся в разговор только при горизонтальном масштабировании, которого не будет. |
| **MinIO** | 🟡 не сейчас; интерфейс — сразу | Один VPS → файлы на диске (`/media` том) + раздача через nginx. Но в коде — **интерфейс `FileStorage`** (`store/load/delete/url`) с `LocalFileStorage` сейчас; если захочется S3-семантики или второй ноды — дописывается `S3FileStorage` (MinIO/S3) без правки бизнес-кода. |

**Правило:** каждый контейнер в проде — это то, что вам двоим патчить, мониторить и бэкапить ближайшие годы
при «минимальной поддержке». Целевой прод-состав: **nginx, backend, postgres, schedule-service. Всё.**

## 4. Бэкенд: слои, модули, асинхронность

### 4.1 Слои и модули

Схема слоёв (уже реализована — сохранить): `Controller → Service → Repository → PostgreSQL`.
- Controller: только DTO + `@Valid`, никаких сущностей наружу.
- Service: `@Transactional` (сейчас нет ни одной аннотации — добавить на классы сервисов), бизнес-правила.
- Repository: Spring Data JPA; для связей — `@EntityGraph`/fetch join (как уже сделано в `TeacherRepository`).
- Ошибки: единый `@RestControllerAdvice` на `ProblemDetail` (RFC 9457) — один формат для валидации, 401/403, 404, 409.

Целевой набор модулей (`ru.stankin.uits.module.*`):

```
security/          # JWT, фильтры (cross-cutting)
common/            # advice-обработчик, пагинация, FileStorage, конфиги
module/
├── auth           # login, refresh
├── user           # профиль, смена пароля, управление пользователями (админ)
├── staff          # Teacher, HelpersEmployee, Subject
├── schedule       # Schedule/Lesson/LessonDate, импорт через schedule-service, сводное, экзамены
├── news           # Post (news|announcement), ConferenceAnnouncement
├── achievements
├── publications   # ScientificPublication, Tag, SerpApi-клиент
├── students       # Student, Postgraduate
├── pages          # EditablePage (13 markdown-слагов)
├── events         # UserEvent (календарь)
├── notifications  # outbox + планировщик напоминаний
├── telegram       # webhook, /register, TelegramUser, отправка
└── files          # upload, ресайз (Thumbnailator), выдача путей
```

«Админка» — это **не модуль**: это CRUD-эндпоинты в каждом модуле под `@PreAuthorize("hasRole('ADMIN')")`
(или MODERATOR), плюс React-интерфейс. Отдельного admin-бэкенда не существует.

### 4.2 Асинхронность: `@Scheduled` + `@Async` + outbox. Без брокеров

Все фоновые задачи проекта:

| Задача | Механизм |
|---|---|
| Напоминания о событиях (day/week/month) | `@Scheduled(cron = "0 * * * * *")`: выборка `WHERE next_notification_at <= now()` (индекс!), пересчёт следующей даты через `ChronoUnit` — не «28 дней в секундах». Состояние в БД → переживает рестарт, Quartz не нужен. |
| Отправка в Telegram | **Transactional outbox**: сервис в одной транзакции с бизнес-изменением пишет строку в `notification_outbox` (chat_id, payload, status, attempts, next_attempt_at); отдельный `@Scheduled`-воркер шлёт батчами с ретраями и backoff. Гарантия доставки без RabbitMQ. |
| Импорт Scholar / парсинг PDF / Excel | Синхронно с фронтовым «идёт загрузка» (админ-операции, редкие), либо `@Async` на ограниченном `ThreadPoolTaskExecutor`. |

`@EnableScheduling` + `@EnableAsync` + явные бины executor'ов с именами и размерами пулов. Никаких `new Thread()`
(в старом коде поток на каждое сообщение — не повторять).

### 4.3 Telegram-бот

- **Webhook**, не long polling (прод за nginx с TLS — условие Telegram выполнено). Long polling — только как
  dev-профиль для локальной отладки без публичного URL.
- Бот живёт **внутри монолита** (`module/telegram`) — тонкий клиент на `RestClient` к
  `api.telegram.org` (вариант A из IMPLEMENTATION.md §1). Библиотека-фреймворк не нужна для трёх команд.
- Диалоги: `/start`, `/register <код>`, `/cancel` — **stateless**, состояние диалога хранить негде и незачем.
  Если когда-нибудь появится многошаговый сценарий — колонка `chat_state` в `telegram_user`, не Redis.
- Webhook-обработчик: проверить `X-Telegram-Bot-Api-Secret-Token` → быстро ответить 200 → обработка в `@Async`.
  Дедупликация по `update_id` (Telegram ретраит доставку — обработчик обязан быть идемпотентным).
- `chat_id`, `user_id` — `BIGINT`. `telegram_code` генерируется **один раз**, не отдаётся списочными API.
- Исходящие — только через outbox (§4.2): ретраи, лимиты (~30 msg/s глобально, ~1/s на чат).

### 4.4 schedule-service (единственный микросервис)

Уже решено и остаётся в силе: Python FastAPI, `POST /parse` (PDF → JSON), `GET /health`; stateless, без БД,
доступен только из docker-сети. Spring сохраняет результат сам. Обязательные фиксы относительно старого парсера:
все страницы PDF (не последняя), структурированная 422 на незнакомый формат, тест на реальном PDF СТАНКИНа.
Excel-ведомости (фаза 5) — второй эндпоинт здесь же (pandas уже в экосистеме), не тащить POI в Java ради одного
модуля, если сервис всё равно есть.

**Реализовано в T-39/T-40**, все три обязательных фикса выполнены; контракт ответа и разбор формата PDF —
в `schedule-service/README.md`. Отклонение от исходного наброска: `POST /parse` отдаёт плоский список занятий
(`{lessons: [...]}` с полями `week_day`/`class_time`), а не дерево дней — Spring всё равно раскладывает его
в строки `ScheduleLesson`/`ScheduleLessonDate`, и дерево пришлось бы разбирать обратно. Ошибки приведены
к общему телу `{error, detail}`: `400` — нет файла в запросе, `413` — сверх лимита, `422` — незнакомый формат,
`500` — без подробностей наружу. Прод-часть (образ в GHCR, сервис в `docker-compose.prod.yml` без публикации
портов, гейт деплоя на его тестах) остаётся за T-17d.

**Бэкенд ходит в сервис по HTTP/1.1 принудительно.** JDK-клиент по умолчанию предлагает переход на HTTP/2
(`Upgrade: h2c`), uvicorn этого не поддерживает и рвёт разбор запроса — живой импорт падал с `503` при
здоровом сервисе. Версия зафиксирована в `ScheduleServiceClientConfig`; менять только вместе с проверкой
на поднятом стеке. Мок-тесты такое не ловят по устройству: `MockRestServiceServer` подменяет транспорт целиком.

### 4.5 Аутентификация

- **Access (15–30 мин, в памяти фронта) + refresh (7–14 дней, httpOnly cookie)** — вместо нынешнего одного
  24-часового access-токена без отзыва.
- **Refresh-токены живут в БД** (таблица `refresh_token`: hash токена/jti, `user_id`, `family_id`, `expires_at`,
  `revoked_at`) — иначе «ротация» декоративна: старый JWT остаётся валиден до истечения, а админ не может убить
  сессию. Логика: refresh → транзакционно проверить и пометить использованным, выдать новую пару;
  повторное использование старого токена = кража → отзыв всей family; grace-окно ~30–60 с на предыдущий токен
  (гонка двух вкладок с общей cookie). Админ-действие «завершить сессии пользователя» = revoke по family.
- Cookie refresh-токена: `HttpOnly; Secure; SameSite=Lax; Path=/api/users/auth/refresh` — cookie не ездит
  с обычными запросами и не доступна JS.
- **Роли — в claims access-токена**, БД-lookup на каждый запрос убрать. Компенсация устаревания ролей — короткий
  TTL access-токена.
- Починить фильтр: `try/catch (JwtException)` → чистый 401 через `AuthenticationEntryPoint`.
- Rate-limit на `/auth/login` (bucket4j), `lastLogin` писать при входе.
- Регистрации нет **и не будет** — аккаунты создаёт админ (осознанное решение старого сайта, оно верное).

*Факт (2026-08-27): реализовано в T-30 — access 15 минут, refresh 14 дней, таблица `refresh_token`
с ротацией, grace-окном в минуту и отзывом семейства при повторном использовании. Три отступления
от плана выше, каждое осознанное:*

1. *Cookie получила `Path=/api/users/auth`, а не `/api/users/auth/refresh`: `Path` — фильтр отправки,
   и с более узким значением ручка `logout` своей же cookie не увидела бы, а отзывать ей было бы нечего.*
2. *Роли в claims не переехали, поход в БД из фильтра остался. Он держит гарантию T-14 —
   заблокированная учётка отваливается мгновенно, а не доживает до конца TTL; при 34 учётных записях
   это один SELECT по unique-индексу. Претензия §4.5 к БД-lookup была про стоимость, здесь она нулевая.*
3. *Отзыва access-токена по списку `jti` нет: отзыв живёт на refresh-семействе, access умирает сам.
   Смену пароля закрывает колонка `users_user.tokens_not_before` — фильтр сверяет её с `iat` токена,
   поэтому выданные раньше access-токены умирают сразу, не дожидаясь своих 15 минут.*

*Побочно отменено решение T-19: режим CORS `allowCredentials` вернулся — без него браузер не примет
`Set-Cookie` на cross-origin ответ и не пришлёт cookie обратно. Белый список origin'ов остался,
`*` при `allowCredentials` браузер запрещает сам.*

## 5. Фронтенд-архитектура

### 5.1 Состояние: Zustand. Redux — нет. «И то и другое» — тем более нет

- **React Query** — всё серверное (списки, детали, мутации, инвалидация). Это 90 % состояния портала.
- **Zustand** — только клиентское: auth-сессия (access-токен в памяти + профиль), тема, язык, состояние сайдбара.
- Redux при таком раскладе не хранит ничего — добавлять его значит добавить boilerplate в проект, где им нечем
  управлять.

### 5.2 Структура (упрощённый FSD — не переусложнять)

```
src/
├── app/            # провайдеры (ОДИН QueryClient), RouterProvider, глобальные стили
├── pages/          # тонкие страницы-композиции (public/, cabinet/, admin/)
├── features/       # auth, news, teachers, schedule, events, publications, pages, admin-crud...
│   └── <feature>/{api,components,hooks}
├── shared/
│   ├── api/        # http-клиент, интерцепторы, query-key фабрики
│   ├── ui/         # кнопки, инпуты, DataTable, FormDrawer, Modal
│   ├── lib/        # cn, форматтеры дат
│   └── config/     # env, роуты, навигация
└── layouts/        # PublicLayout, CabinetLayout, AdminLayout
```

### 5.3 API-слой и токены

- Один axios-инстанс (или fetch-обёртка): `baseURL` из `VITE_API_URL`; request-интерцептор ставит
  `Authorization: Bearer`; response-интерцептор на 401 делает **один** `POST /auth/refresh`
  (cookie уходит сама) и повторяет запрос; при провале — logout + redirect.
- Access-токен — **в памяти** (Zustand), не в localStorage: на сайте пользовательский rich-text/Markdown-контент,
  XSS-поверхность реальна, httpOnly-refresh + in-memory-access — правильный компромисс.
- React Query: фабрики ключей по модулям (`newsKeys.list(filters)`, `newsKeys.detail(id)`), инвалидация в
  `onSuccess` мутаций; `staleTime` ~1–5 мин для публичных списков.

### 5.4 Роутинг

`react-router` 7, `createBrowserRouter`, lazy-загрузка страниц. Три зоны через layout-роуты:
публичная (все информационные разделы), `/cabinet` (за `ProtectedRoute`: профиль, календарь),
`/admin` (за `RoleRoute(ADMIN|MODERATOR)`: CRUD всех сущностей). 404/500 — обязательные страницы + error boundary.

### 5.5 Админка — главный скрытый объём

Django Admin давал CRUD «бесплатно»; теперь это ~15 сущностей ручного интерфейса. Не писать 15 раз одно и то же:
сделать **generic-набор**: `DataTable` (TanStack Table: сортировка, поиск, пагинация) + `FormDrawer`
(react-hook-form + zod по схеме сущности) + конфиг колонок/полей на сущность. Одна сущность = один конфиг-файл.
React-Admin **не берём** (см. §8): собственный тонкий каркас на TanStack проще стилизовать под Tailwind и не
навязывает свой data-provider поверх React Query.

### 5.6 Немедленные фиксы скаффолда (до любых фич)

1. Смонтировать `RouterProvider`, убрать второй `QueryClient` (оставить один — в `app/`).
2. Tailwind v4: перенести тему в CSS `@theme` (нативный путь v4) или добавить `@config "../tailwind.config.ts"` —
   сейчас **вся** дизайн-система мертва, компоненты рендерятся без стилей.
3. Переименовать `AppLAayout` → `AppLayout` (учесть case-sensitivity git на Linux-CI).
4. Выкинуть из `src/assets` наследие Angular-темы: иконочные шрифты 2018 года, ~100 картинок
  (включая личные фото людей — это персональные данные в git), неиспользуемые флаги локалей.
5. `.env` + `VITE_API_URL`, типы API переписать под контракт Spring (сейчас скопированы поля dj-rest-auth:
   `pk`, `isStaff` — контракт разъедется первым же запросом).
6. Включить vitest + RTL и фронтовый CI-job.

## 6. Миграция с Django: план

### 6.1 Данные (Postgres → Postgres)

Имена таблиц совпадают по конвенции — перенос данных это **один offline-скрипт**, а не система синхронизации:

1. `pg_dump` прода → staging-база.
2. Скрипт переноса (SQL или маленький Python/ETL): маппинг колонок 1:1 где совпадает; преобразования:
   - Quill-HTML контент → **прогнать через санитайзер** (OWASP/jsoup) при импорте, не доверять старой базе;
   - base64-PDF публикаций → декодировать в файлы `media/publications/`, в колонку — путь;
   - строковые даты расписания `DD.MM` → нормальные типы/поля с учётом года семестра;
   - роль-флаги и `auth_group` → булевы роли новой модели.
3. Медиа: `rsync media/` на новый том, пути в БД сохраняют относительную структуру.
4. **Пароли:** Django хранит `pbkdf2_sha256$iter$salt$hash`. Решение — кастомный `PasswordEncoder`
   (`DelegatingPasswordEncoder`: `{bcrypt}` по умолчанию + декодер django-pbkdf2 для legacy), с **rehash в BCrypt
   при первом успешном логине**. ~50 строк кода, никто из 34 пользователей не замечает переезда.
   (Запасной вариант — админ раздаёт новые пароли, пользователей мало; но энкодер чище.)

### 6.2 Параллельная работа и cutover

**Не делать** двустороннюю синхронизацию и долгую параллельную жизнь двух записываемых систем — при этом масштабе
это чистый убыток. Схема:

1. Новый портал доводится до паритета на своём поддомене/порте со staging-копией данных (это же UAT для кафедры).
2. **Инвентаризация публичных URL старого сайта** (роуты Angular, `/media/...`) и nginx-карта редиректов на новые
   пути — внешние ссылки (индекс поисковиков, страницы stankin.ru, старые рассылки) не должны падать в 404;
   снять карту нужно ДО отключения старого сайта, потом будет неоткуда.
3. Объявляется **content freeze** на старом сайте (1–2 дня, согласовать с кафедрой).
4. Финальный прогон скрипта миграции + rsync медиа.
5. Переключение nginx (или DNS поддомена) на новый стек; редирект-карта живёт минимум столько же, сколько fallback.
6. Старый сайт остаётся в read-only на внутреннем порту 2–4 недели как страховка, затем гасится.

### 6.3 Этапность

Фазы 0–5 из [MIGRATION.md §6](MIGRATION.md) остаются планом разработки. Два усиления:
- **Фаза 0 расширяется** пунктами §0.2 этого документа (JWT-401, CORS, advice, пагинация, springdoc 3.x,
  ротация секретов, CI на PR/dev) и реанимацией фронтенд-скаффолда (§5.6) — до этого новые модули не начинать.
- Контракт API фиксировать в OpenAPI **до** реализации каждого модуля (фронт и бэк работают от одного контракта).

## 7. DevOps и инфраструктура

### 7.1 Оркестрация: Docker Compose. Kubernetes — нет

Один VPS, 34 пользователя, два разработчика. K8s не даёт здесь ничего, кроме постоянного налога на поддержку.
Compose-файл в `infra/`, прод-состав:

```
nginx            # КАСТОМНЫЙ образ (multi-stage: vite build → nginx) — фронтенд запечён в образ;
                 # TLS (certbot), /api → backend, /media, лимиты размеров тел
backend          # Spring Boot; Liquibase выполняет миграции на старте
postgres         # 17-alpine; named volume; НЕ публиковать порт наружу
schedule-service # только во внутренней сети
```

Фронтенд деплоится **как образ nginx** — это снимает вопрос «как доставить dist на сервер» и делает откат
фронтенда таким же, как у бэкенда (предыдущий тег образа).

Обязательно: `healthcheck` у каждого сервиса + `depends_on: {condition: service_healthy}` (сейчас backend стартует
наперегонки с postgres); контейнеры не под root; `JAVA_OPTS` с лимитами памяти; log-rotation у docker.

### 7.2 CI/CD (замена текущему «собери на проде»)

Сейчас: тесты только на main; на VPS копируется **исходник** и там собирается образ; деплой через полный
`down && up` (даунтайм + рестарт Postgres). Целевая схема:

1. **PR/dev:** path-фильтрованные джобы — backend (gradle build + Testcontainers), frontend (tsc, eslint,
   vite build, vitest), schedule-service (pytest). Merge в dev без зелёного CI запрещён (branch protection).
2. **main:** сборка образов `nginx` (с фронтендом), `backend`, `schedule-service` **в CI** → push в GHCR
   с тегом `sha` (не только `latest` — иначе откатываться не на что). В compose образы параметризованы
   (`image: ghcr.io/...:${TAG}`); деплой-шаг по ssh пишет новый `TAG` в `.env` на VPS →
   `docker compose pull && docker compose up -d nginx backend schedule-service` (без down, postgres не трогается).
   **Откат = вписать предыдущий sha в `.env` и `up -d`.**
3. Изменения `infra/` (compose, nginx.conf) доставляются отдельным scp/rsync-шагом того же workflow —
   pull-only деплой сам по себе их на сервер не принесёт.
4. Тестируется тот же артефакт, который едет в прод (сейчас на проде собирается непроверенный образ с `-x test`).
5. **Реальность РФ-хостинга:** Docker Hub ограничивает pull с российских IP — прод не должен зависеть от
   docker.io. Либо все runtime-образы (включая postgres и базовый nginx) ретегаются в GHCR из CI и VPS тянет
   из одного реестра, либо на VPS настраивается registry-mirror в `/etc/docker/daemon.json`.
   Проверить `docker pull` с конкретного хоста ДО завязывания деплоя на эту схему.

### 7.3 Наблюдаемость — по росту, не по моде

- **Сразу:** Spring Actuator (`/actuator/health` — внутрь сети, для healthcheck), структурированные JSON-логи
  с request-id, `docker logs` + rotation.
- **Сразу и дёшево:** error-tracking на бэкенд и фронтенд — реальные ошибки пользователей вместо тишины.
  Sentry SaaS ушёл из РФ (блокировка аккаунтов, ingest может быть недоступен браузерам пользователей) —
  сначала проверить доступность с целевого хоста; рабочая альтернатива — **self-hosted GlitchTip**
  (один контейнер, живёт на существующем Postgres, совместим с Sentry SDK). Uptime Kuma — пинг доступности,
  **обязательно не на прод-VPS** (иначе умрёт вместе с ним), любой второй хост.
- **Позже, если появится потребность:** Prometheus + Grafana. Не ставить заранее — это ещё два сервиса
  в «минимальную поддержку».

### 7.4 Секреты и бэкапы

- Секреты: `.env` на VPS (chmod 600, вне git) + GitHub Actions Secrets для деплоя. Засвеченные
  `POSTGRES_PASSWORD` и `JWT_SECRET_KEY` ротированы локально 2026-07-27; в git-историю они
  не попадали (см. MIGRATION.md §8). Прод-значения хранить только в GitHub Actions Secrets.
- **Бэкапы отсутствуют и у старого, и у нового сайта — это сейчас самый большой инфраструктурный риск.**
  Ночной cron: `pg_dump -Fc` + tar медиа → offsite (rclone в любое облако/второй хост), хранить 14–30 дней,
  раз в квартал проверять восстановление.

## 8. Жёсткие правила проекта

### Категорически нельзя
1. **MongoDB** — данные реляционные, миграция Postgres→Postgres, FK-целостность. Тема закрыта.
2. **Kafka / RabbitMQ / Celery** — нет задач уровня брокера; outbox в Postgres покрывает гарантированную доставку.
3. **Kubernetes** — один VPS, двое людей.
4. **Микросервисы** сверх `schedule-service` — модульный монолит, пока команда < ~5 человек.
5. **Секреты в git** (уже обожглись — ротация + `.gitignore` + при желании gitleaks в CI).
6. **Несанитизированный HTML** от редакторов в БД или в браузер (в старом коде Quill-HTML не чистился).
7. Хранить **бинарники в БД** (base64-PDF в TEXT — главный антипаттерн старого кода).
8. Деплой с `git pull` и сборкой на проде; деплой без прогона тестов; merge в dev без CI.
   *Известное отклонение: текущий `deploy.yml` собирает Docker-образ на VPS — устраняется в T-17c
   (сборка в CI + registry), правило остаётся в силе.*
9. Дублировать серверные данные в Zustand/Redux — серверное состояние живёт в React Query.
10. Переносить решения старого кода «как есть» — каждый модуль сверяется со списком багов MIGRATION.md §7.
